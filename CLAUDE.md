# WXYC DJ — Claude Code Instructions

A small SwiftUI iOS app: sign in with dj.wxyc.org credentials, search the WXYC library with live results, view release metadata, and edit a per-DJ "bin" of favorites. Read `README.md` for the user-facing tour.

The local directory is `wxyc-dj-ios`; the Xcode project, scheme, and Swift module are all `WXYCDJ`; the display name is "WXYC DJ"; the bundle ID is `org.wxyc.dj`.

## Core conventions

- **Swift 6**, strict concurrency, `@Observable` (never `ObservableObject`).
- iOS **18.4+** target. iPhone-only (`TARGETED_DEVICE_FAMILY = 1`).
- SwiftUI throughout; no UIKit unless asked.
- TDD per `wxyc-ios-64/CLAUDE.md`: failing test → minimum implementation → refactor.
- **Do not introduce third-party packages without asking first.** The rule stands; two third-party packages have cleared it so far. The app uses Foundation, SwiftUI, Security (Keychain), two local packages — `WXYCAPI` (hand-written) and `WXYCAPIModels` (vendored generator output — see "Code Generation") — and three remote packages. Two are third-party and linked to the **app target only**: **`sentry-cocoa`** (`from: 8.58.4`, issue #106, asked for and approved) and **`posthog-ios`** (`from: 3.69.6`, issue #108, asked for and approved). The third is first-party and is **not** app-target-only: **`wxyc-swift-auth`** (`.upToNextMinor(from: 0.1.0)`, product `WXYCAuth`), the org's shared better-auth wire client, which `Packages/WXYCAPI` depends on in its own `Package.swift` and which `project.yml` *additionally* links onto the `WXYCDJ` app target as a pre-emptive mirror of the `WXYCAPIModels` belt-and-braces — a nested local package's transitive product is not reliably picked up for every link product of the app target, though that gap was observed for `WXYCAPIModels`, not for this package. It is governed by [`WXYC/wiki` `plans/wxyc-swift-auth.md`](https://github.com/WXYC/wiki/blob/main/plans/wxyc-swift-auth.md). Its release tags are **immutable** (the inverse of the org's moving `gha/v1` model), but note what that does and doesn't buy: it guarantees a tag keeps pointing at one commit, **not** that the next tag is source-compatible — so it is not on its own a licence for a wide range. The range is `.upToNextMinor` rather than the `from:` the two third-party packages use, because those are 1.0+ where a major range is what SemVer promises, while this one is deliberately 0.x until Phase E cuts 1.0 precisely because its API is expected to churn until both apps have adopted. Its arrival changes how this repo pins and builds — see "Dependency pins" below. Regenerating `WXYCAPIModels` additionally needs `npm`/`node`, `java`, and `rsync` on `PATH`, but only when the contract pin moves.

Follows the canonical rules in `../wxyc-ios-64/CLAUDE.md` — read it for SwiftUI idioms (`Task.sleep(for:)`, `foregroundStyle`, `clipShape(.rect(cornerRadius:))`, `Tab` API, `NavigationStack` + `navigationDestination(for:)`, `localizedStandardContains`, etc.). Repeat-rules are not duplicated here.

## File headers

Every hand-written Swift file (except `Package.swift`) starts with:

```swift
//

//  ModuleName
//
//  One-line purpose: what this file does and how it fits.
//
//  Created by <name> on MM/DD/YY.
//  Copyright © 2026 WXYC. All rights reserved.
//
```

`ModuleName` is `WXYCAPI` for files in `Packages/WXYCAPI/`, `WXYCDJ` for app sources, `WXYCAPITests` for tests.

The ~260 vendored files under `Packages/WXYCAPIModels/Sources/WXYCAPIModels/` (issue #75 — see "Code Generation" below) are the one exception: they carry the generator's own header (`// Filename.swift\n//\n// Generated by openapi-generator\n// https://openapi-generator.tech\n//`) instead, since they're machine output regenerated verbatim by `scripts/regenerate-api-types.sh`, never hand-edited.

## Project structure

```
WXYCDJ/                          App target sources
WXYCDJ/AppIcon.icon/             Icon Composer app-icon document (see below)
WXYCDJ/Telemetry/                Error reporting (issue #106) + product analytics (issue #108): the ErrorReporter/Analytics seams, one file per SDK import (Sentry, PostHog)
WXYCDJTests/                     App-target unit-test bundle (Swift Testing)
Packages/WXYCAPI/                Local SPM package: DTOs, AuthService, APIClient, URLScrubbing — pure Foundation, SDK-free
Packages/WXYCAPIModels/          Vendored SPM package: api.yaml-generated models (issue #75)
project.yml                      xcodegen spec (regen via `xcodegen generate`)
WXYCDJ.xcodeproj/                Generated; tracked in git for IDE convenience
```

**The `Packages/` ↔ `WXYCDJ/` line is a hard boundary, not a filing convention.** `WXYCAPI` and `WXYCAPIModels` are **pure Foundation and link no SDK**, which is what keeps them host-testable under `swift test` with no simulator; every SDK-touching line lives in the app layer instead. That is why issue #106's error reporting (and issue #108's product analytics, which extends the same split) work the way they do: the pure judgment — `URLScrubbing.swift` (strip a URL's query/fragment, keep scheme/host/path), flat at the package root beside `JSONCoders.swift` / `Configuration.swift` / `SignInIdentifier.swift`, the same test-tier split `ArtworkFailureClassification` documents — sits in `WXYCAPI`, while `WXYCDJ/Telemetry/` owns both SDKs' wiring and only two files in it import an SDK at all: `SentryErrorReporter.swift` (`Sentry`) and `PostHogAnalytics.swift` (`PostHog`) — plus `TelemetryBootstrap.swift`, which starts both. Do not add a package dependency on a third-party SDK to fix a layering awkwardness; move the code instead.

**App icon — do not resync `icon.json` verbatim from the design source.** `WXYCDJ/AppIcon.icon` is an Icon Composer (Liquid Glass) document compiled by `actool` via `ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon`; the design source lives outside the repo at `~/Pictures/Graphic Design/WXYC Assets/dj app/app icon/iOS/AppIcon.icon`. Icon Composer 27 emits two constructs that make **Xcode 26.x `actool` crash** rather than degrade (`error: Exception while running actool: *** -[__NSPlaceholderArray initWithObjects:count:]: attempt to insert nil object from objects[0]`, thrown from `selectCatalogIconComposerItemsFromCollection`), so the checked-in copy strips them: the top-level **`"features"` array** (any non-empty value — `refractivity`, `specular-location`) is **omitted**, and a **`"specular"` / `"specular-specializations"` value of `"outside"`** is rewritten to **`true`**. Every other IC-27 key (`refractivity-specializations`, `lighting-specializations`, `blur-material-specializations`, `shadow-specializations`, `translucency-specializations`) compiles clean on 26.x, and the compiled raster is visually indistinguishable — these two are opt-in rendering nuances. CI pins **Xcode 26.2** (`.github/workflows/ci.yml`), so keep the downgrade until the toolchain floor moves to 27. Re-exporting from Icon Composer re-adds both on save; re-apply the downgrade and verify with a standalone `actool` compile (recipe in README) rather than a full build.

The Xcode project is regenerated from `project.yml`. Run `xcodegen generate` after editing `project.yml` **and** after adding any new source files to `WXYCDJ/` or `WXYCDJTests/` — xcodegen bakes explicit file references into the pbxproj at generation time, so new files aren't picked up until you regen.

`WXYCDJTests` is the bundle for anything that has to `@testable import WXYCDJ` (view models, the AppDependencies composition root, etc.). Pure networking / DTO / auth tests stay in `Packages/WXYCAPI/Tests/WXYCAPITests` so `swift test` can run them on the host without booting a simulator. `WXYCDJTests/Support/StubRequestSession.swift` + `Fixtures.swift` are deliberate copies of their `WXYCAPITests/Support/` counterparts — promote them to a shared SPM test-support target if a third bundle ever needs them.

## Networking layer (`WXYCAPI`)

- `Configuration.swift` → `WXYCAPIConfiguration` (auth + API base URLs, timeout). `.production` and `.localDevelopment` presets.
- `TokenStorage.swift` → `TokenStorage` protocol with `TokenSlot.sessionToken` / `.jwt`.
- `KeychainTokenStorage.swift` → kSecClassGenericPassword, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. No iCloud sync.
- `InMemoryTokenStorage.swift` → `OSAllocatedUnfairLock`-backed in-memory store for unit tests.
- `JWTPayload.swift` + `JWTDecoder` → client-side parse only; the server validates the signature against JWKS.
- `AuthService.swift` → `@MainActor @Observable`. State: `.unknown` → `.signedOut | .signingIn | .signedIn(payload: JWTPayload?)` (`Equatable`, so `.onChange(of:)` can observe it). Owns sign-in — by password (routed by `SignInIdentifier` to `/auth/sign-in/email` or `/auth/sign-in/username`) or by mailed one-time code (`sendLoginCode(identifier:)` → `signIn(email:otp:)`, issue #100) — capturing the `set-auth-token` response header on every route, JWT exchange (`GET /auth/token`), JWT cache with 60 s leeway, sign-out, and `restoreSession()` for cold launch. `isSignedIn` is the convenience the Spotlight deep-link handler (step 7) reads to decide present-now vs. stash-and-replay. **Issue #53 transient/terminal split:** the session token is the credential, the JWT a derived re-mintable artifact, so `signIn`/`restoreSession` are two legs — establish the session, then exchange for a JWT. A JWT-leg failure that is *transient* (5xx / network / undecodable-2xx body) keeps the session token and enters a **pending window** `.signedIn(payload: nil)` (`nil` = "session established, JWT pending"; nothing reads the payload off `state`, every consumer keys on the case via `isSignedIn`), re-minting the JWT lazily on first `currentJWT()`; only a **401** on `/auth/token` is terminal (roll back, clear tokens, `.signedOut`). `currentJWT()` is the shared lazy-refresh chokepoint: a 401 there **demotes** to `.signedOut` (clearing tokens, so `RootView` swaps `MainView` → `LoginView`) — but **only if the rejected bearer is still the current `sessionToken`**, so a stale in-flight refresh resuming after a concurrent re-sign-in (interactive callers and the background catalog refresh share one `AuthService`) can't clobber the new session. A successful lazy refresh leaves `state` untouched (no `onChange` churn on the ~hourly refresh). `clearLocalSession()` is the one terminal-cleanup primitive shared by `signIn`'s rollback, `restoreSession`'s 401 arm, `currentJWT`'s demotion, and `signOut`. **Issue #66 success-path guard:** a private monotonic `sessionEpoch` (bumped by `clearLocalSession` and by `signIn` establishing a new token, but **not** by a `set-auth-token` rotation) is captured at the top of `refreshJWT` and re-checked on its 2xx success path *before* persisting — so a `signOut` (or re-sign-in) that lands during an in-flight refresh can't be resurrected by `captureRotatedSessionToken` re-writing the rotated bearer + JWT to the Keychain (which would leave `state == .signedOut` but a live token that the next cold-launch `restoreSession()` silently signs back in). It's the success-path mirror of `currentJWT`'s 401 token-identity guard; because rotation keeps the same generation, a benign overlapping double-refresh still resolves a JWT for both callers. **Cookies are suppressed on every request, and `CookielessSession` (in `RequestSession.swift`) is the policy's one home** — a `RequestSession` decorator every consumer in the package (`AuthService`, `APIClient`, `DiskThumbnailProvider` today) wraps its injected session with at `init` and **stores as a `CookielessSession`**, so dropping the wrap is a compile error rather than an omission, and no transport function flips `httpShouldHandleCookies` itself any more (issue #99, closing a gap #98 left open: back when the policy was a flag two transport functions each set, `DiskThumbnailProvider` was added as a third consumer over `URLSession.shared` with cookie handling at its default and nothing caught it). See the `RequestSession.swift` bullet for the shape and its scope limit. This is load-bearing, not hygiene. better-auth's `bearer()` after-hook *adds* `set-auth-token` without stripping the `Set-Cookie` it rides alongside, so a default `URLSession` stores the session cookie and replays it to the host forever — including on the **next sign-in**. better-auth registers `originCheckMiddleware` **globally on every non-GET** (`api/index.mjs`), and `validateOrigin` enforces the `Origin` header *only when a cookie is present* (`useCookies = headers.has("cookie")`); a native client sends no `Origin`, so a cookie-bearing sign-in is refused with `403 MISSING_OR_NULL_ORIGIN` **before any credential check**. Verified against production on **both** sign-in routes — this is not specific to the issue-#97 email route, and the `/sign-in/email`-only `formCsrfMiddleware` is a red herring, since the global middleware already covers both. A clean `signOut` self-heals (better-auth expires the cookie), but the paths that clear tokens *without* a network sign-out — `currentJWT`'s 401 demotion, `restoreSession`'s 401 arm, `signIn`'s rollback, a `signOut` whose call fails — leave the cookie behind, so the next sign-in 403s. Suppression stops the jar filling **and** stops a pre-existing cookie being sent, and keeps the session off disk outside the Keychain, which `clearLocalSession()` can't reach (issue #52's leave-no-trace). **Issue #100 — the OTP path is a third credential onto the same lifecycle.** `POST /auth/sign-in/email-otp` is a peer of the two password routes: it ends in the same `setSessionCookie`, and `bearer()` is global, so `set-auth-token` arrives identically. That is why redeeming a code adds no session machinery — **both halves of signing in are shared, not restated**. `completeSignIn(establishing:)` owns the orchestration (the #57 grace-anchor reset, the #66 generation bump, leg 1's rollback, leg 2's transient/terminal split) and takes a closure yielding a session token; `establishSession(path:body:rejectionCopy:)` owns the wire (the `set-auth-token` capture, the body-token fallback, the status table). Each public `signIn` overload is one call passing its leg-1 closure. The split is deliberate: those invariants each closed a specific defect, and a second route free to restate them is a second route free to restate one *wrongly*, invisibly, until the interleaving it covers recurs. `establishSession` classifies **status** and the caller words the **rejection** — `rejectionCopy` defaults to rendering the server's message (what the password routes want) and the OTP route passes `OTPRejection.copy`, whose strings are deliberately **unpunctuated** because `.rejected`'s renderer appends a period and carries no doubling guard. `sendLoginCode` is the two-leg pre-step and deliberately does **not** touch `state` (no session exists yet; the view model owns that step's in-flight and error surface) — hence `clearLastError()`, since `lastError` is otherwise only cleared at a sign-in's start and a sign-out's end, which would leave a failed code verify showing under the password form. **The three endpoints speak two error vocabularies, and conflating them produces wrong copy.** better-auth's routes (send, verify) answer `{message, code}`, which `APIErrorResponse` decodes — so the send leg's `400 INVALID_EMAIL` must render verbatim, since `dj@wxyc` classifies as an email on the `@`, skips the lookup, and reaches `z.email()`; that is precisely the payoff `SignInIdentifier` routes on `@` to obtain, and hiding it behind "Server error (400)" would undo it. Backend-Service's own `/auth/wxyc/lookup-email` and the Express limiter answer `{error: …}`, which `APIErrorResponse` (required `message`) cannot decode at all, so that leg maps by **status** only. `{"email": null}` is the single failure this flow can name precisely ("No account matches that username" — never "or email", since an `@` skips the lookup); everything else is vague by design, because `disableSignUp: true` makes the send step report success for an unknown address and the verify step answer `INVALID_OTP` indistinguishably from a wrong code. A **429 is `.rateLimited` on every credential route, including the password one** — reachable in ordinary use, since the limiter keys on `X-Real-IP` (10/15 min) and the control room shares an egress address while an OTP sign-in spends three requests to a password's one. The JWT leg is deliberately unchanged and still renders a 429 as `.serverFailure`. Server-side asymmetry worth knowing: `requireEmailVerification: true` refuses an unverified account at password sign-in, but the OTP route *marks it verified* and proceeds — mailbox possession being the proof the verification email would have demanded (ADR 0006). **Status mapping:** only a **401** means "wrong credentials" (`.invalidCredentials`); **400/403** carry a reason the server named and the DJ can act on — a malformed email, an unverified address (`requireEmailVerification: true` is set server-side), a rejected origin — so they map to `.rejected(message:)`, rendered verbatim rather than behind `.serverFailure`'s "Server error (4xx)" prefix. Folding 403 into `.invalidCredentials` (as it was before) is what made the origin-check refusal read as a bad password, i.e. invisible.
- `SignInIdentifier.swift` → the **sign-in router** (issue #97). One login field, two better-auth routes that are **not** interchangeable: `/sign-in/username` validates the identifier's *shape* before it looks up any user, and Backend-Service registers the plugin as `username({ minUsernameLength: 2 })` with **no** `usernameValidator` override, so better-auth's default `/^[a-zA-Z0-9_.]+$/` applies and an `@` is rejected outright with `422 INVALID_USERNAME` — whose message is literally "Username is invalid". That is why every email sign-in failed at any password before #97. `SignInIdentifier(_:)` classifies on the **`@`**, deliberately *not* dj-site's `isValidEmail` (`useLogin` in `src/hooks/authenticationHooks.ts`), for three reasons: `@` is the exact complement of the failure — the one character a username can never hold, so no identifier is plausible on both routes; it gives a **typo'd** email a better error, since `dj@wxyc` is "not an email" to a regex and would fall back to the username route for the same misleading 422, where `/sign-in/email` validates with `z.email()` and answers `400 INVALID_EMAIL`; and `isValidEmail` lives in `@wxyc/shared`, which has no Swift distribution, so porting its regex would fork a shared validation source of truth into a copy free to drift. The converse case is deliberate too — `dj-name` (a hyphen is outside the username character class but says nothing about email) stays on the username route for an honest 422 rather than being mistranslated into "Invalid email". The same predicate decides a **third** thing since issue #100: `displayTarget` — whether the app already knows the DJ's email or had to ask `POST /auth/wxyc/lookup-email` for it. A looked-up address is never displayed (the route is "a mild enumeration vector" Backend-Service accepts because it is rate-limited; rendering its answer would put it on screen), so the code screen shows a typed email and otherwise the literal "your registered email" — the line dj-site draws in `LoginFormSwitcher.tsx`. It lives here so the `@` predicate is applied once, and `AuthService.sendLoginCode` hands it out as `LoginCodeDestination.displayTarget`, which is what keeps this type **internal** rather than widening the package's public surface for a display string. The type owns **both** the path and the body key (`SignInRequest` vs `EmailSignInRequest`) so the two can't drift apart; everything downstream is route-agnostic — `bearer()` is a global plugin, so `set-auth-token` arrives identically and the #53/#66 state machine is untouched. `AuthError.invalidCredentials`'s message went identifier-neutral in the same change, since a 401 now also reaches it from the email route.
- `APIClient.swift` → URLSession wrapper. Attaches `Authorization: Bearer <jwt>`; the session it holds is wrapped in `CookielessSession` at `init` (see the `AuthService` bullet for why a stored better-auth session cookie breaks the *next sign-in*), so `fire` no longer touches `httpShouldHandleCookies` itself; on a 401, calls `authService.invalidateJWT()` and retries once (the shared `perform` transport core returns the `HTTPURLResponse` so callers impose their own status policy — `sendRaw` requires 2xx, `catalog` also accepts 304). Typed methods: `searchLibrary`, `albumInfo`, `albumMetadata`, `getBin`, `addToBin`, `removeFromBin`, and `catalog(ifModifiedSince:)` — the conditional-GET `GET /library/catalog` bulk export (issue #19) returning `CatalogFetchResult` (`.notModified` on a 304, else `.modified(rows:lastModified:)`); the body is gzipped NDJSON (one `CatalogRow` per line, transparently inflated), and the raw `Last-Modified` string is echoed back verbatim as `If-Modified-Since`. The transport `fire` reports each outcome to the `ConnectivityMonitor` hook (#56) — server-answered → online, thrown transport error → offline — **except a cancelled request** (`URLError.cancelled` / `CancellationError`), which is *not* a connectivity signal (the issue-#58 search debounce cancels the in-flight task on every keystroke); latching offline there would wrongly route later searches to the local clone, and (pre-#81) with no self-recovery at all. The half-open probe now bounds that damage to one `probeCooldown`, but the carve-out is **still load-bearing** and must not be reworked into a probe trigger: a debounce that cancels on every keystroke would otherwise latch on every keystroke *and* spend each window's single allowance on a request the DJ already superseded. So cancellation surfaces the error without touching the monitor.
- **Bin wire shape — trust the server, not `api.yaml`.** `api.yaml`'s `/djs/bin` GET still refs a `DJBinResponse` envelope of `BinEntry` rows (`{dj_id, entries: [{id, dj_id, album_id, added_at, …}]}`). **No such shape is ever emitted, and `bins` has no timestamp column at all.** `djs.controller.getBin` `res.json`s `getBinFromDB`'s result directly: a **bare array** of the denormalized library join — `album_id`, `album_title`, `artist_name`, `alphabetical_name`, `label`, `code_letters`, `code_artist_number`, `code_number`, `format_name`, `genre_name`, `legacy_release_id` — i.e. api.yaml's own `BinLibraryDetails`, which is what dj-site decodes (`lib/features/bin/api.ts`). The iOS `BinEntry` was written from the fictional schema, so every Bin-tab load failed with "Expected to decode Dictionary<String, Any> but found an array instead"; it now mirrors `BinLibraryDetails`. Consequences: **the album is the bin's key** (`BinEntry.id == albumId`; there's no per-row bin id on the wire, and `DELETE /djs/bin` deletes every row for a `(dj, album)` pair), and there's **no added-at to sort by** — `BinViewModel.normalized` sorts by `alphabetical_name` then album title (the server has no `ORDER BY`, so its order is arbitrary and would reshuffle between refreshes) and collapses duplicate album ids. `POST /djs/bin` returns `201` with the **raw inserted `bins` row** (`{id, dj_id, album_id, track_title}`), not a bin entry, so `addToBin` deliberately doesn't decode the body — the 2xx is the acknowledgement. Before adding any bin field, read `Backend-Service/apps/backend/services/djs.service.ts`. **This is an interim state, not standing policy:** [WXYC/wxyc-shared#344](https://github.com/WXYC/wxyc-shared/issues/344) reconciles the GET (points the 200 at an array of `BinLibraryDetails` and declares `alphabetical_name`, which the schema is missing today, so `BinEntry` is currently a *superset* of it) and [#359](https://github.com/WXYC/wxyc-shared/issues/359) covers POST/DELETE. Until #344 lands, issue #75's DTO codegen regenerates the fictional `DJBinResponse` / `BinEntry` pair from that schema — they *are* vendored in `WXYCAPIModels`, and inert only because nothing in `WXYCAPI` typealiases to them. `WXYCAPI.DJBinResponse` was deleted outright in #77; do not reintroduce it. The generated type that matches the real wire is `BinLibraryDetails` — see the DTO table in "Code Generation" below.
- `JSONCoders.swift` → custom ISO-8601 decoder that handles both fractional-seconds and plain forms (since Backend-Service emits both). **There is deliberately no date-only (`YYYY-MM-DD`) branch, and adding one back reintroduces the defect issue #79 removed.** A `Date` is an instant, so parsing a bare calendar day into one invents a time-of-day and a UTC anchor the value never had, and every later render through `Calendar.current` then slips to the previous day on any host west of UTC. The strategy applies to *every* `Date` field the decoder meets, so the old fallback did that silently to any date-only field added later. Nothing lost tolerance when it went: the only two fields decoding to `Date` through it are `AlbumInfo.addDate` and `AlbumSearchResult.addDate`, both from `library.add_date`, which is `timestamp with time zone` in Backend-Service's schema and `format: date-time` in api.yaml — the genuinely date-only columns (`rotation.add_date` / `kill_date`, Postgres `date` via `::text`) are not decoded as `Date` anywhere. A date-only field that wants a type should use `CalendarDate`, which decodes through its own `singleValueContainer` and never touches this strategy. The same file holds **`WXYCDateFormatting`**, the render-side counterpart: its GMT pinning is no longer papering over a fabricated instant but is simply an internal anchor (a `Date.FormatStyle` can only format a `Date`, so a calendar day must be materialized as one) — constructed in GMT and formatted in GMT, both halves in one type so they can't drift. It vends `dateOnly(_ day: CalendarDate)` for narrowed values and `dateOnly(fromISOString:)` for the one path still holding the raw wire string, the latter delegating to the former so the two can never render the same day differently.
- `DTOs/RotationPredicate.swift` → `RotationKillDate` (the three-state expiry) plus the one client-side rotation rule that reads it (issue #79). The rule mirrors the server's `rotation_bin != null && (kill_date == null || kill_date > CURRENT_DATE)` against the client's own calendar day, because the export defers daily expiry to the client; it is shared so `CatalogRow` (offline clone) and `AlbumInfo.Rotation` (online) cannot answer differently for the same album on the same screen. **The comparison is over `CalendarDate`**, whose ordering is a total order over `(year, month, day)` that never consults `Calendar`/`TimeZone` — that removes the old padded-`"YYYY-MM-DD"` lexicographic compare whose "must be zero-padded" precondition was enforced only by a doc comment and an `internal` keyword. **Why `RotationKillDate` is an enum and not a `CalendarDate?`** — the obvious reading of #79, and wrong: absent and unreadable are *opposite* answers (absent = no expiry = in rotation indefinitely; unreadable must fail **closed**), so collapsing an unparseable value into `nil` leaves a record whose expiry we can't read in rotation forever. Typing it `CalendarDate?` and decoding strictly instead makes `CatalogRow` **throw**, and a throw inside `APIClient.decodeNDJSON` fails the *whole* catalog fetch rather than one row — costing the entire clone refresh over one album's badge, and breaking the `CatalogRow` ↔ `AlbumInfo.Rotation` parity matrix (issue #95) that asserts both fail closed identically on `"not-a-date"` / `""` / `"2026-6-2"`. So `CatalogRow` decodes the raw string and narrows via `RotationKillDate(wireValue:)`, keeping the same per-field tolerance its `artwork_url` and `rotation_bin` decoding already has. There is deliberately **one** predicate entry point, not an overload per representation: both types hand it a `RotationKillDate`, `AlbumInfo.Rotation` converting its still-raw string at the call. `RotationKillDate`'s `Codable` encodes the **bare wire value** (string or null), never an enum envelope — `SQLiteCatalogStore` persists `CatalogRow` as a `JSONCoders` blob, so that encoding *is* the clone's on-disk format, and an `.unreadable` value round-trips verbatim rather than being normalized away by a client that couldn't parse it. Read `RotationKillDate.day` (the `CalendarDate?`) only for display; it is `nil` for both the absent and unreadable cases, so never branch rotation state on it — ask the row's `isInRotation(asOf:timeZone:)`. The **prefix-tolerant parse lives on `CalendarDate`, not here**: `DTOs/CalendarDate.swift`'s `init?(leadingDayOf:)` takes a value's leading ten bytes, so a full timestamp stays comparable against a bare day without being reinterpreted through a time zone. It sits beside the strict decoder it deliberately relaxes rather than on the rotation rule, because nothing about it is rotation-specific and hanging it there left `WXYCDateFormatting` reaching into a `DTOs/` domain namespace to parse a date. It scans UTF-8 bytes with no intermediate array or `String`, which matters because it runs once per kill-date-bearing row on the full NDJSON catalog decode **and** again on `SQLiteCatalogStore.ensureSearchIndex()`'s whole-clone re-decode.
- `RequestSession.swift` → tiny protocol over `URLSession.data(for:)` so tests can inject a `StubRequestSession`, **plus `CookielessSession`, the one home of the package's no-cookie policy** (issue #99). It's a decorator that flips `httpShouldHandleCookies` off on every request and forwards, so the policy holds whatever session performs the fetch — and each consumer stores its session **as a `CookielessSession`**, not as an `any RequestSession`, which makes assigning the raw injected session a compile error rather than something a fourth consumer has to remember. The full better-auth argument for *why* (a stored cookie arms `originCheckMiddleware` and 403s the next sign-in) lives on the type; the `AuthService` bullet summarizes it. Scope is **requests this package issues**: SwiftUI's `AsyncImage` covers load on `URLSession.shared` outside `RequestSession` entirely and are not covered — only a process-wide `HTTPCookieStorage` denial would reach them.
- `Connectivity/ConnectivityMonitor.swift` → the `@MainActor @Observable` app-wide online/offline signal (#56), owned by `AppDependencies`. Two signals feed it with **last-write-wins** precedence — the OS path (via the `PathProvider` seam) and real request outcomes (`APIClient.fire` / `AuthService.send`) — because a `.satisfied` path lies (captive portal, backend down), so a transport failure **latches offline even under a satisfied path**. Both funnel through the `nonisolated ingest(isOnline:)` into one unbounded `AsyncStream` drained by a single consumer, so near-simultaneous signals apply in submission order (independent `Task { @MainActor }` hops have no ordering guarantee, and out-of-order application would leave `isOnline` reflecting the *stale* signal). `reconnects` yields once per offline→online edge, cause-agnostic, buffered **newest-1** (#61's queued-bin flush attaches after launch and must wake on the *next* edge, not replay the whole app-lifetime backlog). **Issue #81 half-open probe:** the latch had no exit reachable from the search surface — `LibrarySearch`'s offline branch issued no request, so no outcome, so no un-latch, and `NWPathMonitor` only fires on path *changes*; one timed-out request stranded every subsequent keystroke on local results until the DJ did something else entirely. The monitor now owns a circuit-breaker cooldown (`defaultProbeCooldown` = 30 s, injectable, with the time source injected as `now: @Sendable () -> ContinuousClock.Instant` so tests drive a `ManualClock` instead of sleeping — **monotonic, not `Date`**, because everything here measures an elapsed interval and a backward wall-clock correction would otherwise put the anchor in the future and block every probe until wall time caught up; `ContinuousClock` rather than `SuspendingClock` so the cooldown keeps elapsing while the device sleeps): `isHalfOpen` is the **side-effect-free** eligibility read and `consumeProbe() -> Bool` atomically claims the window's **single** allowance — synchronous and `@MainActor`-isolated with no `await` between check and claim, so no two callers can both win. The state lives here, not in `LibrarySearch`, so that the allowance is monitor-wide: `LibrarySearch` is the only caller today, and `AlbumDetailView` / `BinViewModel` / `CatalogRefreshService` are **documented future readers** who'd want the same allowance rather than each inventing their own cooldown (the source comment on `consumeProbe()` says the same; until one of them adopts it, the latch's only exit remains the search surface). Two anchors: `offlineSince` moves forward on **every** offline signal (not just the online→offline edge, so a failed probe restarts the cooldown from the failure rather than reopening the window immediately), and `probeClaimedAt` records **when** an allowance was handed out; eligibility measures `probeCooldown` from the **later of the two**. The `max` is load-bearing rather than defensive: a claimed probe may report no outcome at all — `APIClient.perform` resolves a bearer before touching the network, so a signed-out `AuthService` throws `.notSignedIn` with nothing fired, and the cancellation carve-out reports nothing by design — and since `offlineSince` only moves inside `apply(isOnline:)`, keying release solely on it would let one silent probe spend the allowance **permanently** and strand the monitor offline forever, reintroducing the exact dead end #81 removes. A timestamped claim makes a silent probe cost one cooldown instead. Going online clears both anchors, so the reconnect edge and the half-open bookkeeping stay consistent whatever the cause.
- `Catalog/CatalogStore.swift` + `Catalog/SQLiteCatalogStore.swift` → the id-keyed on-device catalog clone (issue #19 step 2). `CatalogStore` is a `Sendable` protocol (`row(id:)` O(1) lookup, `count()`, `lastModified()`, `replace(rows:lastModified:)`) so the shared `CatalogRefreshService` (step 4) can be spied. It is now purely the **deep-link read model** plus the **replace target**: issue #36 moved the Spotlight diff index-side (the indexer diffs the in-memory export snapshot against its own persisted fingerprint map), so the issue-#19 store-paging primitives `ids()` (the `SELECT id` diff input) and `rows(after:limit:)` (the keyset bulk read the indexer paged) were removed — they had no remaining callers. `SQLiteCatalogStore` is an `actor` over raw `import SQLite3`: rows are `JSONCoders`-encoded `CatalogRow` BLOBs in `catalog(id INTEGER PRIMARY KEY, row BLOB NOT NULL)`, the verbatim `Last-Modified` watermark lives in a `meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)` row (`NOT NULL` because the store DELETEs the row for a nil watermark rather than storing NULL), and a `200` wholesale-replaces both in one `BEGIN IMMEDIATE` transaction (a duplicate id, or any failure, rolls back and keeps the last-good clone — same fail-closed posture as the NDJSON parser). The C handle is owned by a nested `Connection` class so its `deinit` can `sqlite3_close` (an actor's nonisolated `deinit` can't touch the non-`Sendable` pointer). `CatalogRow.detailFallback` bridges a cloned row to an `AlbumSearchResult` for `AlbumDetailView`'s instant deep-link header (step 7). `AppDependencies` (step 5) opens the production store at `<Application Support>/Catalog/catalog.sqlite` (via the testable `defaultCatalogStoreURL()`), degrading to inert catalog features if it can't. **Issue #58 offline search:** `CatalogStore` also vends `search(query:limit:) -> [CatalogRow]` (artist/album/call-number full-text). `SQLiteCatalogStore` backs it with a **contentless** (`content=''`) FTS5 virtual table `catalog_fts(artist, album, call_number, tokenize='unicode61 remove_diacritics 2')` keyed by `rowid = catalog.id`, **rebuilt inside the same `BEGIN IMMEDIATE` transaction as the rows** (so the index can never drift) — a contentless table rejects `DELETE FROM`, so the rebuild clears it with the documented `INSERT INTO catalog_fts(catalog_fts) VALUES('delete-all')` command, then re-inserts. `remove_diacritics 2` makes "nilufer" match "Nilüfer Yanya". `search` runs `… WHERE catalog_fts MATCH ? ORDER BY rank LIMIT ?` then loads each match's BLOB by id (the contentless index stores no original text). FTS5 ships in Apple's system libsqlite3 on iOS/macOS, so the `CREATE VIRTUAL TABLE` always succeeds; a missing module would surface as a store-open error. **Migration self-heal (#58 review):** the index is created empty and only `replace()` (a `200`) fills it, so a clone written by a pre-#58 build (rows present, no `catalog_fts`) would `304` forever with an empty index; `search` therefore calls a one-time `ensureSearchIndex()` that backfills the index from the existing rows when a `COUNT(catalog) != COUNT(catalog_fts)` mismatch shows it's stale — **watermark untouched** (the conditional-GET path is undisturbed), run inside the actor (off-main) and only when offline search is exercised, latched per connection (`replace` keeps both in sync thereafter).
- `Catalog/FTSQuery.swift` + `Search/LibrarySearch.swift` → the issue-#58 offline search seam. `FTSQuery.match(for:)` is the pure, safe MATCH builder: empty/whitespace → `nil`; each whitespace token becomes a **quoted prefix** term (`juana` → `"juana"*`, `bar baz` → `"bar"* "baz"*`) with interior double quotes doubled, so user punctuation can never inject FTS5 operators. `LibrarySearch` (`@MainActor` struct over `APIClient` + `any CatalogStore?` + `ConnectivityMonitor`) is the online-first/offline-fallback router: **online** tries the server (byte-for-byte the old `searchLibrary(artist:title:)` call) and on *any* thrown error falls back to local; **offline** serves local — but no longer *only* local, which is what issue #81 changed: it first calls `connectivity.consumeProbe()`, and on a `true` (the cooldown has elapsed and this caller won the window's one allowance) fires a real `searchLibrary` as a **fire-and-forget probe** before returning the clone's results. Three things about that probe are deliberate. It is **never awaited**, so a probe against a dead backend can't add `configuration.timeout` to a keystroke — the local results the DJ sees are unaffected either way, which is what keeps #58's offline-first ergonomics intact without racing the probe or plumbing a second, shorter timeout. Its **result is discarded**; the probe exists to produce a *connectivity signal*, not to serve this query (the local arm already did), and that signal needs no new plumbing — it rides `APIClient.fire`'s existing `onOutcome` hook into `ConnectivityMonitor.ingest` exactly like any other request, so success un-latches and fires the reconnect edge for free while failure moves the cooldown anchor forward. And its `Task` is **unstructured on purpose**: `SearchViewModel`'s debounce cancels its in-flight search task on every keystroke, and a child task would be torn down with it — the probe would be cancelled before reaching the server, which (per the carve-out above) reports nothing, so a DJ could type past every cooldown without one real attempt ever completing. `Task.init` inherits actor isolation and priority but **not** cancellation, and nothing retains the handle, so the probe always runs to completion. **Offline with the allowance already spent** → straight to local, no round-trip, exactly as before. The local arm maps `store.search` rows through `CatalogRow.detailFallback`. It never throws — a failed/offline search degrades automatically (no manual retry) — and returns `LibrarySearchOutcome(results:source:)` with `.server`/`.local` so the UI can frame offline results. A `nil` store makes it server-only (offline → empty `.local`). Built once by `AppDependencies` and handed to each `SearchViewModel`; host-tested against `StubRequestSession` + `SpyCatalogStore` (whose `search` is a diacritic-folded substring filter).
- `Catalog/CatalogIndexing.swift` + `Catalog/SpotlightCatalogIndexer.swift` + `Catalog/SearchableIndexing.swift` + `Catalog/CatalogSpotlight.swift` + `Catalog/CatalogIndexState.swift` → the **Core Spotlight indexer** (issue #19 step 3; **delta-reindex reshape in issue #36**). `CatalogIndexing` is the `Sendable` seam step 4 drives — `reindex(snapshot:watermark:) -> ReindexSummary` mirrors the **in-memory `[CatalogRow]` export** into `CSSearchableIndex` and `indexedWatermark()` reads the committed watermark back (step 4 sources its poll watermark from *this*, not `store.lastModified()`, so a crash can't strand the store ahead of the index). The reshape: instead of paging the store and re-upserting every row, `SpotlightCatalogIndexer` diffs the snapshot against its **own persisted `id → content-fingerprint` map** (`CatalogIndexState`, committed as Core Spotlight **client state** alongside the watermark) and derives **add** (id absent from the map), **change** (id present, fingerprint differs), **remove** (in the map, absent from the export — so the removed set survives `store.replace` and is reproducible across a mid-reindex crash, fixing issue #36 limitation 1), and **unchanged** (equal fingerprint → skipped, so a typical `200` costs `O(delta)`, fixing limitation 2). The fingerprint (`CatalogSpotlight.fingerprint(for:)`) is a **stable** SHA-256-derived `UInt64` over exactly the fields feeding `searchableItem(for:)` (album/artist/label/call-number components + `artworkURL` for #44) — never `CatalogRow.hashValue`, which Swift salts per process. It upserts `add ∪ change` and deletes `remove`, packing **both** into bounded batches whose combined item count never exceeds 32 767 (`Int16.max`; Core Spotlight rejects a larger single `beginBatch()`/`endBatch(withClientState:)` cycle with `CSIndexErrorDomain -1001`). The watermark advances **only on the final batch**; each batch commits the fingerprint map of work applied **so far** (cumulative, since a batch's `endBatch` durably applies its upserts/deletes) and intermediate batches withhold the watermark (`nil`), so the persisted map stays consistent with the physical index between batches — a crash mid-run leaves the next run able to reconcile a *fresh* export against what the index actually holds (re-deleting a now-vanished id rather than stranding it), not just an unchanged one. `indexedWatermark()` reads only the watermark prefix (`CatalogIndexState.decodeWatermark`) so the cheap conditional-GET path never decodes the whole map. `CatalogIndexState` is a compact little-endian codec (version byte + watermark + sorted `id`/`fingerprint` entries) that decodes an empty/legacy-bare-watermark/truncated blob to `nil` → treated as empty, forcing a from-scratch reindex. The ~1 MB map written through client state is the accepted cost of keeping the watermark + map a single atomically-committed blob (option (a) in the issue); a typical change day is a single batch so the map is written once. It is **gap-free**: the `SearchableIndexing` seam exposes no delete-by-domain, so home-screen search is never emptied mid-reindex. `SearchableIndexing` wraps the four `CSSearchableIndex` batch calls (auto-bridged to `async throws` — no manual continuation needed); the real conformer `RealSearchableIndex` is `@unchecked Sendable` (`CSSearchableIndex` isn't `Sendable` and isn't thread-safe in batch mode, but step 4 drives exactly one sequential reindex). `CatalogSpotlight` owns the `"album.<id>"` ↔ `Int` round-trip (step 7's deep link reuses `albumID(from:)`), the pure `CatalogRow → CSSearchableItem` mapping (the `searchableItem(for:thumbnailData:)` overload embeds an issue-#44 cover; `searchableItem(for:)` delegates with `nil`), and the content fingerprint. `CatalogIndexing.upsert(row:thumbnailData:)` is the issue-#44 single-row **non-batch** write (no `beginBatch`/`endBatch`, so no client-state commit — a thumbnail attach never advances the watermark). CoreSpotlight + CryptoKit import on the package's macOS slice, so this is all host-testable under `swift test` against `FakeSearchableIndex` (a lock-guarded `Sendable` class, **not** an actor; its committed client state decodes back to `CatalogIndexState` for assertions). The live index is a **client-owned named index** (`CatalogSpotlight.indexName = "org.wxyc.dj.catalog"`) — batching and client-state are unsupported on the shared `.default()`; `SpotlightCatalogIndexer(indexName:)` is the convenience that builds `RealSearchableIndex(CSSearchableIndex(name:))`, wired by `AppDependencies` in step 5. **Simulator gotcha (cost us a debugging detour):** Core Spotlight *surfacing* is unreliable on the iOS Simulator — a clean `Catalog refresh: refreshed(rowCount: …)` log there does **not** mean items appear in home-screen search; they frequently never surface on the sim even when correctly indexed. Always confirm home-screen search on a **physical device**. A simulator no-show is not evidence of an indexing bug — check the refresh log for the real outcome (a `-1001` would be a genuine indexing failure; no error + no results = sim flakiness).
- `Catalog/ThumbnailDownscaling.swift` + `Catalog/ThumbnailProviding.swift` → the **Spotlight thumbnail cache** (issue #44). Spotlight does **not** fetch a remote `artwork_url` for app-indexed content, so a cover must be materialized on-device and embedded as `CSSearchableItem.thumbnailData` (embedded bytes, **not** `thumbnailURL` — the index owns its own copy, so eviction/container-path-rot can never dangle a live item's art, rdar://23592852). `ThumbnailDownscaler.downscaledJPEG(from:maxPixelDimension:compressionQuality:)` is the pure ImageIO transform (256 px, JPEG q0.8, never upscales; **no HEIC** — broken on the 17.5+ Simulator and undocumented for Spotlight). `ThumbnailProviding` is the `Sendable` seam (`localThumbnailURL(for:) async -> URL?`); the real `DiskThumbnailProvider` is an `actor` caching `<App Support>/Catalog/Thumbnails/<id>-<urlhash>.jpg` (the urlhash = first 16 hex of SHA-256 over the URL, so a changed cover invalidates), fetching via an injected `RequestSession` (production: `URLSession.shared`, reusing the `AsyncImage`/`URLCache` in-app cover loads populated — safe to share that process-wide session **because** the injected one is wrapped in `CookielessSession` at `init`, which strips cookie handling per request while leaving the `URLCache` reuse intact; a dedicated cookie-free `URLSessionConfiguration` was rejected for exactly that reason, issue #99), downscaling, and writing atomically (`.write(.atomic)`) with per-key single-flight. The cache is only the **fetch-dedup ledger** — never load-bearing for "does the index still have the art" (the index owns the bytes). No Discogs API key (stored URLs are pre-signed CDN URLs, plain `GET`); single lazy fetches only, never bulk. Populated by use (the Apple Music `AMPArtworkAgent` model), wired from `AlbumDetailView.task` + `SearchResultRow.onAppear` via `AppDependencies.cacheThumbnail(forAlbumID:)` (a thin pass-through; the dedup lives in `CatalogRefreshService`, keyed on the cover's cache-file so a *changed* cover re-attaches and cleared on every reindex so a stripped cover self-heals). **PR-2 deferrals (issue #44):** the cached-only `reindex` attach + global-sweep cache cap/prune; host-testable under `swift test` (ImageIO/CryptoKit on the macOS slice) against `StubRequestSession`/`BlockingRequestSession`. The home-screen "result shows the cover" half is a **device-only** check (Simulator surfacing is unreliable, per #19/#32).
- `Catalog/CatalogRefreshService.swift` → the **shared refresh service** (issue #19 step 4): the poll → `304`/`200` → store-replace → Spotlight-reindex flow the foreground path and both background tasks call, so the bulk runs off the main actor and the BGTask layer stays thin. It is an **`actor` that serializes *all* index touches** — every `refresh()` **and** every issue-#44 lazy `cacheThumbnail()` — through one serial chain (`runSerial`/`inFlight`): each op drains its predecessor before starting, in **both** directions, so no two Core Spotlight batches/writes ever overlap (the soundness condition for `RealSearchableIndex`'s `@unchecked Sendable`) and the indexer's fingerprint-map diff can't race a concurrent `replace`. The `Task { }` in `runSerial` inherits the actor's isolation, so cleanup (`endSerialOp`, which frees the tail and decrements the counters) runs in the *wrapper task's* frame when the work settles — a cancelled caller can't free the slot mid-batch, and the increment/decrement can't be skipped by a cancellation delivered while the op awaits its predecessor. **Issue #44 dropped issue-#19's refresh↔refresh coalescing** for this single mechanism: two overlapping refreshes now run sequentially (the second a cheap `304`) instead of collapsing onto one round-trip — the accepted trade for one serialization primitive. Two derived counters (not gates): `activeCount` frees the tail at idle; `refreshInFlight` is what `poll()` defers to (a thumbnail upsert must **not** suppress the poll — it doesn't reindex). `refresh()` sources the poll watermark from `indexer.indexedWatermark()` (the index's committed client state), **not** `store.lastModified()` — the load-bearing crash-safety invariant: the store is replaced *before* the index commits, so if a crash lands between them the next poll re-fetches and re-indexes instead of `304`-ing past a watermark the index never reached (equivalently, the watermark advances only when `endBatch` succeeds). On a `200` it replaces the store, then hands the **in-memory snapshot** to `indexer.reindex(snapshot:watermark:)` — the indexer derives the add/change/remove delta against its own persisted fingerprint map (issue #36), so the removed set survives the replace and unchanged rows are skipped — returning an `Outcome` (`.upToDate` / `.refreshed(rowCount:upserted:removed:)` / `.skippedEmptyExport`) for logging. An **empty `200` body is skipped** (`.skippedEmptyExport`, no replace, no watermark advance) — a defensive data-safety guard, since an empty export is far likelier a backend hiccup than a real empty catalog and replacing with it would wipe the last-good clone and then `304` forever. Host-tested under `swift test` against a `StubRequestSession` client + `SpyCatalogStore`/`SpyCatalogIndexer` (304 is a no-op; 200 replaces the store then hands the snapshot to the indexer, the spy modelling its own fingerprint map so the recorded delta is faithful; an empty 200 is skipped; a failed reindex leaves the watermark un-advanced and a fresh indexer retries) plus an end-to-end pass over the real `SQLiteCatalogStore` + `SpotlightCatalogIndexer`. `poll()` (step 5) is the cheap conditional probe the background app-refresh leg uses: it reports whether the catalog moved **without** replacing the store or reindexing (so the heavy work defers to a charging-gated processing task). It opens no batch and isn't serialized into the chain, but **short-circuits to "no change" when a refresh is in flight** (`refreshInFlight > 0`) — that refresh reindexes, so the reindex leg has nothing to add, and skipping avoids a second index handle reading client state during the refresh's open batch. It does **not** defer to a lazy thumbnail upsert: an upsert neither reindexes (deferring would skip a real catalog change) nor opens a batch (so the client-state read is safe). Still pays the body download + decode on a `200` — a body-less probe is a Backend-Service follow-up. It returns a **`PollOutcome`** (`.changed` / `.unchanged` / `.skippedRefreshInFlight`), not a `Bool` (issue #118 review): the short-circuit and a genuine `304` both used to collapse to `false`, which was harmless while the only consumer asked "should I schedule a reindex?" — but the caller now *records* the answer, and reporting a skipped poll as "the catalog didn't move" asserts something the app never learned. The service takes a **`makeIndexer` factory and builds a fresh indexer per `refresh()`/`poll()`/`cacheThumbnail()`** (step 5): `CatalogIndexing`'s contract is that a reindex throwing mid-batch can only be recovered on a freshly-constructed `CSSearchableIndex`, so reusing one for the process would let a single mid-batch failure poison every in-process retry (scene-activation refresh, the background reindex leg) until relaunch — a fresh indexer reads the same persisted client-state watermark and recovers on the next run, and keeps `poll()`'s watermark read off any in-flight reindex's open batch. **`cacheThumbnail(forAlbumID:)`** (issue #44) is the lazy thumbnail attach: best-effort, non-throwing, serialized through the chain; it resolves the cloned row + its cover off the actor via the injected `thumbnailProvider`, then a **plain non-batch** `indexer.upsert(row:thumbnailData:)` that touches no client state (the watermark never advances on a thumbnail attach).

When adding a new endpoint, prefer to:
1. Add a typed method on `APIClient` (don't expose raw `sendRaw`).
2. Check whether the response/request has an api.yaml schema first (see "Code Generation" below) — if it's generation-safe, reference the generated `WXYCAPIModels` type (directly, or via a `public typealias` in `Sources/WXYCAPI/DTOs/` if the app wants its own name for it) instead of hand-rolling a new struct. Only hand-roll a DTO in `Sources/WXYCAPI/DTOs/` when the schema doesn't exist, or is unsafe to generate (same section). Keep `snake_case` mapping in an explicit `CodingKeys` enum for anything hand-rolled — `convertFromSnakeCase` is intentionally not used because the wire format mixes camelCase paths (e.g. `albumId` in nested types coming from Drizzle) with snake_case top-level.
3. Write tests against `StubRequestSession`. See `APIClientTests.swift` for the pattern.

## Code Generation (`WXYCAPIModels`)

`Packages/WXYCAPIModels` is a vendored SwiftPM package of Swift types generated from `wxyc-shared`'s `api.yaml` (issue #75; the org's OpenAPI 3.0 contract — see the org-level `CLAUDE.md`'s "API Contract" section). It is a **separate package from `WXYCAPI`**, not a replacement for it: the generator's `swift6.yaml` config emits `projectName: WXYCAPI`, which would collide with (and, with `useSPMFileStructure: true`, overwrite) this repo's hand-curated package if vendored in place. `WXYCAPI`'s `Package.swift` depends on `WXYCAPIModels` as a local sibling package; the hand-written `APIClient` / `AuthService` / `Bin/` / `Catalog/` / `Connectivity/` code is untouched by this — it still calls the same DTO names it always has, most of which now resolve to a `public typealias` pointing at a generated type.

This mirrors `wxyc-ios-64`'s `Shared/WXYCAPIModels` (see its `docs/code-generation.md`) — same pattern, ported here rather than reinvented.

**What's vendored.** `Models/` (every api.yaml schema, minus one narrow exception below) plus a curated subset of `Infrastructure/` — not the whole output tree. `APIs/` — the generated endpoint clients — is intentionally dropped on every regen; this package is models-only (`generateApis: false` in `swift6.yaml` does **not** actually suppress `APIs/` under the swift6 generator, so the scripts below drop it by only rsyncing `Models/`+`Infrastructure/`).

`Infrastructure/` is curated to seven files — `Models.swift`, `Validation.swift`, `JSONValue.swift`, `CodableHelper.swift`, `OpenAPIMutex.swift`, `OpenISO8601DateFormatter.swift`, `CalendarDate.swift` — the support types `Models/` actually needs (`JSONValue`, `NumericRule`, `CaseIterableDefaultsLast`, `UnknownCaseCheckable`, ISO-8601 date formatting, and the calendar-date type below), determined empirically by compiling (issue #75 review finding F3), not the generator's full ~2,171-line output.

**`CalendarDate.swift` is the one entry that is not openapi-generator output**, and knowing that matters when the list next changes. It is hand-authored upstream at `wxyc-shared`'s `openapi-config/swift-support/CalendarDate.swift` and copied into the generator's `Infrastructure/` by that repo's `postgenerate:swift` hook ([wxyc-shared#358](https://github.com/WXYC/wxyc-shared/pull/358)), so by the time `regenerate-api-types.sh` reads the output tree it is indistinguishable from the rest — which is exactly why it belongs on the keep-list rather than in a second mechanism. It is load-bearing: `swift6.yaml` maps `format: date` to it (`typeMappings: date=CalendarDate` — note the generator keys on its own internal type names, so the sibling mapping is spelled `DateTime`, never the OpenAPI `date-time`), so the six models carrying such a property — `CatalogExportRow`, `Concert`, `KillRotationRequest`, `Rotation`, `RotationEntry`, `RotationWithAlbum`, nine declarations once the generator flattens `RotationWithAlbum`'s `allOf` over `RotationEntry` — reference a type that is only in scope if this file is staged. `CalendarDate` stores `(year, month, day)` and nothing else: a `Foundation.Date` is a point on the UTC timeline, so decoding a bare `YYYY-MM-DD` into one fabricates a time-of-day and a UTC anchor the value never had, shifting the rendered day back by one on every host west of UTC. Comparison is a total order over the three components and never consults `Calendar`/`TimeZone`.

**The keep-list is an allow-list, so an unclassified generator file is silently DROPPED, not vendored.** That is a real failure mode, not a hypothetical: `CalendarDate.swift` arrived exactly this way, and the symptom of missing it would have been `cannot find type 'CalendarDate' in scope` in whatever target links the package — far from the script that caused it. Two things conspire to hide it. The count guard at the bottom of `regenerate-api-types.sh` (`STAGED_INFRA == ${#INFRA_KEEP[@]}`) counts a staging directory built by looping over `INFRA_KEEP` itself, so it is equal by construction — a consistency check that catches a `cp` writing nothing, never a tripwire that can notice a new file. And nothing upstream reports it either, because `verify-api-types.sh` regenerates from the **pinned** sha in `contract-version.json`: CI here stays green against a `wxyc-shared` that has already moved, right up until a PR bumps the pin. The script therefore also classifies every emitted file against `INFRA_KEEP` ∪ `INFRA_DROP` and **fails on anything in neither**, so a new support file is a decision someone makes rather than one the allow-list makes silently. `INFRA_DROP` is the deliberate-exclusion half: an unused HTTP client this models-only package never calls (`URLSessionImplementations.swift` + its `APIs.swift`/`APIHelper.swift`/`JSONDataEncoding.swift`/`JSONEncodingHelper.swift`/`SynchronizedDictionary.swift` support cast — a URLSession request builder, an auth-challenge delegate, and a process-global mutable credential store). `Extensions.swift` is worse than merely unused: it declares `extension String: @retroactive CodingKey`, whose `String.init?(intValue:)` silently wins Swift's overload resolution over `String.init(_:)` wherever `String.init` is passed as a bare function value over an `Int` — `[1, 2, 3].map(String.init)` becomes `[nil, nil, nil]`, verified empirically, not a hypothetical — and the conformance leaks to every file in the app the instant `WXYCAPIModels` is linked in, no import required at the use site. `Infrastructure/Models.swift` (confusingly the same name as the `Models/` directory — this is the generator's static support-type file, emitted unconditionally regardless of api.yaml content) is otherwise self-contained but declares a trailing `RequestTask` class that exists only to support the excluded `APIs/` output; `scripts/regenerate-api-types.sh` strips it (a scripted, reproducible transform, never a hand-edit of the committed tree) rather than pulling `URLSessionImplementations.swift` back in to satisfy one dead class.

**Two exclusions carve into the otherwise-unconditional "vendor everything" rule.** The first is one file; the second is eighteen.

`Models/HealthCheckResponse.swift` is the first: it's the only schema in the spec whose `additionalProperties: true` support needs a String-keyed container (`container(keyedBy: String.self)`), which only compiles with `String: CodingKey` — the exact unsafe conformance above. wxyc-dj-ios never calls a `/health`-shaped endpoint, so `scripts/regenerate-api-types.sh` drops this one file rather than reintroducing the unsafe conformance to satisfy it. Re-evaluate if this app ever needs it.

**The auth schemas belong to `WXYCAuth`, not to this package.** [`WXYC/wxyc-swift-auth`](https://github.com/WXYC/wxyc-swift-auth) vendors its own generated copy of the non-device `/auth/*` schema closure and declares every one of those types `public`; this package declares its models `public` too, so vendoring the same schemas in both would put a **second public declaration of each name into any build graph holding both packages** — ambiguity at every use site, with no import-level workaround, since both are libraries the app depends on directly. `scripts/regenerate-api-types.sh` therefore drops **eighteen** models: the sixteen component schemas in that closure (`AuthErrorResponse`, `AuthPlainErrorResponse`, `AuthRateLimitedResponse`, `AuthSendCodeResult`, `AuthSignInResult`, `AuthSignOutResult`, `AuthTokenAndUserResult`, `AuthTokenResponse`, `AuthUser`, `EmailSignInRequest`, `LookupEmailRequest`, `LookupEmailResponse`, `OTPSignInRequest`, `OTPType`, `SendLoginCodeRequest`, `UsernameSignInRequest`) plus two the closure structurally **cannot** name (see below).

**The device-authorization surface stays here.** `WXYCAuth` does not vend the `DeviceAuth*` types — issue #64's approve/deny/verify surface is this app's own — so `/auth/device/*` is excluded from the closure and all seventeen `DeviceAuth*` models remain vendored, unaffected. That carve-out is **segment-matched, not a string prefix**: `startsWith('/auth/device')` would also swallow a future `/auth/devices` or `/auth/device-code`, and a schema reachable only from such a path would then be kept by *both* packages with every guard still passing — the collision, undetected.

**Dropping these is behaviourally inert today, which is exactly why it needed doing now.** `WXYCAPI` hand-rolls `EmailSignInRequest`, `LookupEmailRequest`/`LookupEmailResponse`, `SendLoginCodeRequest` and `OTPSignInRequest` itself, and a same-module declaration already silently shadowed the generated one — the quiet failure mode this section's "Never import `WXYCAPIModels` directly" rule warns about, and the reason nothing broke while both copies existed. The other eleven were vendored and unreferenced. The collision only becomes *loud* at the moment the app adds the `WXYCAuth` dependency, so the exclusion has to land before or with that PR, not after it.

**The list is checked in both directions against an independent input, because an exclusion list cannot be its own guard.** `scripts/auth-schema-closure.mjs` computes the transitive `$ref` closure of every non-device `/auth/*` operation **from `api.yaml`** and the script compares it against `AUTH_MODELS_DROP` **both ways**: a schema newly reachable from an auth operation fails the run (it would otherwise keep being vendored, and the collision would surface as a redeclaration error in whatever target links both packages, far from the list that caused it), and a list entry that stops being reachable fails it too (it would otherwise keep deleting a type this app may need). This is the same tripwire `INFRA_KEEP`'s classification check provides, for the same stated reason: a count or a self-referential check is a consistency check, never a tripwire.

That script is a deliberate near-duplicate of `wxyc-swift-auth`'s file of the same name, and the duplication is load-bearing rather than a wart: **both repos derive the partition from the same `api.yaml`**, so while the two pins name the same commit the two sets are equal by construction and cannot drift into either a collision (a schema kept by both) or a gap (one dropped here and never vended there). Bumping either repo's pin without the other is what re-opens that.

**Two of the eighteen are invisible to the closure, and that gap has its own guard.** The closure follows `$ref`s, so it names only schemas declared under `components/schemas`. The generator *also* synthesizes a model per **inline** schema on a path — here the `oneOf` bodies on the two password routes' 429 responses, emitted as `AuthSignInEmailPost429Response` / `AuthSignInUsernamePost429Response`, each `case`ing over two closure members. Keeping them would leave the tree referencing types the script had just deleted. They are listed separately in `AUTH_INLINE_MODELS_DROP` and covered by two guards the closure comparison cannot provide: every staged `Auth`-prefixed model must be accounted for by one of the two lists (the generator names an inline path model after its path, so the prefix is derived from the generator's own convention rather than from the list it checks — and it deliberately also covers a future `/auth/device/*` inline model, which would fire and force a decision rather than being dropped silently), and **no surviving staged file may reference a dropped name** (comment-stripped first, into a directory outside the staging dir, since the generator's `/** … */` schema descriptions quote these type names in English). That second guard is not a formality — it is what caught these two wrappers in the first place.

**Never import `WXYCAPIModels` directly from app-layer code (`WXYCDJ/`).** Five type names now exist in both modules — `AlbumSearchResult`, `BinEntry`, `RotationBin`, `AddToBinRequest`, `AlbumMetadata` (`TrackMatchHint` / `TrackMatchSource` / `CalendarDate` also appear in both, but as `public typealias`es onto the generated types, so they're the same type and carry no shadowing risk). The symptom differs by name, and only one of the three is loud: **decode-throw** for `AlbumSearchResult` / `BinEntry` / `AlbumMetadata` (the generated variant is the strict one this table documents as unsafe against real Backend-Service responses); **silent field loss on encode** for `AddToBinRequest`, which is a request body and never decoded — binding to `WXYCAPIModels.AddToBinRequest` (the dead `{album_id}`-only schema) compiles fine and just drops `track_title` on the wire; and a **compile error** for `RotationBin`, where the generated enum is actually *more* tolerant but its `.h`/`.m`/`.l`/`.s` cases fail `SearchResultRow.color`'s exhaustive switch. `project.yml` links `WXYCAPIModels` into the app and test targets directly (see below), so a stray `import WXYCAPIModels` in a view model resolves. The failure mode depends on what else that file imports, and only one of the two is loud: alongside an `import WXYCAPI` the duplicated names become ambiguous and the file won't compile, which is the good case; in a file importing `WXYCAPIModels` *alone*, the names bind to the throwing generated types with nothing to flag it, and the first symptom is a decode failure at runtime against a real Backend-Service response. Always `import WXYCAPI` and use the DTO names it exports (most of which are typealiases onto generated types where that's safe — see the tables below) — never reach past it into `WXYCAPIModels` from `WXYCDJ/`. **The rule binds `WXYCDJTests/` too**, and that is where it first broke: issue #79 typed `CatalogRow`'s public initializer on `CalendarDate`, a name `WXYCAPI` depended on but did not re-export, so every out-of-package caller constructing a row had to import `WXYCAPIModels` to name the parameter — `AlbumDetailFallbackTests` duly did. A public API that *forces* the forbidden import is the bug, not the caller: `DTOs/CalendarDate.swift` now re-exports it (the `TrackMatchHint` treatment), which also collapsed the targeted `import struct WXYCAPIModels.CalendarDate` from eleven files to one. Prefer that fix whenever a generated type reaches a public signature.

**The pin.** `Packages/WXYCAPIModels/contract-version.json` pins the vendored tree to an exact `wxyc-shared` commit (`wxycSharedSha`, the field the scripts actually read) and the `api.yaml` version it shipped (`apiYamlVersion`, for humans). Never hand-edit a file under `Packages/WXYCAPIModels/Sources/WXYCAPIModels` — the next regen silently discards it, and `verify-api-types.sh` exists to catch anyone who tries.

**Regenerating and verifying.**

```bash
# Update the contract: bump contract-version.json's wxycSharedSha (and, for
# legibility, wxycSharedTag / apiYamlVersion) to the new wxyc-shared commit first, then:
scripts/regenerate-api-types.sh

# Drift check -- regenerates into a scratch dir (never touches the committed
# tree) and diffs it against Packages/WXYCAPIModels/Sources/WXYCAPIModels:
scripts/verify-api-types.sh
```

Requires `git`, `npm`/`node`, `java` (the OpenAPI generator runs on the JVM via `openapi-generator-cli`), and `rsync` on `PATH`. After regenerating, review the diff, then run `swift test --package-path Packages/WXYCAPI` and the affected app tests before committing. `.github/workflows/verify-api-types.yml` runs `verify-api-types.sh` on every PR touching `Packages/WXYCAPIModels/**` or either script, plus on every push to `main` (a `pull_request` run doesn't re-fire on a base-branch advance, so the `push` trigger catches two individually-green PRs merging into a drifted tree).

**Know what this guard does and does not prove.** `verify-api-types.sh` proves the vendored tree matches `api.yaml`. It proves **nothing** about whether `api.yaml` matches the handler that actually serves the endpoint — it is a mirror-drift check, and the `/djs/bin` failure ([#77](https://github.com/WXYC/wxyc-dj-ios/issues/77)) is the case where the mirror and the spec agreed and were *both* wrong (`docs/library-row-type-contract.md` records the post-mortem; the missing guard is [wxyc-shared#328](https://github.com/WXYC/wxyc-shared/issues/328)'s declared-response-vs-handler check, which lives upstream). That boundary is why `BinEntry`, `AlbumInfo`, `AddToBinRequest`, and `AlbumMetadata` stay hand-authored below: in each case the schema is a faithful mirror of something the server doesn't send. **Generating a DTO is safe only once you've read the handler, not just the schema.**

**Which DTOs are generated, and which stay hand-authored.** Of the DTOs in `Sources/WXYCAPI/DTOs/` with an api.yaml counterpart, only three were safe to convert to a `public typealias` onto the generated type:

Required-vs-nullable is one possible gap, not the only one — the table above's history is a caution against assuming it's the default explanation without checking the actual server code and DB schema, the way every row in it was re-verified for issue #75's review.

## UI layer (`WXYCDJ`)

- `AppDependencies` is the composition root. One instance, owned by `AppDelegate` (so the SwiftUI scene and the reindex BGTask handler share the same `CatalogRefreshService` — required for its serial-chain no-overlapping-batch guarantee across all index touches), read via `appDelegate.dependencies` and environment-injected.
- **Catalog refresh wiring (issue #19 step 5).** Foreground-primary, background-best-effort. `WXYCDJApp`'s launch `.task` runs `restoreSession()` then `refreshCatalog()`, and re-runs `refreshCatalog()` on a *genuine* scene `.active` re-entry; on scene `.background` it arms the poll. A *genuine* re-entry is one that follows a real `.background`, which is what `ForegroundReentryTracker` tracks (issue #118 item 4). Without it a cold launch double-fired `catalog_refresh_completed` (once `.launch`, once `.foreground`, the latter racily dependent on whether `restoreSession()` had finished). **The rule is "an `.active` counts only after a `.background`", not "ignore the first `.active`"**, and the difference is load-bearing twice: it doesn't assume SwiftUI delivers an `onChange(of: scenePhase)` for the cold-launch activation (not contractually guaranteed — and if it ever doesn't fire, consuming the first `.active` eats the first *genuine* re-entry instead, so `refreshCatalog(trigger: .foreground)` silently never runs after a background cycle, a functional regression rather than a miscount), and it ignores an `inactive → active` blip from Control Centre or the app switcher, which never reaches `.background` and is not a return from anywhere. The background split lives in `Catalog/CatalogBackgroundTasks.swift`: `org.wxyc.dj.catalog.refresh` is a `BGAppRefreshTask` registered by SwiftUI's `.backgroundTask(.appRefresh:)` (re-arms, polls, submits the reindex on a `200`); `org.wxyc.dj.catalog.reindex` is a `requiresExternalPower` `BGProcessingTask` registered in `AppDelegate` (SwiftUI has no `.processing` matcher) — the launch handler is non-`Sendable`, so the `task` is bridged into structured concurrency with `nonisolated(unsafe)` (sound because only the work task touches `task`; the expiration block captures only the `Sendable` work task). `setTaskCompleted(success:)` reports `refreshCatalog()`'s **real** outcome (`refreshCatalog()` returns a `Bool`), not whether the work was cancelled. Expiration cancellation is a cooperative signal, not true preemption — the watermark invariant makes an interrupted reindex safe to retry. A missing/expired session is a silent skip + reschedule (pinned by a no-session `CatalogRefreshService` test); the background poll re-arms only when a catalog store exists. Both ids + `UIBackgroundModes` (`fetch`, `processing`) live in `project.yml`'s `info:` block (this target uses a **generated `Info.plist`**, not `GENERATE_INFOPLIST_FILE`, since those keys aren't `INFOPLIST_KEY_*`-expressible); the entitlements file is unchanged (Core Spotlight + BackgroundTasks need none). **Debug a BGTask leg** from a paused debugger with the LLDB SPI `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"org.wxyc.dj.catalog.refresh"]` (or `_simulateExpirationForTaskWithIdentifier:`); the task must already be submitted, and `_simulateLaunch` bypasses the external-power/network gates. See README for the full recipe.
- **Routable navigation (issue #19 step 6).** `AlbumRoute.swift` is the single value pushed onto every album `NavigationStack` path — `struct AlbumRoute: Hashable, Identifiable { let id: Int; var fallback: AlbumSearchResult? }` with `==`/`hash` over **`id` only**. Both `SearchView` and `BinView` carry **one** `.navigationDestination(for: AlbumRoute.self)` hoisted onto their always-mounted `Group` (was nested inside `SearchView`'s `.results` case / `BinView`'s non-empty `default` case — unregistered in idle/empty states, fatal for a programmatic push and a latent lazy-container warning even for the tap). Search rows route `AlbumRoute(id: row.id, fallback: row)` (the live row renders the detail header instantly); Bin rows route `AlbumRoute(id: entry.albumId, fallback: entry.detailFallback)` (issue #87 — `BinEntry` decodes the full `/djs/bin` projection since issue #80, so `BinEntry.detailFallback` bridges it to an `AlbumSearchResult` that renders title/artist/label/call number instantly too, with artwork/plays/rotation left `nil`; `AlbumDetailView` still fetches `/library/info` to replace it with the authoritative row). **Both bridges go through one factory:** `CatalogRow.detailFallback` and `BinEntry.detailFallback` were the same 18-argument `AlbumSearchResult` construction differing in four positions (`id` source, plus `plays`/`onStreaming`/`artworkURL`, which the export projection carries and the bin projection doesn't), with the *rationale* for the six dropped fields duplicated across two doc comments. They now both call `AlbumSearchResult.headerStandIn(…)`, which takes only the twelve fields a stand-in can carry and fixes the six drops in one place — `rotationBin`/`rotationId` (the closed `H`/`M`/`L`/`S` cohort enum can't represent `CatalogRow`'s raw `String?` bin, which is typed that way so a bin added server-side ahead of the app survives; bridging through the enum would collapse such a value to `nil` and read as *out* of rotation) and `addDate`/`labelId`/`albumArtist`/`matchedVia` (search-response decoration with no meaning on a stand-in). Value semantics pinned in `WXYCDJTests/AlbumRouteTests.swift`.
- **Spotlight deep link + auth replay (issue #19 step 7).** A home-screen Spotlight tap opens the release detail in **its own `fullScreenCover` + `NavigationStack`** over `RootView` (`Detail/DeepLinkAlbumCover.swift`) — never pushed onto the Search/Bin tab stacks, so it can't pollute their nav/scroll state or fabricate a Back target; the cover's "Close" returns the DJ to the exact tab + scroll position. `Router.swift` is a `@MainActor @Observable` two-slot holder (`deepLink: AlbumRoute?` bound to the cover, `pending: Int?` the cold-launch stash) owned by `AppDependencies` and injected via `.environment`. The resolution logic lives on `AppDependencies` (it owns `catalogStore`): `handleSpotlightTap(albumID:isSignedIn:)` presents immediately when signed in (O(1) `catalogStore.row(id:)` lookup → `CatalogRow.detailFallback` for the instant header; a clone miss routes `fallback: nil` and the detail view awaits `/library/info`) or parks the id in `Router.pending` otherwise; `handleAuthChange(wasSignedIn:isSignedIn:)` reconciles the surface on every auth transition — **flip to signed-in** replays a parked id, **genuine sign-out** (`wasSignedIn && !isSignedIn`) tears down via `invalidateDeepLink()` (dismiss the cover + drop the park) so a detail can't strand over `LoginView` issuing 401s, while a **cold-launch `.unknown` → `.signedOut`** keeps the park for a later manual sign-in (which is why it needs the old *and* new flags, via `AuthService.State.isSignedIn`). Presentation funnels through a private `present(albumID:)`: it early-outs when the same album is already shown (skipping a redundant clone read), clears `pending` synchronously (so a fresh tap supersedes a park), and gates the post-`await` `deepLink` write behind a monotonic `presentationToken` — so when a parked replay, a fresh tap, **or a sign-out** race across the clone-lookup suspension, the **most-recently-requested** outcome wins deterministically rather than whichever store read resumes last (a sign-out bumps the token via `invalidateDeepLink`, so an in-flight `present` resuming post-sign-out bows out). **Activity delivery is via a `UIWindowSceneDelegate`, not the view-level `onContinueUserActivity`** — the latter was silently dropping the `CSSearchableItemActionType` activity in **both** cold- and warm-launch states (the original step-7 bug). `SceneDelegate.swift` is attached to SwiftUI's window scene through `AppDelegate.application(_:configurationForConnecting:)` (only `delegateClass` is set — no `sceneClass`/storyboard — so SwiftUI keeps owning the window and hosting `RootView`; verified no black-screen). It catches the tap in the two states the system actually routes through the scene: cold launch via `scene(_:willConnectTo:)`'s `connectionOptions.userActivities` (the launch activity is **not** delivered to `UIApplication`'s `continue` method in a scene-based app), and warm via `scene(_:continue:)`. Both forward to `AppDependencies.handleSpotlightContinuation(_:)`, which parses the activity via `CatalogSpotlight.albumID(fromActivity:)` (the testable seam wrapping the `userInfo[CSSearchableItemActivityIdentifier]` → `"album.<id>"` extraction, pinned in `CatalogSpotlightTests`) and calls `handleSpotlightTap(albumID:isSignedIn:)` with the live auth state. `RootView` still carries `.onContinueUserActivity(CSSearchableItemActionType)` as a **fallback** routed through the same `handleSpotlightContinuation` (a double-delivery is a harmless no-op — `present()` early-outs on the already-shown album, and the `presentationToken` latch collapses a concurrent double-present), kept until the scene-delegate path is confirmed on device. `RootView` wires its remaining two modifiers onto its always-mounted `Group` (so they're live in **every** auth state, incl. the cold-launch spinner): `.onChange(of: auth.state) { old, new in … }` → `handleAuthChange`, and `.fullScreenCover(item: $router.deepLink)`. Both the scene root and the cover inject the app-wide observable trio (`deps` + its `authService` + its `router`) through one `View.wxycAppEnvironment(_:)` helper (`View+AppEnvironment.swift`) — cover content doesn't inherit the presenter's `.environment(_:)` objects, and the single helper keeps the two injection sites from drifting, so the shared `AlbumDetailView` runs under an identical environment on the deep-link and tab-push paths. The signed-in gate is **passed in** to `handleSpotlightTap` (not read off `authService`) so the replay is unit-testable without a real sign-in — `WXYCDJTests/RouterDeepLinkTests.swift` drives an `AppDependencies` over a temp `SQLiteCatalogStore`. The deep link is an in-app `NSUserActivity` continuation, **not** a Universal Link, so it needs no Associated Domains / AASA entitlement.
- **Sign-in screen (issue #100).** `LoginView` leads with the mailed one-time code and keeps the password form behind "Sign in with password instead" (ADR 0006). `LoginViewModel` drives an explicit `Stage` — `.identifier` / `.awaitingCode(email:displayTarget:)` / `.password` — rather than booleans, because two of the states carry data and the stage is what keeps the screen's **two** error surfaces from ever appearing together: **One error surface, not one per credential:** `sendLoginCode`/`resendLoginCode` record into `lastError` before rethrowing, exactly as `signIn` mutates it, so `displayedError` reads a single field. An earlier design had the code request report *only* by throwing, which forced a second store in the VM and a coalesce between the two — and produced a real defect: a failed resend went unrendered *and* wiped the message already on screen, since `sendLoginCode` clears `lastError` on entry. One convention is also what the next credential route copies. Every stage change calls `auth.clearLastError()` — without it a failed code verify would still be set when the DJ taps through to the password form, rendering "That code isn't right" under a form that never produced a code. `isSendingCode` exists for the same reason `sendError` does: that leg never enters `.signingIn`, so `auth.state` can't drive its spinner. `LoginCodeDestination` carries `email` (keys the verify call) beside `typedEmail` (`nil` when the address was resolved rather than typed, so the UI has nothing to leak); its init is **internal**, which makes the leak unrepresentable rather than resting on `sendLoginCode` being the only constructor. The `nil` case's wording lives in `OTPCodeView`, not the package — carrying the fact rather than the copy keeps user-facing English out of `WXYCAPI`. The code field normalizes to digits and caps at 6 on input (matching dj-site's `OTPCodeForm`), `.textContentType(.oneTimeCode)` lets iOS offer it straight from the mail notification, and resend is gated by a 30 s cooldown held as **observable state flipped by a task** (`isResendOnCooldown`), with the sleeper injected so tests drive it. `resendCode()` goes through `AuthService.resendLoginCode(to:)` rather than re-running `requestCode()`, so a username resend does **not** re-POST the lookup for an answer that cannot have changed — that would spend two slots of the per-IP budget where one does. Deliberately *not* a clock read: SwiftUI re-renders on mutation and time passing is not one, so a computed `now() - sentAt >= cooldown` latched the button disabled until some unrelated edit invalidated the view — worst right after `TOO_MANY_ATTEMPTS`, whose copy says "Request a new code" while the only button that can looks dead. The cooldown starts on **failure too** (a 429 is the case most worth throttling) and **survives a stage change**, because `canRequestCode` gates on it as well — otherwise "Send login code → Use a different account → Send login code" loops unlimited sends past a budget that is per-IP and therefore not refilled by switching accounts. `canSubmitCode` gates on `isSendingCode` for a subtler reason: Backend-Service sets no `resendStrategy`, so a resend **replaces** the stored OTP, and verifying the first mail's code mid-resend fails `INVALID_OTP` on a correctly-read code while spending one of 5 attempts. `canResendCode` carries the mirror-image gate, `auth.state != .signingIn` (issue #118 item 5): without it, Resend stayed live while `submitCode()`'s verify was in flight, so a resend that failed while the verify succeeded could land its error in `auth.lastError` right as `settle(.otp)` read it, misattributing a resend failure as a sign-in failure to both `sign_in_failed` (issue #108) and Sentry (issue #106, which this predates). `canRequestCode` carries the same guard for the same reason (issue #118 review). Both close one writer each to the single mutable `auth.lastError` slot that `settle(_:)` reads as the finishing leg's own outcome; a **third** writer is still open — `enter(_:)` calls `auth.clearLastError()`, and the "Use a different account" / "Email me a code instead" buttons are not themselves disabled while `.signingIn`, so a stage change mid-verify erases the outcome instead of overwriting it, costing the Sentry event as well as the analytics one ([#127](https://github.com/WXYC/wxyc-dj-ios/issues/127)).
- View models are `@MainActor @Observable` classes; each view either constructs its VM via `onAppear` (e.g. `SearchView`) or takes one from a parent.
- Views read `AuthService` directly from `@Environment(AuthService.self)` when they need state, e.g. the toolbar sign-out menu.
- Debounce pattern (in `SearchViewModel`): cancel `searchTask` on every query change, then start a new `Task` that `Task.sleep(for: .milliseconds(300))`s and checks `Task.isCancelled` before issuing the request. Don't reach for Combine. The debounced task delegates to `LibrarySearch` (issue #58) rather than calling `api.searchLibrary` directly, so the VM has no `.error` state — a failed/offline request falls back to the on-device clone automatically. The VM exposes `source` (`.server`/`.local`); `SearchView` shows a quiet "Showing saved library" note in the `.results` state when `source == .local`, and in the `.empty` state a `source == .local` miss renders a distinct "No saved matches" placeholder (so a local-clone miss doesn't read as a confirmed "not in the WXYC library" — the live catalog wasn't consulted) instead of the generic "No Results".

## Telemetry (`WXYCDJ/Telemetry/`)

Crash/error reporting via `sentry-cocoa` (issue #106) and anonymous product analytics via `posthog-ios` (issue #108, extending the same contract rather than negotiating a new one). **Read [`docs/adr/0007-ios-anonymous-error-reporting.md`](docs/adr/0007-ios-anonymous-error-reporting.md) before touching any of this** — it records the privacy contract and, more usefully, the three non-obvious leak channels the design exists to close. The one-line version: DJ-app users are signed in with real identities (usernames, emails, DJ ids, JWTs) where `wxyc-ios-64`'s listeners are anonymous, so this app's posture is strictly tighter than the reference implementation it otherwise borrows from, and every item of the contract is held by a mechanism that makes the violating code **fail to compile** or strips the value before it leaves the device — never by a comment asking the next contributor to be careful.

- `Telemetry/ErrorReporting.swift` → the seam, and the two type-level guards. `ErrorReporter` is a **`Sendable` protocol** — `report(_ error: any Error, context: StaticString, extra: [String: TelemetryValue])` — so a capture site on any isolation (`@MainActor` view models, `AppDependencies`, a `nonisolated` helper) calls it with no actor hop; conformers hold no mutable state, the SDK singleton doing its own synchronization. **`context` is a `StaticString`, not a `String`, and that is the whole point:** a `StaticString` can only be spelled as a source literal, so `context: "signIn for \(username)"` is a *compile* error rather than a *review* obligation. `TelemetryValue` closes the other door a call site would reach for — `.int`, `.bool`, `.string(StaticString)`, `.errorIdentity(domain:code:)`, and deliberately **no free-text case**, so `extra: ["query": typedText]` doesn't type-check either. (`TelemetryValue`'s hand-written `==` compares `.string` by rendered text because `StaticString` has no built-in `Equatable`, and switches on `lhs` alone — never a `(lhs, rhs)` tuple with a `default:` — so a fifth case is a compile error here until this function grows an arm for it, not two equal values silently comparing unequal.) `.errorIdentity` exists because `AppDependencies.catalogErrorDetail` already assembles an `NSError`'s domain+code for its `os_log` line; reach for it only to tag a fact *beside* a different primary error, never as a substitute for passing the real error — Sentry captures an `NSError`'s domain/code/underlying chain natively. `NoOpErrorReporter` lives here too. The file imports **Foundation only**: everything except `SentryErrorReporter` stays SDK-free, which is what lets `WXYCDJTests` exercise it through `@testable import WXYCDJ` without linking sentry-cocoa into the test bundle.
- `TelemetryErrorClassification` (same file) → **the raw enum must never reach `SentrySDK.capture(error:)`.** sentry-cocoa builds `exception.value` *and* `mechanism.desc` from `String(describing: error)` on a bridged Swift error, so `AuthError.rejected(message: "<server copy>")` would ship that copy verbatim into the field a human reads first — regardless of any `caseName` mapping applied elsewhere. `curated(_:)` replaces an `AuthError`/`APIError` with a **curated `NSError`**: a controlled domain (`org.wxyc.dj.AuthError` / `.APIError`), a code from `stableCode(for:)`, and a `userInfo` allowlisted to `caseName` + `statusCode` — plus, for `APIError` only, `.decoding(detail:)`'s narrowed `detail` string (read off `APIError.CaseName.detail`, the one deliberate exception the package-level doc comment argues for). It reads those off the package's own `caseName` mapping rather than switching on the raw case, deliberately: `caseName` is the one place permitted to see the message-bearing payloads, and a second switch here would be a second place a future edit could read `message` back into scope. `stableCode` is **FNV-1a, never `String.hashValue`** — Swift salts `hashValue` per process (the same gotcha `CatalogSpotlight.fingerprint` documents), which would give one `AuthError` case a different code every launch and shred Sentry's issue grouping; a collision is immaterial since `userInfo["caseName"]` is what actually names the case. A `URLError` passes through **unchanged** (the `NSURLErrorDomain` code bridge is exactly what makes a transport failure legible; its URLs are handled downstream by the scrub), as does any other error type.
- `Telemetry/SentryErrorReporter.swift` → **the only file in the app that imports `Sentry`.** Kept separate from `ErrorReporting.swift` for precisely that reason. Calls `curated(_:)` first, then `capture(error:)` with a scope that sets `context` as a low-cardinality tag (safe because it's a `StaticString` by construction) and fans `extra` out to `setExtra`.
- `Telemetry/TelemetryPrivacyScrub.swift` → the pure, SDK-free walk `beforeSend`/`beforeBreadcrumb` adapt over. `scrub(_:Any)` recurses through nested dictionaries/arrays, descends into a nested `NSError` (rebuilding it with a recursively-scrubbed `userInfo`, same domain/code — the `NSUnderlyingErrorKey` leaf a `URLError`'s `userInfo` routinely carries, and the reason it needed its own case rather than falling through `default:`), and handles `URL`/`NSURL`/`String` leaves; everything else passes through. **`scrubEmbeddedURLs(in:)` is the non-obvious half and must not be "simplified" to the package's whole-string scrubber.** `WXYCAPI.URLScrubbing.scrub(_:String)` is conservative on purpose — it only touches a value that parses as a URL *in its entirety*, which is right for a structured leaf and useless for `exception.value` / `mechanism.desc`, because Foundation's default `NSError.description` renders the **entire `userInfo` dict inline as free text** (`… UserInfo={NSErrorFailingURLStringKey=https://…/library/search?artist=…, …}`), so a query-carrying URL appears there only as a **substring**. `scrubEmbeddedURLs` scans with `NSDataDetector` (built once; the type is documented as reusable) and rewrites matches **back-to-front** so earlier ranges stay valid against the mutating string. It is a strict generalization of the whole-string case, not a competing path.
- `Telemetry/BuildEnvironment.swift` → three cases (`development` via `#if DEBUG`, `testflight` via a receipt file literally named `sandboxReceipt`, else `production`). Sentry's `environment` defaults to `"production"` when unset, so without this every Simulator run files under real DJ traffic. Kept **whole in the app layer** (one caller, and it reads `Bundle.main`, which is meaningless under `swift test`), but the pure `classify(receiptURL:)` core takes the URL as a **parameter** — and is deliberately *not* itself `#if DEBUG`-guarded, since `WXYCDJTests` is a DEBUG build and an internal debug special-case would make the testflight/production split permanently untestable.
- `Telemetry/TelemetryBootstrap.swift` → `SentrySDK.start`, called at the **top of `AppDelegate.init()`** — which is why `AppDelegate.dependencies` moved from a default-value stored property to an assignment in the init body: default-value initializers run *before* the body, so the old shape built `AppDependencies` (and its real reporter) before telemetry was live, and the composition root's own store-open failures are exactly what this exists to see. Every option carries a comment pinning why; the six privacy options (`sendDefaultPii`, `attachScreenshot`, `attachViewHierarchy`, both session-replay rates) are stated **explicitly even where they match today's defaults**, so a future SDK version flipping one can't widen collection without this file changing too. `tracesSampleRate = 0` is a deliberate departure from the listener app's `0.05` (tracing adds a URL-carrying span surface for a benefit nobody asked for) and `enableCaptureFailedRequests = false` is load-bearing (this app fails requests **by design** and falls back to the clone — #58/#81 — so auto-capture would turn expected offline behavior into event spam). No client-side fingerprinting: the listener app measured client fingerprints degenerating to a single bucket on unsymbolicated Release frames, and dSYM upload is still a follow-up (#107). **Concurrency, already resolved:** a bare `import Sentry` suffices — sentry-cocoa annotates `beforeSend`/`beforeBreadcrumb` `NS_SWIFT_SENDABLE`, so no `@preconcurrency`, no `@Sendable`, no `nonisolated(unsafe)` is needed under `SWIFT_STRICT_CONCURRENCY: complete`. `productionDSN` is **hardcoded on purpose**, pointing at the `wxyc-dj-ios` project in org `wxyc` — a DSN authorizes writing events to one project and nothing else, and it ships inside the app binary wherever it's read from, so Info.plist plumbing or a remote-config fetch would buy nothing. The `#if DEBUG` `debugCaptureSerializedEvent(for:dsn:breadcrumb:via:)` hook returns the scrubbed event as a plain `[String: Any]` (never a `SentryEvent`: `@testable import` does **not** re-export `Sentry`, so the test bundle can't name a Sentry type — which is the same reason the test target never links the package). It's readable synchronously right after `capture` because `beforeSend` runs inline on the calling thread, verified against `SentryClient.m`.
- **Injection, never a global.** `AppDependencies` owns `let errorReporter: any ErrorReporter`. The **no-op default sits on *both* test-facing inits** — `init(catalogStoreURL:binStoreURL:reporter:)` and `init(catalogStore:catalogRefreshService:reporter:)` — because both are test paths, and the store-open degrade tests exercise exactly the paths the capture sites live on; defaulting a real `SentryErrorReporter` there would fire real events on every CI run. Only `convenience init()`, whose sole caller is `AppDelegate`, passes the real one explicitly. `BinViewModel.init(…errorReporter:)` and `LoginViewModel.init(…reporter:)` default to the no-op for the same reason plus a second one: ~34 existing construction sites across `WXYCDJTests` compile untouched. `LoginView` gained `@Environment(AppDependencies.self)` solely to hand the real reporter down (the object is already injected at every presentation context by `View+AppEnvironment`). No `ErrorReporting.shared`-style holder — that's the listener app's shape, not this repo's; here it's the same seam-injection style as `TokenStorage`, `RequestSession`, `PathProvider`.
- **Package prerequisites this landed in `WXYCAPI` (all pure Foundation, all host-tested).** `URLScrubbing` (see the project-structure boundary note). `ConnectivityErrorClassification` — the connectivity-class `URLError` list factored out of `ArtworkFailureClassification` so **one** home serves #86's "does this indict the URL" and both `AuthError`'s and `APIError`'s "is this just offline". `AuthError.offline(message:)` — the honest transport split: `AuthService` used to flatten every non-`AuthError` throw into `.network(message:)`, conflating a supported mode with a genuine defect, so the two flatten sites (`completeSignIn`'s leg 1, `recordingFailure`'s catch-all) now classify through one `classifyTransportFailure`; the two "Non-HTTP response" throws deliberately stay `.network` (a response reaching the HTTP layer with no status code is a bug, not evidence of being offline), and `localizedMessage` renders both cases identically so **nothing on screen changed** — only which case a capture site matches on. **`APIError.offline(message:)` is `AuthError.offline`'s peer** (added in review, since the API path had the identical flatten-and-discard shape without the split): `APIClient` classifies at **two** sites, not one — `fire(_:)`'s catch-all (including the pre-existing cancellation carve-out, which stays a carve-out from `onOutcome` but now throws `.offline` rather than `.network`, since a debounced-search cancellation or a DJ backing out of `AlbumDetailView` before `/library/info` returns is exactly the non-defect this split exists to name) and `currentJWT()`'s catch-all, a second discard site one layer below `fire` — `AuthService.currentJWT()` rethrows a raw, unwrapped transport error (not an `AuthError`) when its own lazy JWT-refresh leg fails offline, so `APIClient` has to classify that leg too or the same bug reopens through the token refresh instead of a data fetch. `AuthError.caseName` / `APIError.caseName` — **exhaustive switches with no `default:`**, so adding a message-bearing case is a compile-time decision rather than a silent leak; `APIError.CaseName` additionally carries a `detail: String?`, populated only for `.decoding` (the one deliberate exception — see its doc comment for why that's safe). And `APIClient.describe(_:)` narrowed to code-derived facts only (case kind, coding path, and — for `.typeMismatch`/`.valueNotFound` — the expected `Any.Type` Foundation itself supplies, which is code-derived and restores most of what issue #77's original triage needed), with `Context.debugDescription` dropped and the `@unknown default:` arm made a **constant**: `String(describing:)` on a `DecodingError` re-embeds that same `debugDescription`, so the constant is what stops the one branch a test can't construct from reopening the channel.
- **Capture-site inventory, and the report-vs-skip rule.** Each site sits **beside** its existing `os_log` call, never replacing it — the log line stays the on-device diagnostic of record.
  - `AppDependencies.init` catalog-store and bin-store open failures (`openBinStore(at:reporter:)` takes the reporter as a parameter — it's `static`, with no instance to read it off). Pure silent degrade: the DJ sees inert catalog/bin features and nothing that says why.
  - `AppDependencies.refreshCatalog()` / `handleBackgroundPoll()` error arms — **but not the `APIError.notSignedIn` skip** (an expected state — a missing/expired session is a silent skip + reschedule everywhere else too) **and not `APIError.offline`** (a supported mode, never a defect — an offline DJ must not generate an event on every launch/scene-`.active` refresh, or on a background poll running on a system schedule). `refreshCatalog()`'s `success` return value stays `false` on an offline failure exactly as it would on a genuine one — only the report is skipped, not the BGTask-reschedule signal. This is where a Core Spotlight `-1001` batch rejection or a genuine decode failure becomes visible in the field for the first time.
  - `BinViewModel.refresh()` load failures (**except `.offline`** — the bin already falls back to its offline snapshot, issue #60, so being offline here is not new information) and `persistSnapshot(after:)` save failures.
  - `AlbumDetailView.loadInfo()` — every failure **except `.offline`**, because `/library/info` is the shelf source of truth, not enrichment, but being offline is a supported mode on this leg exactly as on `loadMetadata()`'s below — the two legs may legitimately differ on `.http` (routine LML noise vs. a fatal shelf-data failure) but must not differ on `.offline`. This is also what a `.task { await loadAll() }` cancellation classifies as now (a DJ backing out of the screen before `/library/info` returns), so a routine Back tap no longer files an event. `loadMetadata()` is gated on the pure static total switch `shouldReportMetadataFailure(_:)`: `.decoding` **and** `.network` report (our own parsing breaking against a real payload, or a genuine transport defect — a malformed URL, a "Non-HTTP response" bug — now that `.offline` carries the connectivity meaning on its own), `.unauthorized`/`.notSignedIn`/`.http`/`.offline` don't (routine LML gaps, session states, or being offline).
  - **Sign-in has no throw to catch, so the capture point is `LoginViewModel`.** `AuthService.signIn`/`sendLoginCode`/`resendLoginCode` record into `lastError` rather than throwing to the app layer, so `reportIfDefect()` runs after each of the **four** legs settles (`submit`, `submitCode`, `requestCode`, `resendCode`) and reads `auth.lastError` — safe because `AuthService` clears it at the *start* of each of those calls, so what's left is this call's own outcome, never a stale carryover. `resendCode()` is the case worth the trouble: its `try?` swallows the throw entirely, so a failing resend was previously invisible *everywhere* — not thrown, not logged, not reported. The decision is the total switch `shouldReport(_:)`: **report** `.serverFailure`, `.missingSessionToken`, `.network`, `.notSignedIn` (here it means a session leg 1 just established was immediately rejected on the JWT exchange — an internal inconsistency, not the ordinary expiry that case means elsewhere); **never report** `.invalidCredentials`, `.rateLimited`, `.rejected`, `.offline` (expected outcomes the DJ can act on, or a supported mode). **A fifth signal, orthogonal to `lastError`:** `submit()`/`submitCode()` also call `reportPendingJWTIfNeeded()` after the leg settles, which reports whenever `auth.state == .signedIn(payload: nil)` — the issue-#53 "session established, JWT pending" window a *transient* JWT-leg failure (e.g. a `503` from `GET /auth/token`) leaves behind. `AuthService` deliberately does not treat that as an `AuthError` (the DJ *is* signed in), so `lastError` stays `nil` and `reportIfDefect()` alone would see nothing — a real gap, since the capture-site table above lists `.serverFailure` as reported and a JWT-leg `.serverFailure` never reaches `lastError` at all. No package change: `.signedIn(payload: nil)` is already public and already documented as meaning exactly this, so `LoginViewModel` just observes `auth.state` post-hoc via a synthetic `PendingJWTAfterSignIn` error under context `"LoginViewModel.pendingJWT"` (distinct from the `"LoginViewModel"` context `reportIfDefect()` uses, so the two group separately in Sentry). Only `submit()`/`submitCode()` check it — `requestCode()`/`resendCode()` never touch `state`, so checking there would risk reporting a stale pending window left by an unrelated, earlier sign-in.
- **Tests.** `WXYCDJTests` is **never linked against the `Sentry` package** — sentry-cocoa is largely ObjC and statically linking it into both a host app and its loaded test bundle produces duplicate ObjC class registration and two competing SDK singletons. Everything Sentry-touching is reached through the `WXYCDJ` seam under `@testable import`. `TelemetryPrivacyScrubTests` / `ErrorReportingTests` / `BuildEnvironmentTests` pin the pure logic; `SentryPrivacyPipelineTests` is the end-to-end belt, driving the real started SDK through `debugCaptureSerializedEvent` and asserting on **every string leaf in the serialized event** rather than a handful of anticipated field paths — that breadth is the point, since the bar is "nowhere in the event". Its `@Suite` is **`.serialized`**, and that is load-bearing, not tidiness: every test resets and reads `TelemetryBootstrap.lastSerializedEvent` (a `nonisolated(unsafe) static var`) and (re-)calls `SentrySDK.start`, both process-wide state Swift Testing's default parallelism would race — one test's reset nulling another's in-flight capture, or a test reading back a *different* test's event and passing vacuously. `SpyErrorReporter` (`WXYCDJTests/Support/`) is the lock-guarded recording double, in the style of `SpyBinStore`/`FakeThumbnailProvider`.
- **Known gaps, so nobody re-derives them.** `BinViewModel.remove()`'s failure arm is not reported (it surfaces a user-visible `removeError`, so it isn't a silent degrade — but a *systematic* DELETE failure would still be invisible to us). `AlbumDetailView`'s capture-site *wiring* is untested — only the pure `shouldReportMetadataFailure` decision is covered — because a SwiftUI `View`'s private async methods have no test harness in this repo, the same limitation `AlbumDetailArtworkTests` already lives with.

### PostHog product analytics (issue #108)

Anonymous product analytics via `posthog-ios`, extending ADR 0007's privacy contract rather than negotiating a new one — DJ-app users are individually identifiable by everything *else* the app holds (username, email, JWT), so analytics has to be strictly more anonymous than the identity it sits beside, not merely "PostHog's defaults."

**This app shares dj-site's PostHog project (444958), it does not have its own.** A deliberate exception to the org's one-project-per-surface convention — recorded in the org-level `CLAUDE.md` too, so the next reader doesn't diagnose it as drift. The reasoning is not the free tier's project cap: dj-site *is* the web equivalent of this app, the same DJs doing the same jobs (library search, the bin) on a different surface, and in separate projects "do DJs reach for the phone or the desktop for library search?" is unanswerable where in one project it is a breakdown on `$lib`. Verified before deciding (2026-08-24): the project's trailing-30-day traffic was entirely `$lib = web` with no `$identify` events, so `$lib` separates the surfaces cleanly and anonymous iOS events aren't dropped into a pool of identified DJ profiles. The token is hardcoded in `TelemetryBootstrap` beside `productionDSN`, for the same reason — a project token is a publishable client identifier that ships in the binary wherever it's read from, and this one is already public in dj-site's web bundle.

**Two consequences of sharing, both load-bearing.**

- **Event names must stay collision-free across both surfaces.** dj-site's live names (`$pageview`, `$rageclick`, `web_vitals`, `$exception`, `csp_violation`, `login_post_redirect`, `login_server_bounce`, the five `sse_*`, `flowsheet_optimistic_replace_miss`) collide with none of this app's twelve. Keep it that way in both repos: a reused name puts two schemas under one event, and `$lib` is a filter you have to remember to apply, not a guarantee.
- **Privacy contract item 3 (no IP retention) is the one item this app cannot hold by construction.** There is no client-side option for it; it's `anonymize_ips`, a **project-wide server-side setting**, so enabling it for this app also turns it on for dj-site — which loses its Web Analytics geo breakdown **going forward** (not retroactively; historical data is untouched). Accepted deliberately: dj-site's audience is the same Chapel Hill DJs, so the breakdown was worth little there either. It is only *safe* because dj-site runs `cookieless_server_hash_mode: 0` — **that setting is a tripwire for this whole decision.** With cookieless mode on, `$ip` becomes part of the identity hash and discarding it would break dj-site's person identification, so anyone turning cookieless mode on must revisit item 3 first.

- `Telemetry/Analytics.swift` → the seam, mirroring `ErrorReporting.swift`'s shape. `Analytics` is a **`Sendable` protocol** — `capture(_ event: some AnalyticsEvent)` — so any capture site calls it with no actor hop, matching `ErrorReporter.report`. `AnalyticsPropertyValue` is the closed set a property value may take: `.int`, `.bool`, and **`.enumString(any AnalyticsEnum)`** — where `AnalyticsEnum` is `RawRepresentable & CaseIterable & Sendable where RawValue == String`. The existential payload is the whole mechanism: `.enumString(typedText)` is a **compile error** ("argument type 'String' does not conform to expected type 'AnalyticsEnum'"), and `allowedValues` (the enum's full vocabulary, for the PII audit to check membership against) is a protocol extension derived on demand rather than data carried on every value. An earlier shape was `.enumString(String, allowedValues: Set<String>)` plus a doc comment asking call sites to use a factory — a hand-built `.enumString(typedText, allowedValues: [typedText])` compiled *and* passed the audit, i.e. the exact comment-enforced invariant ADR 0007 forbids. There is deliberately **no `.string(String)` case** — the identical trap `TelemetryValue` closes for Sentry's `extra` payload. `Equatable` is hand-written (an existential isn't `Equatable`) and compares the **type as well as** the raw value, so two vocabularies that share a spelling are never equal; it switches on `lhs` alone with no `default:`, so a fourth case is a compile error there. `AnalyticsPrivacyAllowlist` is the runtime backstop: `allowedKeys` is the flat `Set<String>` of every property key the wave-1 catalog may ever emit (`build_type` included, even though no event's own `properties` carries it — see `TelemetryBootstrap` below), `sdkLifecycleKeys` is the **separately-named, separately-reviewed** set of the five non-`$` properties posthog-ios attaches to its own application-lifecycle events (`version`, `build`, `previous_version`, `previous_build`, `from_background` — every one a `Bundle.main` version string or a `Bool`), and `filterNonSDKProperties(_:)` is the pure function wired into `PostHogConfig.setBeforeSend([...])`, scoped to **non-`$`-prefixed keys** — PostHog's `beforeSend` runs over the *fully merged* property dict, after its internal `buildProperties` has folded in `$app_version`/`$os_version`/`$device_type`/`$locale`/`$session_id` and, crucially, `$process_person_profile: false`, so a blanket allowlist would strip the anonymity flag `personProfiles = .never` depends on landing on every event, along with the SDK context. Keeping `sdkLifecycleKeys` a *separate constant* from `allowedKeys` (the two are asserted **disjoint**) is what lets the catalog audit keep meaning "keys this app's own events emit" while still letting the SDK's lifecycle events keep the payload that makes them worth having — without it, `Application Opened` arrives with no `from_background` and can't distinguish a cold launch from a resume. It is a named allowance, not a loosening: the mechanism is still "drop every non-`$` key that isn't on a reviewed list." `NoOpAnalytics` lives here too. The file imports **Foundation only** — same reasoning as `ErrorReporting.swift`: `WXYCDJTests` exercises the filter and the property-value shapes through `@testable import WXYCDJ` without linking `posthog-ios` into the test bundle.
- `Telemetry/AnalyticsEvents.swift` → **every event and property this app ever sends lives in this one file**, so the whole data-collection surface is auditable in a single diff — the acceptance bar issue #108 states explicitly. - `Telemetry/PostHogAnalytics.swift` → **the only file besides `TelemetryBootstrap.swift` that imports `PostHog`.** Holds no stored state (`PostHogSDK.shared` is the SDK's own internally-synchronized singleton, the same shape `SentryErrorReporter` uses), so it's trivially `Sendable`. `capture(_:)` is a single call: `PostHogSDK.shared.capture(type(of: event).name, properties: event.properties.mapValues(\.wireValue))`. **`build_type` is deliberately not stamped here** — it belongs on *every* event, and `captureApplicationLifecycleEvents = true` means the SDK emits `Application Opened`/`Installed`/`Updated`/`Backgrounded` by calling `PostHogSDK.capture` directly, bypassing this conformer entirely. `Application Opened` is both the canonical launch/retention event *and* the one a developer generates dozens of times a day, i.e. precisely where the dev-traffic pollution `build_type` exists to make filterable is worst. The `.enumString` membership assertion (`enumValue.allowedValues.contains(enumValue.rawValue)`) holds by construction for every synthesized `CaseIterable` `String` enum in the catalog today, so it can't fail against a real production event — its demonstrated value is catching a hand-written struct conformer with a hostile `allCases`, pinned by a dedicated negative test (issue #117). ## Dependency pins

`wxyc-swift-auth` is this repo's first remote dependency below the app target (the app itself has had sentry-cocoa and posthog-ios since #106/#108), and three things follow.

**Two committed resolved files, and nothing keeps them in step.** `Packages/WXYCAPI/Package.resolved` is the pin of record for `swift test --package-path Packages/WXYCAPI`; `WXYCDJ.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` (tracked via the `.gitignore` negation) pins the `xcodebuild` app builds. They are two independently-written files that happen to resolve the same graph, so a bump that touches one and not the other is a silent divergence — no check catches it, a reviewer has to. Move both together.

**A third, untracked one can appear.** `.gitignore` excludes `.swiftpm/`, so opening `Packages/WXYCAPI` **directly** in Xcode writes `.swiftpm/xcode/…/Package.resolved`, which drifts unseen. The two committed files are authoritative — delete the untracked one rather than reconciling it.

**A clean checkout no longer builds offline.** The first build of either the package or the app fetches `wxyc-swift-auth` over the network, so `swift test --package-path Packages/WXYCAPI` — CI's first step and the first line of the pre-flight below — now needs network where it previously did not.

## CI / pre-push checks

Two workflows run on PRs: `.github/workflows/ci.yml` (every PR and push to `main`) and `.github/workflows/verify-api-types.yml` (only when the vendored tree, the contract pin, or either codegen script changes — see "Code Generation"). The third command is needed **only if you touched `Packages/WXYCAPIModels/**` or `scripts/*-api-types.sh`**:

```bash
swift test --package-path Packages/WXYCAPI

# Pick any booted iPhone simulator; the workflow pre-boots the first available modern iPhone (preferring iPhone 16 Pro).

Both are enabled by default via scheme env vars in `project.yml` so a **physical-device** run picks them up automatically; `-skip-testing` skips *execution*, not compilation, so they still build on the Simulator. Run either by targeting a device destination and dropping its flag.

- `SpotlightClientStateToleranceTests` (`WXYC_SPOTLIGHT_TOLERANCE=1`, issue #36): Core Spotlight rejects client-state commits on the Simulator with `CSIndexError -1002`, so it can only pass on device.
- `SpotlightFieldResolutionTests` (`WXYC_SPOTLIGHT_FIELD_RESOLUTION=1`, issue #32): measures which `CSSearchableItemAttributeSet` fields resolve a free-text `CSSearchQuery` (and that a real `CatalogRow` resolves by artist / label / call number). The Simulator's Spotlight query path is unreliable, so the measurement is only trustworthy on device — the recorded `SPOTLIGHT FIELD RESOLUTION […]` log line is the issue-#32 "measured and recorded" artifact.

- Rotation editing — requires MD/SM role; separate concept from the personal bin.
- Flowsheet, playback, schedule, request line — different apps own those.

Don't add `swift-openapi-generator` as a second, competing codegen tool.

## LML enrichment

The detail view fan-outs two calls: `GET /library/info` (catalog row, source of truth for shelf data) and `GET /proxy/metadata/album` (LML — release year, label, genres, styles, tracklist, streaming URLs, Discogs URL, Wikipedia URL). The `AlbumMetadata` DTO matches the camelCase response shape `proxy.controller.ts` emits (hand-authored, not generated — see "Code Generation" above for why). The metadata call is **best-effort**: a 404, decoding failure, or rate-limit is captured via `os_log` under subsystem `org.wxyc.dj`, category `metadata`, and surfaced inline as a faint footer note instead of a red error banner — the catalog row still renders.

`loadAll` branches the fan-out on **whether a `fallback` exists**, because the LML call needs an artist name to key on. With one, metadata is fetched **concurrently** with `/library/info` off the fallback's artist/title — the case for every tab push, Search → Detail and (since issue #87) Bin → Detail. That's safe for the bin row specifically because `djs.service.getBinFromDB` and `library.service.getAlbumFromDB` both select `artists.artist_name` / `library.album_title` off the same joins, so the two sources can't disagree on the lookup keys; the bin row just knows them a round-trip earlier. Without a fallback — a Spotlight deep link that missed the on-device clone — `/library/info` is the only source of an artist name, so it's awaited first and metadata goes second. `infoLoaded` (which gates the Release-section label dedup) is set after `/library/info` settles on both branches.

**Header artwork precedence** (`AlbumDetailView.preferredArtworkURL`): `/library/info` → the live search-row `fallback` → the on-device clone → LML `metadata`. LML art is strictly last because it can resolve to a label-level image instead of the cover (Autechre — Confield coming back as the Warp Records logo). Two things are load-bearing:

- The catalog legs are read **directly off the view's state, not through `resolveCatalog`** — that resolver drops the search row the moment `info` lands, which is right for shelf *fields* but wrong for artwork, because Backend-Service's `getAlbumFromDB` (the `GET /library/info` select) **does not project `artwork_url`**, so `info.artworkURL` is in practice always `nil`. Routing artwork through the resolver knocked the correct cover out of the running the instant `/library/info` landed and let LML's label logo take the slot — the visible "cover swaps a beat after tapping a search result" bug.
- The clone is the artwork backstop, so `loadAll` reads it whenever the `fallback` row can't supply a cover (`shouldReadCloneForArtwork` — a row with a nil `artworkURL`, or no row at all on a Spotlight clone miss), **not** only in `loadInfo`'s failure arm as it once did. It branches on the **cover**, never on whether a `fallback` exists, which is what makes issue #87's Bin → Detail fallback (`BinEntry.detailFallback`, always artwork-less since the `/djs/bin` projection carries no `artwork_url`) behave here exactly as the old `fallback: nil` did — `fallback?.artworkURL` optional-chains to `nil` in both `shouldReadCloneForArtwork` and `preferredArtworkURL`, so the clone keeps the slot. The catalog export *does* carry `artwork_url` (`catalog-export.service.ts`), so this is what gives Bin → Detail a real cover instead of the label logo. It's read **concurrently with the network legs**: awaited afterwards, a clone-sourced cover would land after LML's and the header would visibly swap — the very defect this precedence exists to prevent.

Both pinned by `AlbumDetailArtworkTests`. **Issue #86 dead-URL fallthrough:** `AlbumDetailView` also holds `@State private var failedArtworkURLs: Set<URL>`, populated by the header's `AsyncImage` phase switch — `case .failure` (never `.empty`, which is "still loading," not "failed") calls `.onAppear { failedArtworkURLs.insert(url) }`, since the closure can't mutate `@State` during body evaluation but can once the failure view has rendered. `preferredArtworkURL` takes `failedURLs: Set<URL> = []` as a trailing parameter and walks the same `info` → `fallback` → `cloneRow` → `metadata` precedence, returning the first candidate URL **not** in `failedURLs`. Keying by URL rather than a bare "catalog failed" bool matters twice: a dead URL shared by two catalog sources (the search row and the clone commonly carry the same value) retires both in one record, and a failure recorded against one source's URL can never mask a *different*, healthy URL from another source — so a failed clone URL can't suppress a working `info` URL if `getAlbumFromDB` ever starts projecting `artwork_url`. Membership is permanent for the view's lifetime (a dead URL is tried at most once, never retried in a loop), and an empty `failedURLs` reproduces the pre-#86 behavior exactly — nothing is ever skipped just because it hasn't loaded yet, which is what keeps the #83 invariant (catalog art is never displaced by LML while genuinely in-flight) intact. The header is blank only once every candidate, catalog and LML alike, has failed.

Because recording is a **one-way door**, the failure is classified before it's recorded — `WXYCAPI`'s `ArtworkFailureClassification.indictsURL(_:)` is the gate. It lives in the package rather than on the view because it is pure Foundation (so `swift test` covers it on the host, per the test-tier split above) and because `ThumbnailProviding` fetches the same `artwork_url` CDN links and would want the same judgment. A **connectivity-class `URLError`** (`.notConnectedToInternet`, `.networkConnectionLost`, `.timedOut`, `.cannotConnectToHost`, `.cannotFindHost`, `.dnsLookupFailed`, `.secureConnectionFailed`, `.dataNotAllowed`, `.internationalRoamingOff`, `.callIsActive`, `.cancelled`) indicts the *link*, not the URL, so it is **not** recorded — otherwise a momentary blip on station Wi-Fi would permanently retire a healthy cover and hand the header to LML's label logo the instant connectivity returned, reintroducing the #83 defect through a different door and with no self-recovery. Everything else retires the URL: any non-`URLError`, and the **resource-level** `URLError`s (`.cannotDecodeContentData`, `.badServerResponse`, `.fileDoesNotExist`, `.resourceUnavailable`, `.badURL`, `.unsupportedURL`) — the first two being what a CDN's 403/404 error page looks like by the time it reaches the image decoder, i.e. the expired-signature and purged-asset cases #86 exists to recover from. **Do not simplify this to "any `URLError` is transient"** — that would swallow `.cannotDecodeContentData` and silently disable the whole fallthrough. The split fails safe (a blank header until the DJ re-enters the screen and `@State` resets) rather than unsafe (a permanently wrong cover), and mirrors `AuthService`'s transient/terminal JWT split (#53) and `APIClient`'s transport-vs-cancellation split (#58). The `.failure` branch also carries **`.id(url)`**, so the failure recorder re-mounts per URL rather than relying on `AsyncImage` passing back through `.empty` between two failing URLs — a `.failure(a)` → `.failure(b)` transition would otherwise keep the same `_ConditionalContent` branch, never re-fire `onAppear`, and stall the chain with candidates unvisited. Note the clone leg is only *populated* when `/library/info` failed or the search row is artless (`shouldReadCloneForArtwork` is `fallback?.artworkURL == nil`), so on the online Search → Detail path a dead search-row cover falls through to LML, not to the clone.
