# WXYC DJ — Claude Code Instructions

A small SwiftUI iOS app: sign in with dj.wxyc.org credentials, search the WXYC library with live results, view release metadata, and edit a per-DJ "bin" of favorites. Read `README.md` for the user-facing tour.

The local directory is `wxyc-dj-ios`; the Xcode project, scheme, and Swift module are all `WXYCDJ`; the display name is "WXYC DJ"; the bundle ID is `org.wxyc.dj`.

## Core conventions

- **Swift 6**, strict concurrency, `@Observable` (never `ObservableObject`).
- iOS **18.4+** target. iPhone-only (`TARGETED_DEVICE_FAMILY = 1`).
- SwiftUI throughout; no UIKit unless asked.
- TDD per `wxyc-ios-64/CLAUDE.md`: failing test → minimum implementation → refactor.
- **Do not introduce third-party packages without asking first.** The app uses Foundation, SwiftUI, Security (Keychain), and the local `WXYCAPI` package.

Follows the canonical rules in `../wxyc-ios-64/CLAUDE.md` — read it for SwiftUI idioms (`Task.sleep(for:)`, `foregroundStyle`, `clipShape(.rect(cornerRadius:))`, `Tab` API, `NavigationStack` + `navigationDestination(for:)`, `localizedStandardContains`, etc.). Repeat-rules are not duplicated here.

The Xcode project is regenerated from `project.yml`. Run `xcodegen generate` after editing `project.yml` **and** after adding any new source files to `WXYCDJ/` or `WXYCDJTests/` — xcodegen bakes explicit file references into the pbxproj at generation time, so new files aren't picked up until you regen.

`WXYCDJTests` is the bundle for anything that has to `@testable import WXYCDJ` (view models, the AppDependencies composition root, etc.). Pure networking / DTO / auth tests stay in `Packages/WXYCAPI/Tests/WXYCAPITests` so `swift test` can run them on the host without booting a simulator. `WXYCDJTests/Support/StubRequestSession.swift` + `Fixtures.swift` are deliberate copies of their `WXYCAPITests/Support/` counterparts — promote them to a shared SPM test-support target if a third bundle ever needs them.

## Networking layer (`WXYCAPI`)

- `Configuration.swift` → `WXYCAPIConfiguration` (auth + API base URLs, timeout). `.production` and `.localDevelopment` presets.
- `TokenStorage.swift` → `TokenStorage` protocol with `TokenSlot.sessionToken` / `.jwt`.
- `KeychainTokenStorage.swift` → kSecClassGenericPassword, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. No iCloud sync.
- `InMemoryTokenStorage.swift` → `OSAllocatedUnfairLock`-backed in-memory store for unit tests.
- `JWTPayload.swift` + `JWTDecoder` → client-side parse only; the server validates the signature against JWKS.
- `AuthService.swift` → `@MainActor @Observable`. State: `.unknown` → `.signedOut | .signingIn | .signedIn(payload: JWTPayload?)` (`Equatable`, so `.onChange(of:)` can observe it). Owns sign-in (`/auth/sign-in/username`, captures the `set-auth-token` response header), JWT exchange (`GET /auth/token`), JWT cache with 60 s leeway, sign-out, and `restoreSession()` for cold launch. `isSignedIn` is the convenience the Spotlight deep-link handler (step 7) reads to decide present-now vs. stash-and-replay. **Issue #53 transient/terminal split:** the session token is the credential, the JWT a derived re-mintable artifact, so `signIn`/`restoreSession` are two legs — establish the session, then exchange for a JWT. A JWT-leg failure that is *transient* (5xx / network / undecodable-2xx body) keeps the session token and enters a **pending window** `.signedIn(payload: nil)` (`nil` = "session established, JWT pending"; nothing reads the payload off `state`, every consumer keys on the case via `isSignedIn`), re-minting the JWT lazily on first `currentJWT()`; only a **401** on `/auth/token` is terminal (roll back, clear tokens, `.signedOut`). `currentJWT()` is the shared lazy-refresh chokepoint: a 401 there **demotes** to `.signedOut` (clearing tokens, so `RootView` swaps `MainView` → `LoginView`) — but **only if the rejected bearer is still the current `sessionToken`**, so a stale in-flight refresh resuming after a concurrent re-sign-in (interactive callers and the background catalog refresh share one `AuthService`) can't clobber the new session. A successful lazy refresh leaves `state` untouched (no `onChange` churn on the ~hourly refresh). `clearLocalSession()` is the one terminal-cleanup primitive shared by `signIn`'s rollback, `restoreSession`'s 401 arm, `currentJWT`'s demotion, and `signOut`. **Issue #66 success-path guard:** a private monotonic `sessionEpoch` (bumped by `clearLocalSession` and by `signIn` establishing a new token, but **not** by a `set-auth-token` rotation) is captured at the top of `refreshJWT` and re-checked on its 2xx success path *before* persisting — so a `signOut` (or re-sign-in) that lands during an in-flight refresh can't be resurrected by `captureRotatedSessionToken` re-writing the rotated bearer + JWT to the Keychain (which would leave `state == .signedOut` but a live token that the next cold-launch `restoreSession()` silently signs back in). It's the success-path mirror of `currentJWT`'s 401 token-identity guard; because rotation keeps the same generation, a benign overlapping double-refresh still resolves a JWT for both callers.
- `APIClient.swift` → URLSession wrapper. Attaches `Authorization: Bearer <jwt>`; on a 401, calls `authService.invalidateJWT()` and retries once (the shared `perform` transport core returns the `HTTPURLResponse` so callers impose their own status policy — `sendRaw` requires 2xx, `catalog` also accepts 304). Typed methods: `searchLibrary`, `albumInfo`, `albumMetadata`, `getBin`, `addToBin`, `removeFromBin`, and `catalog(ifModifiedSince:)` — the conditional-GET `GET /library/catalog` bulk export (issue #19) returning `CatalogFetchResult` (`.notModified` on a 304, else `.modified(rows:lastModified:)`); the body is gzipped NDJSON (one `CatalogRow` per line, transparently inflated), and the raw `Last-Modified` string is echoed back verbatim as `If-Modified-Since`. The transport `fire` reports each outcome to the `ConnectivityMonitor` hook (#56) — server-answered → online, thrown transport error → offline — **except a cancelled request** (`URLError.cancelled` / `CancellationError`), which is *not* a connectivity signal (the issue-#58 search debounce cancels the in-flight task on every keystroke); latching offline there would wrongly route later searches to the local clone with no self-recovery, so cancellation surfaces the error without touching the monitor.
- `JSONCoders.swift` → custom ISO-8601 decoder that handles both fractional-seconds and plain forms (since Backend-Service emits both).
- `RequestSession.swift` → tiny protocol over `URLSession.data(for:)` so tests can inject a `StubRequestSession`.
- `Catalog/CatalogStore.swift` + `Catalog/SQLiteCatalogStore.swift` → the id-keyed on-device catalog clone (issue #19 step 2). `CatalogStore` is a `Sendable` protocol (`row(id:)` O(1) lookup, `count()`, `lastModified()`, `replace(rows:lastModified:)`) so the shared `CatalogRefreshService` (step 4) can be spied. It is now purely the **deep-link read model** plus the **replace target**: issue #36 moved the Spotlight diff index-side (the indexer diffs the in-memory export snapshot against its own persisted fingerprint map), so the issue-#19 store-paging primitives `ids()` (the `SELECT id` diff input) and `rows(after:limit:)` (the keyset bulk read the indexer paged) were removed — they had no remaining callers. `SQLiteCatalogStore` is an `actor` over raw `import SQLite3`: rows are `JSONCoders`-encoded `CatalogRow` BLOBs in `catalog(id INTEGER PRIMARY KEY, row BLOB NOT NULL)`, the verbatim `Last-Modified` watermark lives in a `meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)` row (`NOT NULL` because the store DELETEs the row for a nil watermark rather than storing NULL), and a `200` wholesale-replaces both in one `BEGIN IMMEDIATE` transaction (a duplicate id, or any failure, rolls back and keeps the last-good clone — same fail-closed posture as the NDJSON parser). The C handle is owned by a nested `Connection` class so its `deinit` can `sqlite3_close` (an actor's nonisolated `deinit` can't touch the non-`Sendable` pointer). `CatalogRow.detailFallback` bridges a cloned row to an `AlbumSearchResult` for `AlbumDetailView`'s instant deep-link header (step 7). `AppDependencies` (step 5) opens the production store at `<Application Support>/Catalog/catalog.sqlite` (via the testable `defaultCatalogStoreURL()`), degrading to inert catalog features if it can't. **Issue #58 offline search:** `CatalogStore` also vends `search(query:limit:) -> [CatalogRow]` (artist/album/call-number full-text). `SQLiteCatalogStore` backs it with a **contentless** (`content=''`) FTS5 virtual table `catalog_fts(artist, album, call_number, tokenize='unicode61 remove_diacritics 2')` keyed by `rowid = catalog.id`, **rebuilt inside the same `BEGIN IMMEDIATE` transaction as the rows** (so the index can never drift) — a contentless table rejects `DELETE FROM`, so the rebuild clears it with the documented `INSERT INTO catalog_fts(catalog_fts) VALUES('delete-all')` command, then re-inserts. `remove_diacritics 2` makes "nilufer" match "Nilüfer Yanya". `search` runs `… WHERE catalog_fts MATCH ? ORDER BY rank LIMIT ?` then loads each match's BLOB by id (the contentless index stores no original text). FTS5 ships in Apple's system libsqlite3 on iOS/macOS, so the `CREATE VIRTUAL TABLE` always succeeds; a missing module would surface as a store-open error. **Migration self-heal (#58 review):** the index is created empty and only `replace()` (a `200`) fills it, so a clone written by a pre-#58 build (rows present, no `catalog_fts`) would `304` forever with an empty index; `search` therefore calls a one-time `ensureSearchIndex()` that backfills the index from the existing rows when a `COUNT(catalog) != COUNT(catalog_fts)` mismatch shows it's stale — **watermark untouched** (the conditional-GET path is undisturbed), run inside the actor (off-main) and only when offline search is exercised, latched per connection (`replace` keeps both in sync thereafter).
- `Catalog/FTSQuery.swift` + `Search/LibrarySearch.swift` → the issue-#58 offline search seam. `FTSQuery.match(for:)` is the pure, safe MATCH builder: empty/whitespace → `nil`; each whitespace token becomes a **quoted prefix** term (`juana` → `"juana"*`, `bar baz` → `"bar"* "baz"*`) with interior double quotes doubled, so user punctuation can never inject FTS5 operators. `LibrarySearch` (`@MainActor` struct over `APIClient` + `any CatalogStore?` + `ConnectivityMonitor`) is the online-first/offline-fallback router: **online** tries the server (byte-for-byte the old `searchLibrary(artist:title:)` call) and on *any* thrown error falls back to local; **offline** goes straight to local; the local arm maps `store.search` rows through `CatalogRow.detailFallback`. It never throws — a failed/offline search degrades automatically (no manual retry) — and returns `LibrarySearchOutcome(results:source:)` with `.server`/`.local` so the UI can frame offline results. A `nil` store makes it server-only (offline → empty `.local`). Built once by `AppDependencies` and handed to each `SearchViewModel`; host-tested against `StubRequestSession` + `SpyCatalogStore` (whose `search` is a diacritic-folded substring filter).
- `Catalog/CatalogIndexing.swift` + `Catalog/SpotlightCatalogIndexer.swift` + `Catalog/SearchableIndexing.swift` + `Catalog/CatalogSpotlight.swift` + `Catalog/CatalogIndexState.swift` → the **Core Spotlight indexer** (issue #19 step 3; **delta-reindex reshape in issue #36**). `CatalogIndexing` is the `Sendable` seam step 4 drives — `reindex(snapshot:watermark:) -> ReindexSummary` mirrors the **in-memory `[CatalogRow]` export** into `CSSearchableIndex` and `indexedWatermark()` reads the committed watermark back (step 4 sources its poll watermark from *this*, not `store.lastModified()`, so a crash can't strand the store ahead of the index). The reshape: instead of paging the store and re-upserting every row, `SpotlightCatalogIndexer` diffs the snapshot against its **own persisted `id → content-fingerprint` map** (`CatalogIndexState`, committed as Core Spotlight **client state** alongside the watermark) and derives **add** (id absent from the map), **change** (id present, fingerprint differs), **remove** (in the map, absent from the export — so the removed set survives `store.replace` and is reproducible across a mid-reindex crash, fixing issue #36 limitation 1), and **unchanged** (equal fingerprint → skipped, so a typical `200` costs `O(delta)`, fixing limitation 2). The fingerprint (`CatalogSpotlight.fingerprint(for:)`) is a **stable** SHA-256-derived `UInt64` over exactly the fields feeding `searchableItem(for:)` (album/artist/label/call-number components + `artworkURL` for #44) — never `CatalogRow.hashValue`, which Swift salts per process. It upserts `add ∪ change` and deletes `remove`, packing **both** into bounded batches whose combined item count never exceeds 32 767 (`Int16.max`; Core Spotlight rejects a larger single `beginBatch()`/`endBatch(withClientState:)` cycle with `CSIndexErrorDomain -1001`). The watermark advances **only on the final batch**; each batch commits the fingerprint map of work applied **so far** (cumulative, since a batch's `endBatch` durably applies its upserts/deletes) and intermediate batches withhold the watermark (`nil`), so the persisted map stays consistent with the physical index between batches — a crash mid-run leaves the next run able to reconcile a *fresh* export against what the index actually holds (re-deleting a now-vanished id rather than stranding it), not just an unchanged one. `indexedWatermark()` reads only the watermark prefix (`CatalogIndexState.decodeWatermark`) so the cheap conditional-GET path never decodes the whole map. `CatalogIndexState` is a compact little-endian codec (version byte + watermark + sorted `id`/`fingerprint` entries) that decodes an empty/legacy-bare-watermark/truncated blob to `nil` → treated as empty, forcing a from-scratch reindex. The ~1 MB map written through client state is the accepted cost of keeping the watermark + map a single atomically-committed blob (option (a) in the issue); a typical change day is a single batch so the map is written once. It is **gap-free**: the `SearchableIndexing` seam exposes no delete-by-domain, so home-screen search is never emptied mid-reindex. `SearchableIndexing` wraps the four `CSSearchableIndex` batch calls (auto-bridged to `async throws` — no manual continuation needed); the real conformer `RealSearchableIndex` is `@unchecked Sendable` (`CSSearchableIndex` isn't `Sendable` and isn't thread-safe in batch mode, but step 4 drives exactly one sequential reindex). `CatalogSpotlight` owns the `"album.<id>"` ↔ `Int` round-trip (step 7's deep link reuses `albumID(from:)`), the pure `CatalogRow → CSSearchableItem` mapping (the `searchableItem(for:thumbnailData:)` overload embeds an issue-#44 cover; `searchableItem(for:)` delegates with `nil`), and the content fingerprint. `CatalogIndexing.upsert(row:thumbnailData:)` is the issue-#44 single-row **non-batch** write (no `beginBatch`/`endBatch`, so no client-state commit — a thumbnail attach never advances the watermark). CoreSpotlight + CryptoKit import on the package's macOS slice, so this is all host-testable under `swift test` against `FakeSearchableIndex` (a lock-guarded `Sendable` class, **not** an actor; its committed client state decodes back to `CatalogIndexState` for assertions). The live index is a **client-owned named index** (`CatalogSpotlight.indexName = "org.wxyc.dj.catalog"`) — batching and client-state are unsupported on the shared `.default()`; `SpotlightCatalogIndexer(indexName:)` is the convenience that builds `RealSearchableIndex(CSSearchableIndex(name:))`, wired by `AppDependencies` in step 5. **Simulator gotcha (cost us a debugging detour):** Core Spotlight *surfacing* is unreliable on the iOS Simulator — a clean `Catalog refresh: refreshed(rowCount: …)` log there does **not** mean items appear in home-screen search; they frequently never surface on the sim even when correctly indexed. Always confirm home-screen search on a **physical device**. A simulator no-show is not evidence of an indexing bug — check the refresh log for the real outcome (a `-1001` would be a genuine indexing failure; no error + no results = sim flakiness).
- `Catalog/ThumbnailDownscaling.swift` + `Catalog/ThumbnailProviding.swift` → the **Spotlight thumbnail cache** (issue #44). Spotlight does **not** fetch a remote `artwork_url` for app-indexed content, so a cover must be materialized on-device and embedded as `CSSearchableItem.thumbnailData` (embedded bytes, **not** `thumbnailURL` — the index owns its own copy, so eviction/container-path-rot can never dangle a live item's art, rdar://23592852). `ThumbnailDownscaler.downscaledJPEG(from:maxPixelDimension:compressionQuality:)` is the pure ImageIO transform (256 px, JPEG q0.8, never upscales; **no HEIC** — broken on the 17.5+ Simulator and undocumented for Spotlight). `ThumbnailProviding` is the `Sendable` seam (`localThumbnailURL(for:) async -> URL?`); the real `DiskThumbnailProvider` is an `actor` caching `<App Support>/Catalog/Thumbnails/<id>-<urlhash>.jpg` (the urlhash = first 16 hex of SHA-256 over the URL, so a changed cover invalidates), fetching via an injected `RequestSession` (production: `URLSession.shared`, reusing the `AsyncImage`/`URLCache` in-app cover loads populated), downscaling, and writing atomically (`.write(.atomic)`) with per-key single-flight. The cache is only the **fetch-dedup ledger** — never load-bearing for "does the index still have the art" (the index owns the bytes). No Discogs API key (stored URLs are pre-signed CDN URLs, plain `GET`); single lazy fetches only, never bulk. Populated by use (the Apple Music `AMPArtworkAgent` model), wired from `AlbumDetailView.task` + `SearchResultRow.onAppear` via `AppDependencies.cacheThumbnail(forAlbumID:)` (a thin pass-through; the dedup lives in `CatalogRefreshService`, keyed on the cover's cache-file so a *changed* cover re-attaches and cleared on every reindex so a stripped cover self-heals). **PR-2 deferrals (issue #44):** the cached-only `reindex` attach + global-sweep cache cap/prune; host-testable under `swift test` (ImageIO/CryptoKit on the macOS slice) against `StubRequestSession`/`BlockingRequestSession`. The home-screen "result shows the cover" half is a **device-only** check (Simulator surfacing is unreliable, per #19/#32).
- `Catalog/CatalogRefreshService.swift` → the **shared refresh service** (issue #19 step 4): the poll → `304`/`200` → store-replace → Spotlight-reindex flow the foreground path and both background tasks call, so the bulk runs off the main actor and the BGTask layer stays thin. It is an **`actor` that serializes *all* index touches** — every `refresh()` **and** every issue-#44 lazy `cacheThumbnail()` — through one serial chain (`runSerial`/`inFlight`): each op drains its predecessor before starting, in **both** directions, so no two Core Spotlight batches/writes ever overlap (the soundness condition for `RealSearchableIndex`'s `@unchecked Sendable`) and the indexer's fingerprint-map diff can't race a concurrent `replace`. The `Task { }` in `runSerial` inherits the actor's isolation, so cleanup (`endSerialOp`, which frees the tail and decrements the counters) runs in the *wrapper task's* frame when the work settles — a cancelled caller can't free the slot mid-batch, and the increment/decrement can't be skipped by a cancellation delivered while the op awaits its predecessor. **Issue #44 dropped issue-#19's refresh↔refresh coalescing** for this single mechanism: two overlapping refreshes now run sequentially (the second a cheap `304`) instead of collapsing onto one round-trip — the accepted trade for one serialization primitive. Two derived counters (not gates): `activeCount` frees the tail at idle; `refreshInFlight` is what `poll()` defers to (a thumbnail upsert must **not** suppress the poll — it doesn't reindex). `refresh()` sources the poll watermark from `indexer.indexedWatermark()` (the index's committed client state), **not** `store.lastModified()` — the load-bearing crash-safety invariant: the store is replaced *before* the index commits, so if a crash lands between them the next poll re-fetches and re-indexes instead of `304`-ing past a watermark the index never reached (equivalently, the watermark advances only when `endBatch` succeeds). On a `200` it replaces the store, then hands the **in-memory snapshot** to `indexer.reindex(snapshot:watermark:)` — the indexer derives the add/change/remove delta against its own persisted fingerprint map (issue #36), so the removed set survives the replace and unchanged rows are skipped — returning an `Outcome` (`.upToDate` / `.refreshed(rowCount:upserted:removed:)` / `.skippedEmptyExport`) for logging. An **empty `200` body is skipped** (`.skippedEmptyExport`, no replace, no watermark advance) — a defensive data-safety guard, since an empty export is far likelier a backend hiccup than a real empty catalog and replacing with it would wipe the last-good clone and then `304` forever. Host-tested under `swift test` against a `StubRequestSession` client + `SpyCatalogStore`/`SpyCatalogIndexer` (304 is a no-op; 200 replaces the store then hands the snapshot to the indexer, the spy modelling its own fingerprint map so the recorded delta is faithful; an empty 200 is skipped; a failed reindex leaves the watermark un-advanced and a fresh indexer retries) plus an end-to-end pass over the real `SQLiteCatalogStore` + `SpotlightCatalogIndexer`. `poll()` (step 5) is the cheap conditional probe the background app-refresh leg uses: it returns whether the catalog moved **without** replacing the store or reindexing (so the heavy work defers to a charging-gated processing task). It opens no batch and isn't serialized into the chain, but **short-circuits to "no change" when a refresh is in flight** (`refreshInFlight > 0`) — that refresh reindexes, so the reindex leg has nothing to add, and skipping avoids a second index handle reading client state during the refresh's open batch. It does **not** defer to a lazy thumbnail upsert: an upsert neither reindexes (deferring would skip a real catalog change) nor opens a batch (so the client-state read is safe). Still pays the body download + decode on a `200` — a body-less probe is a Backend-Service follow-up. The service takes a **`makeIndexer` factory and builds a fresh indexer per `refresh()`/`poll()`/`cacheThumbnail()`** (step 5): `CatalogIndexing`'s contract is that a reindex throwing mid-batch can only be recovered on a freshly-constructed `CSSearchableIndex`, so reusing one for the process would let a single mid-batch failure poison every in-process retry (scene-activation refresh, the background reindex leg) until relaunch — a fresh indexer reads the same persisted client-state watermark and recovers on the next run, and keeps `poll()`'s watermark read off any in-flight reindex's open batch. **`cacheThumbnail(forAlbumID:)`** (issue #44) is the lazy thumbnail attach: best-effort, non-throwing, serialized through the chain; it resolves the cloned row + its cover off the actor via the injected `thumbnailProvider`, then a **plain non-batch** `indexer.upsert(row:thumbnailData:)` that touches no client state (the watermark never advances on a thumbnail attach).

When adding a new endpoint, prefer to:
1. Add a typed method on `APIClient` (don't expose raw `sendRaw`).
2. Add a DTO in `Sources/WXYCAPI/DTOs/`. Keep `snake_case` mapping in an explicit `CodingKeys` enum — `convertFromSnakeCase` is intentionally not used because the wire format mixes camelCase paths (e.g. `albumId` in nested types coming from Drizzle) with snake_case top-level.
3. Write tests against `StubRequestSession`. See `APIClientTests.swift` for the pattern.

## UI layer (`WXYCDJ`)

- `AppDependencies` is the composition root. One instance, owned by `AppDelegate` (so the SwiftUI scene and the reindex BGTask handler share the same `CatalogRefreshService` — required for its serial-chain no-overlapping-batch guarantee across all index touches), read via `appDelegate.dependencies` and environment-injected.
- **Catalog refresh wiring (issue #19 step 5).** Foreground-primary, background-best-effort. `WXYCDJApp`'s launch `.task` runs `restoreSession()` then `refreshCatalog()`, and re-runs `refreshCatalog()` on scene `.active`; on scene `.background` it arms the poll. The background split lives in `Catalog/CatalogBackgroundTasks.swift`: `org.wxyc.dj.catalog.refresh` is a `BGAppRefreshTask` registered by SwiftUI's `.backgroundTask(.appRefresh:)` (re-arms, polls, submits the reindex on a `200`); `org.wxyc.dj.catalog.reindex` is a `requiresExternalPower` `BGProcessingTask` registered in `AppDelegate` (SwiftUI has no `.processing` matcher) — the launch handler is non-`Sendable`, so the `task` is bridged into structured concurrency with `nonisolated(unsafe)` (sound because only the work task touches `task`; the expiration block captures only the `Sendable` work task). `setTaskCompleted(success:)` reports `refreshCatalog()`'s **real** outcome (`refreshCatalog()` returns a `Bool`), not whether the work was cancelled. Expiration cancellation is a cooperative signal, not true preemption — the watermark invariant makes an interrupted reindex safe to retry. A missing/expired session is a silent skip + reschedule (pinned by a no-session `CatalogRefreshService` test); the background poll re-arms only when a catalog store exists. Both ids + `UIBackgroundModes` (`fetch`, `processing`) live in `project.yml`'s `info:` block (this target uses a **generated `Info.plist`**, not `GENERATE_INFOPLIST_FILE`, since those keys aren't `INFOPLIST_KEY_*`-expressible); the entitlements file is unchanged (Core Spotlight + BackgroundTasks need none). **Debug a BGTask leg** from a paused debugger with the LLDB SPI `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"org.wxyc.dj.catalog.refresh"]` (or `_simulateExpirationForTaskWithIdentifier:`); the task must already be submitted, and `_simulateLaunch` bypasses the external-power/network gates. See README for the full recipe.
- **Routable navigation (issue #19 step 6).** `AlbumRoute.swift` is the single value pushed onto every album `NavigationStack` path — `struct AlbumRoute: Hashable, Identifiable { let id: Int; var fallback: AlbumSearchResult? }` with `==`/`hash` over **`id` only**. Both `SearchView` and `BinView` carry **one** `.navigationDestination(for: AlbumRoute.self)` hoisted onto their always-mounted `Group` (was nested inside `SearchView`'s `.results` case / `BinView`'s non-empty `default` case — unregistered in idle/empty states, fatal for a programmatic push and a latent lazy-container warning even for the tap). Search rows route `AlbumRoute(id: row.id, fallback: row)` (the live row renders the detail header instantly); Bin rows route `AlbumRoute(id: entry.albumId, fallback: nil)` (no clone, so the detail view awaits `/library/info`). id-only identity is load-bearing: a clone-hit (`fallback`-bearing) and a clone-miss (`fallback: nil`) for the same album coalesce on the path, and `AlbumSearchResult`'s whole-struct `Hashable` (which diverges across cloned vs. live rows on `addDate`/`artworkURL`/`plays`) never fragments it — the property the step-7 deep link relies on. Value semantics pinned in `WXYCDJTests/AlbumRouteTests.swift`.
- **Spotlight deep link + auth replay (issue #19 step 7).** A home-screen Spotlight tap opens the release detail in **its own `fullScreenCover` + `NavigationStack`** over `RootView` (`Detail/DeepLinkAlbumCover.swift`) — never pushed onto the Search/Bin tab stacks, so it can't pollute their nav/scroll state or fabricate a Back target; the cover's "Close" returns the DJ to the exact tab + scroll position. `Router.swift` is a `@MainActor @Observable` two-slot holder (`deepLink: AlbumRoute?` bound to the cover, `pending: Int?` the cold-launch stash) owned by `AppDependencies` and injected via `.environment`. The resolution logic lives on `AppDependencies` (it owns `catalogStore`): `handleSpotlightTap(albumID:isSignedIn:)` presents immediately when signed in (O(1) `catalogStore.row(id:)` lookup → `CatalogRow.detailFallback` for the instant header; a clone miss routes `fallback: nil` and the detail view awaits `/library/info`) or parks the id in `Router.pending` otherwise; `handleAuthChange(wasSignedIn:isSignedIn:)` reconciles the surface on every auth transition — **flip to signed-in** replays a parked id, **genuine sign-out** (`wasSignedIn && !isSignedIn`) tears down via `invalidateDeepLink()` (dismiss the cover + drop the park) so a detail can't strand over `LoginView` issuing 401s, while a **cold-launch `.unknown` → `.signedOut`** keeps the park for a later manual sign-in (which is why it needs the old *and* new flags, via `AuthService.State.isSignedIn`). Presentation funnels through a private `present(albumID:)`: it early-outs when the same album is already shown (skipping a redundant clone read), clears `pending` synchronously (so a fresh tap supersedes a park), and gates the post-`await` `deepLink` write behind a monotonic `presentationToken` — so when a parked replay, a fresh tap, **or a sign-out** race across the clone-lookup suspension, the **most-recently-requested** outcome wins deterministically rather than whichever store read resumes last (a sign-out bumps the token via `invalidateDeepLink`, so an in-flight `present` resuming post-sign-out bows out). **Activity delivery is via a `UIWindowSceneDelegate`, not the view-level `onContinueUserActivity`** — the latter was silently dropping the `CSSearchableItemActionType` activity in **both** cold- and warm-launch states (the original step-7 bug). `SceneDelegate.swift` is attached to SwiftUI's window scene through `AppDelegate.application(_:configurationForConnecting:)` (only `delegateClass` is set — no `sceneClass`/storyboard — so SwiftUI keeps owning the window and hosting `RootView`; verified no black-screen). It catches the tap in the two states the system actually routes through the scene: cold launch via `scene(_:willConnectTo:)`'s `connectionOptions.userActivities` (the launch activity is **not** delivered to `UIApplication`'s `continue` method in a scene-based app), and warm via `scene(_:continue:)`. Both forward to `AppDependencies.handleSpotlightContinuation(_:)`, which parses the activity via `CatalogSpotlight.albumID(fromActivity:)` (the testable seam wrapping the `userInfo[CSSearchableItemActivityIdentifier]` → `"album.<id>"` extraction, pinned in `CatalogSpotlightTests`) and calls `handleSpotlightTap(albumID:isSignedIn:)` with the live auth state. `RootView` still carries `.onContinueUserActivity(CSSearchableItemActionType)` as a **fallback** routed through the same `handleSpotlightContinuation` (a double-delivery is a harmless no-op — `present()` early-outs on the already-shown album, and the `presentationToken` latch collapses a concurrent double-present), kept until the scene-delegate path is confirmed on device. `RootView` wires its remaining two modifiers onto its always-mounted `Group` (so they're live in **every** auth state, incl. the cold-launch spinner): `.onChange(of: auth.state) { old, new in … }` → `handleAuthChange`, and `.fullScreenCover(item: $router.deepLink)`. Both the scene root and the cover inject the app-wide observable trio (`deps` + its `authService` + its `router`) through one `View.wxycAppEnvironment(_:)` helper (`View+AppEnvironment.swift`) — cover content doesn't inherit the presenter's `.environment(_:)` objects, and the single helper keeps the two injection sites from drifting, so the shared `AlbumDetailView` runs under an identical environment on the deep-link and tab-push paths. The signed-in gate is **passed in** to `handleSpotlightTap` (not read off `authService`) so the replay is unit-testable without a real sign-in — `WXYCDJTests/RouterDeepLinkTests.swift` drives an `AppDependencies` over a temp `SQLiteCatalogStore`. The deep link is an in-app `NSUserActivity` continuation, **not** a Universal Link, so it needs no Associated Domains / AASA entitlement.
- **QR sign-in for the shared control-room computer (ADR 0002).** `WXYCDJ/QRSignIn/` holds the iOS half of the device-authorization flow: a `QRScannerView` (AVFoundation `AVCaptureMetadataOutput` over a `UIViewControllerRepresentable` whose `AVCaptureSession` is `nonisolated(unsafe)`-owned and start/stopped on a dedicated `sessionQueue`), a `QRSignInPayload` pure parser that accepts only `https://dj.wxyc.org/auth/device?user_code=…` (the trust boundary — a hostile QR pointing elsewhere never reaches a verify call), a `BiometricAuthenticator` protocol whose production conformer wraps `LAContext.evaluatePolicy(.deviceOwnerAuthentication, …)` (Face ID → Touch ID → passcode cascade), a `@MainActor @Observable QRSignInViewModel` state machine (`scanning → approving → authenticating → verifying → succeeded | rejected | roleGated | error`) that runs a **proactive client-side role gate** (`dj`/`music_director`/`station_manager`/`engineer` only — server is still source of truth) before any approve, and a `QRSignInFlowView` host the toolbar `fullScreenCover` presents. `AccountMenuToolbar` is the shared `ToolbarContent` `SearchView` and `BinView` both adopt — `qrSignInEnabled` is the **feature-gate** Info.plist boolean `WXYCQRSignInEnabled` (default `false` until Backend-Service ships the endpoints; flipping it on rebuild is the rollout). The wire contract matches `wxyc-shared/api.yaml` (issue #195, `@wxyc/shared@1.14.0`): two endpoints `POST {authBaseURL}/device/approve` and `POST {authBaseURL}/device/deny` (auth base URL — better-auth mounts the device-authorization plugin under `/auth/device/*`), camelCase body `{ "userCode": "…" }` (intentionally asymmetric with the snake_case `GET /auth/device?user_code=…` lookup — do **not** "normalize"), success `{ "success": true }`, error envelope `{ "error", "error_description" }` with four typed codes (`invalid_request` → `QRSignInError.invalidCode`, `expired_token` → `.expiredCode`, `unauthorized` → `.notSignedIn`, `access_denied` → `.accessDenied`); anything else wraps as `.transport(APIError)`. `APIClient.approveDevice`/`denyDevice` use a parallel `performAuthBaseURL` to reuse the Bearer + 401-retry chain. The biometric authenticator and feature gate are both held on `AppDependencies` (default `LocalAuthenticationAuthenticator()`; test seam initializer takes both as parameters). **Note** that ADR 0002 in this repo predates the published api.yaml and describes a single unified `/device/verify` endpoint with an `action` field; the published contract diverged to the approve/deny split. The implementation tracks the published contract — update ADR 0002 if a future change needs the historical framing.
- View models are `@MainActor @Observable` classes; each view either constructs its VM via `onAppear` (e.g. `SearchView`) or takes one from a parent.
- Views read `AuthService` directly from `@Environment(AuthService.self)` when they need state, e.g. the toolbar sign-out menu.
- Debounce pattern (in `SearchViewModel`): cancel `searchTask` on every query change, then start a new `Task` that `Task.sleep(for: .milliseconds(300))`s and checks `Task.isCancelled` before issuing the request. Don't reach for Combine. The debounced task delegates to `LibrarySearch` (issue #58) rather than calling `api.searchLibrary` directly, so the VM has no `.error` state — a failed/offline request falls back to the on-device clone automatically. The VM exposes `source` (`.server`/`.local`); `SearchView` shows a quiet "Showing saved library" note in the `.results` state when `source == .local`, and in the `.empty` state a `source == .local` miss renders a distinct "No saved matches" placeholder (so a local-clone miss doesn't read as a confirmed "not in the WXYC library" — the live catalog wasn't consulted) instead of the generic "No Results".

## Tests

Two bundles, both Swift Testing (not XCTest):

- **`WXYCAPITests`** in `Packages/WXYCAPI/Tests/` — networking, DTOs, auth, JWT decoding. Runs via `swift test --package-path Packages/WXYCAPI` on the host (no simulator needed; the package declares both `.iOS(.v18)` and `.macOS(.v14)`).
- **`WXYCDJTests`** in `WXYCDJTests/` — app-target tests for view models and other code that has to `@testable import WXYCDJ`. Runs via `xcodebuild test` against a booted iOS simulator.

Test fixtures use WXYC-representative artists — Juana Molina / DOGA, Jessica Pratt / On Your Own Love Again, Chuquimamani-Condori / Edits. **Do not** introduce mainstream substitutes (Queen, Radiohead, The Beatles); the canonical pool is `wxyc-shared/src/test-utils/wxyc-example-data.json`.

## CI / pre-push checks

GitHub Actions (`.github/workflows/ci.yml`) runs on every PR and push to `main`. The local pre-flight mirrors it — run both commands before opening a PR so CI minutes aren't wasted on red builds:

```bash
swift test --package-path Packages/WXYCAPI

# Pick any booted iPhone simulator; the workflow pre-boots the first available modern iPhone (preferring iPhone 16 Pro).
SIM_ID=$(xcrun simctl list devices available | grep -m1 'iPhone 1[67].*Booted' | grep -oE '\([A-F0-9-]{36}\)' | tr -d '()')
xcodebuild test \
  -project WXYCDJ.xcodeproj \
  -scheme WXYCDJ \
  -destination "platform=iOS Simulator,id=$SIM_ID" \
  -configuration Debug \
  -skip-testing:WXYCDJTests/SpotlightClientStateToleranceTests \
  -skip-testing:WXYCDJTests/SpotlightFieldResolutionTests \
  CODE_SIGNING_ALLOWED=NO
```

`CODE_SIGNING_ALLOWED=NO` keeps the test step from requiring a provisioning profile. The test step needs a real simulator (not `generic/platform=iOS Simulator`) because `WXYCDJTests` is a host-app unit-test bundle.

Two **device-only** Spotlight suites are `-skip-testing`'d on the Simulator (CI and local). Both are enabled by default via scheme env vars in `project.yml` so a **physical-device** run picks them up automatically; `-skip-testing` skips *execution*, not compilation, so they still build on the Simulator. Run either by targeting a device destination and dropping its flag.

- `SpotlightClientStateToleranceTests` (`WXYC_SPOTLIGHT_TOLERANCE=1`, issue #36): Core Spotlight rejects client-state commits on the Simulator with `CSIndexError -1002`, so it can only pass on device.
- `SpotlightFieldResolutionTests` (`WXYC_SPOTLIGHT_FIELD_RESOLUTION=1`, issue #32): measures which `CSSearchableItemAttributeSet` fields resolve a free-text `CSSearchQuery` (and that a real `CatalogRow` resolves by artist / label / call number). The Simulator's Spotlight query path is unreliable, so the measurement is only trustworthy on device — the recorded `SPOTLIGHT FIELD RESOLUTION […]` log line is the issue-#32 "measured and recorded" artifact.

## Things explicitly out of scope

Don't add these without asking:

- Rotation editing — requires MD/SM role; separate concept from the personal bin.
- Flowsheet, playback, schedule, request line — different apps own those.

## LML enrichment

The detail view fan-outs two calls: `GET /library/info` (catalog row, source of truth for shelf data) and `GET /proxy/metadata/album` (LML — release year, label, genres, styles, tracklist, streaming URLs, Discogs URL, Wikipedia URL). The `AlbumMetadata` DTO matches the camelCase response shape `proxy.controller.ts` emits. The metadata call is **best-effort**: a 404, decoding failure, or rate-limit is captured via `os_log` under subsystem `org.wxyc.dj`, category `metadata`, and surfaced inline as a faint footer note instead of a red error banner — the catalog row still renders.
