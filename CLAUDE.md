# WXYC DJ — Claude Code Instructions

A small SwiftUI iOS app: sign in with dj.wxyc.org credentials, search the WXYC library with live results, view release metadata, and edit a per-DJ "bin" of favorites. Read `README.md` for the user-facing tour.

The local directory is `wxyc-dj-ios`; the Xcode project, scheme, and Swift module are all `WXYCDJ`; the display name is "WXYC DJ"; the bundle ID is `org.wxyc.dj`.

## Core conventions

- **Swift 6**, strict concurrency, `@Observable` (never `ObservableObject`).
- iOS **18.4+** target. iPhone-only (`TARGETED_DEVICE_FAMILY = 1`).
- SwiftUI throughout; no UIKit unless asked.
- TDD per `wxyc-ios-64/CLAUDE.md`: failing test → minimum implementation → refactor.
- **Do not introduce third-party packages without asking first.** The app uses Foundation, SwiftUI, Security (Keychain), and the local `WXYCAPI` package.

Follows the canonical rules in `../wxyc-ios-64/CLAUDE.md` — read it for SwiftUI idioms (`Task.sleep(for:)`, `foregroundStyle`, `clipShape(.rect(cornerRadius:))`, `Tab` API, `NavigationStack` + `navigationDestination(for:)`, `localizedStandardContains`, etc.). Repeat-rules are not duplicated here.

## Networking layer (`WXYCAPI`)

- `Configuration.swift` → `WXYCAPIConfiguration` (auth + API base URLs, timeout). `.production` and `.localDevelopment` presets.
- `TokenStorage.swift` → `TokenStorage` protocol with `TokenSlot.sessionToken` / `.jwt`.
- `KeychainTokenStorage.swift` → kSecClassGenericPassword, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly. No iCloud sync.
- `InMemoryTokenStorage.swift` → `OSAllocatedUnfairLock`-backed in-memory store for unit tests.
- `JWTPayload.swift` + `JWTDecoder` → client-side parse only; the server validates the signature against JWKS.
- `AuthService.swift` → `@MainActor @Observable`. State: `.unknown` → `.signedOut | .signingIn | .signedIn(payload)` (`Equatable`, so `.onChange(of:)` can observe it). Owns sign-in (`/auth/sign-in/username`, captures the `set-auth-token` response header), JWT exchange (`GET /auth/token`), JWT cache with 60 s leeway, sign-out, and `restoreSession()` for cold launch. `isSignedIn` is the convenience the Spotlight deep-link handler (step 7) reads to decide present-now vs. stash-and-replay.
- `APIClient.swift` → URLSession wrapper. Attaches `Authorization: Bearer <jwt>`; on a 401, calls `authService.invalidateJWT()` and retries once (the shared `perform` transport core returns the `HTTPURLResponse` so callers impose their own status policy — `sendRaw` requires 2xx, `catalog` also accepts 304). Typed methods: `searchLibrary`, `albumInfo`, `albumMetadata`, `getBin`, `addToBin`, `removeFromBin`, and `catalog(ifModifiedSince:)` — the conditional-GET `GET /library/catalog` bulk export (issue #19) returning `CatalogFetchResult` (`.notModified` on a 304, else `.modified(rows:lastModified:)`); the body is gzipped NDJSON (one `CatalogRow` per line, transparently inflated), and the raw `Last-Modified` string is echoed back verbatim as `If-Modified-Since`.
- `JSONCoders.swift` → custom ISO-8601 decoder that handles both fractional-seconds and plain forms (since Backend-Service emits both).
- `RequestSession.swift` → tiny protocol over `URLSession.data(for:)` so tests can inject a `StubRequestSession`.
- `Catalog/CatalogStore.swift` + `Catalog/SQLiteCatalogStore.swift` → the id-keyed on-device catalog clone (issue #19 step 2). `CatalogStore` is a `Sendable` protocol (`row(id:)` O(1) lookup, `count()`, `lastModified()`, `replace(rows:lastModified:)`) so the shared `CatalogRefreshService` (step 4) can be spied. It is now purely the **deep-link read model** plus the **replace target**: issue #36 moved the Spotlight diff index-side (the indexer diffs the in-memory export snapshot against its own persisted fingerprint map), so the issue-#19 store-paging primitives `ids()` (the `SELECT id` diff input) and `rows(after:limit:)` (the keyset bulk read the indexer paged) were removed — they had no remaining callers. `SQLiteCatalogStore` is an `actor` over raw `import SQLite3`: rows are `JSONCoders`-encoded `CatalogRow` BLOBs in `catalog(id INTEGER PRIMARY KEY, row BLOB NOT NULL)`, the verbatim `Last-Modified` watermark lives in a `meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)` row (`NOT NULL` because the store DELETEs the row for a nil watermark rather than storing NULL), and a `200` wholesale-replaces both in one `BEGIN IMMEDIATE` transaction (a duplicate id, or any failure, rolls back and keeps the last-good clone — same fail-closed posture as the NDJSON parser). The C handle is owned by a nested `Connection` class so its `deinit` can `sqlite3_close` (an actor's nonisolated `deinit` can't touch the non-`Sendable` pointer). `CatalogRow.detailFallback` bridges a cloned row to an `AlbumSearchResult` for `AlbumDetailView`'s instant deep-link header (step 7). `AppDependencies` (step 5) opens the production store at `<Application Support>/Catalog/catalog.sqlite` (via the testable `defaultCatalogStoreURL()`), degrading to inert catalog features if it can't.
- `Catalog/CatalogIndexing.swift` + `Catalog/SpotlightCatalogIndexer.swift` + `Catalog/SearchableIndexing.swift` + `Catalog/CatalogSpotlight.swift` + `Catalog/CatalogIndexState.swift` → the **Core Spotlight indexer** (issue #19 step 3; **delta-reindex reshape in issue #36**). `CatalogIndexing` is the `Sendable` seam step 4 drives — `reindex(snapshot:watermark:) -> ReindexSummary` mirrors the **in-memory `[CatalogRow]` export** into `CSSearchableIndex` and `indexedWatermark()` reads the committed watermark back (step 4 sources its poll watermark from *this*, not `store.lastModified()`, so a crash can't strand the store ahead of the index). The reshape: instead of paging the store and re-upserting every row, `SpotlightCatalogIndexer` diffs the snapshot against its **own persisted `id → content-fingerprint` map** (`CatalogIndexState`, committed as Core Spotlight **client state** alongside the watermark) and derives **add** (id absent from the map), **change** (id present, fingerprint differs), **remove** (in the map, absent from the export — so the removed set survives `store.replace` and is reproducible across a mid-reindex crash, fixing issue #36 limitation 1), and **unchanged** (equal fingerprint → skipped, so a typical `200` costs `O(delta)`, fixing limitation 2). The fingerprint (`CatalogSpotlight.fingerprint(for:)`) is a **stable** SHA-256-derived `UInt64` over exactly the fields feeding `searchableItem(for:)` (album/artist/label/call-number components + `artworkURL` for #44) — never `CatalogRow.hashValue`, which Swift salts per process. It upserts `add ∪ change` and deletes `remove`, packing **both** into bounded batches whose combined item count never exceeds 32 767 (`Int16.max`; Core Spotlight rejects a larger single `beginBatch()`/`endBatch(withClientState:)` cycle with `CSIndexErrorDomain -1001`). The watermark advances **only on the final batch**; each batch commits the fingerprint map of work applied **so far** (cumulative, since a batch's `endBatch` durably applies its upserts/deletes) and intermediate batches withhold the watermark (`nil`), so the persisted map stays consistent with the physical index between batches — a crash mid-run leaves the next run able to reconcile a *fresh* export against what the index actually holds (re-deleting a now-vanished id rather than stranding it), not just an unchanged one. `indexedWatermark()` reads only the watermark prefix (`CatalogIndexState.decodeWatermark`) so the cheap conditional-GET path never decodes the whole map. `CatalogIndexState` is a compact little-endian codec (version byte + watermark + sorted `id`/`fingerprint` entries) that decodes an empty/legacy-bare-watermark/truncated blob to `nil` → treated as empty, forcing a from-scratch reindex. The ~1 MB map written through client state is the accepted cost of keeping the watermark + map a single atomically-committed blob (option (a) in the issue); a typical change day is a single batch so the map is written once. It is **gap-free**: the `SearchableIndexing` seam exposes no delete-by-domain, so home-screen search is never emptied mid-reindex. `SearchableIndexing` wraps the four `CSSearchableIndex` batch calls (auto-bridged to `async throws` — no manual continuation needed); the real conformer `RealSearchableIndex` is `@unchecked Sendable` (`CSSearchableIndex` isn't `Sendable` and isn't thread-safe in batch mode, but step 4 drives exactly one sequential reindex). `CatalogSpotlight` owns the `"album.<id>"` ↔ `Int` round-trip (step 7's deep link reuses `albumID(from:)`), the pure `CatalogRow → CSSearchableItem` mapping, and the content fingerprint. CoreSpotlight + CryptoKit import on the package's macOS slice, so this is all host-testable under `swift test` against `FakeSearchableIndex` (a lock-guarded `Sendable` class, **not** an actor; its committed client state decodes back to `CatalogIndexState` for assertions). The live index is a **client-owned named index** (`CatalogSpotlight.indexName = "org.wxyc.dj.catalog"`) — batching and client-state are unsupported on the shared `.default()`; `SpotlightCatalogIndexer(indexName:)` is the convenience that builds `RealSearchableIndex(CSSearchableIndex(name:))`, wired by `AppDependencies` in step 5. **Simulator gotcha (cost us a debugging detour):** Core Spotlight *surfacing* is unreliable on the iOS Simulator — a clean `Catalog refresh: refreshed(rowCount: …)` log there does **not** mean items appear in home-screen search; they frequently never surface on the sim even when correctly indexed. Always confirm home-screen search on a **physical device**. A simulator no-show is not evidence of an indexing bug — check the refresh log for the real outcome (a `-1001` would be a genuine indexing failure; no error + no results = sim flakiness).
- `Catalog/CatalogRefreshService.swift` → the **shared refresh service** (issue #19 step 4): the poll → `304`/`200` → store-replace → Spotlight-reindex flow the foreground path and both background tasks call, so the bulk runs off the main actor and the BGTask layer stays thin. It is an **`actor` that single-flights** overlapping refreshes (a second `refresh()` while one is in flight coalesces onto it via a stored `inFlight` `Task`, cleared by the run's own `defer` so a cancelled caller can't free the slot mid-batch) — because `RealSearchableIndex`'s `@unchecked Sendable` is sound *only* if "step 4 guarantees no overlapping reindex", and so the indexer's fingerprint-map diff can't race a concurrent `replace`. `refresh()` sources the poll watermark from `indexer.indexedWatermark()` (the index's committed client state), **not** `store.lastModified()` — the load-bearing crash-safety invariant: the store is replaced *before* the index commits, so if a crash lands between them the next poll re-fetches and re-indexes instead of `304`-ing past a watermark the index never reached (equivalently, the watermark advances only when `endBatch` succeeds). On a `200` it replaces the store, then hands the **in-memory snapshot** to `indexer.reindex(snapshot:watermark:)` — the indexer derives the add/change/remove delta against its own persisted fingerprint map (issue #36), so the removed set survives the replace and unchanged rows are skipped — returning an `Outcome` (`.upToDate` / `.refreshed(rowCount:upserted:removed:)` / `.skippedEmptyExport`) for logging. An **empty `200` body is skipped** (`.skippedEmptyExport`, no replace, no watermark advance) — a defensive data-safety guard, since an empty export is far likelier a backend hiccup than a real empty catalog and replacing with it would wipe the last-good clone and then `304` forever. Host-tested under `swift test` against a `StubRequestSession` client + `SpyCatalogStore`/`SpyCatalogIndexer` (304 is a no-op; 200 replaces the store then hands the snapshot to the indexer, the spy modelling its own fingerprint map so the recorded delta is faithful; an empty 200 is skipped; a failed reindex leaves the watermark un-advanced and a fresh indexer retries) plus an end-to-end pass over the real `SQLiteCatalogStore` + `SpotlightCatalogIndexer`. `poll()` (step 5) is the cheap conditional probe the background app-refresh leg uses: it returns whether the catalog moved **without** replacing the store or reindexing (so the heavy work defers to a charging-gated processing task). It opens no batch and isn't single-flighted against `refresh()`, but **short-circuits to "no change" when a refresh is already in flight** — that refresh covers the work, and skipping avoids a second index handle reading client state during its open batch (still pays the body download + decode on a `200` though — a body-less probe is a Backend-Service follow-up). The service takes a **`makeIndexer` factory and builds a fresh indexer per `refresh()`/`poll()`** (step 5): `CatalogIndexing`'s contract is that a reindex throwing mid-batch can only be recovered on a freshly-constructed `CSSearchableIndex`, so reusing one for the process would let a single mid-batch failure poison every in-process retry (scene-activation refresh, the background reindex leg) until relaunch — a fresh indexer reads the same persisted client-state watermark and recovers on the next run, and keeps `poll()`'s watermark read off any in-flight reindex's open batch.

When adding a new endpoint, prefer to:
1. Add a typed method on `APIClient` (don't expose raw `sendRaw`).
2. Add a DTO in `Sources/WXYCAPI/DTOs/`. Keep `snake_case` mapping in an explicit `CodingKeys` enum — `convertFromSnakeCase` is intentionally not used because the wire format mixes camelCase paths (e.g. `albumId` in nested types coming from Drizzle) with snake_case top-level.
3. Write tests against `StubRequestSession`. See `APIClientTests.swift` for the pattern.

## UI layer (`WXYCDJ`)

- `AppDependencies` is the composition root. One instance, owned by `AppDelegate` (so the SwiftUI scene and the reindex BGTask handler share the same `CatalogRefreshService` — required for its single-flight no-overlapping-batch guarantee), read via `appDelegate.dependencies` and environment-injected.
- **Catalog refresh wiring (issue #19 step 5).** Foreground-primary, background-best-effort. `WXYCDJApp`'s launch `.task` runs `restoreSession()` then `refreshCatalog()`, and re-runs `refreshCatalog()` on scene `.active`; on scene `.background` it arms the poll. The background split lives in `Catalog/CatalogBackgroundTasks.swift`: `org.wxyc.dj.catalog.refresh` is a `BGAppRefreshTask` registered by SwiftUI's `.backgroundTask(.appRefresh:)` (re-arms, polls, submits the reindex on a `200`); `org.wxyc.dj.catalog.reindex` is a `requiresExternalPower` `BGProcessingTask` registered in `AppDelegate` (SwiftUI has no `.processing` matcher) — the launch handler is non-`Sendable`, so the `task` is bridged into structured concurrency with `nonisolated(unsafe)` (sound because only the work task touches `task`; the expiration block captures only the `Sendable` work task). `setTaskCompleted(success:)` reports `refreshCatalog()`'s **real** outcome (`refreshCatalog()` returns a `Bool`), not whether the work was cancelled. Expiration cancellation is a cooperative signal, not true preemption — the watermark invariant makes an interrupted reindex safe to retry. A missing/expired session is a silent skip + reschedule (pinned by a no-session `CatalogRefreshService` test); the background poll re-arms only when a catalog store exists. Both ids + `UIBackgroundModes` (`fetch`, `processing`) live in `project.yml`'s `info:` block (this target uses a **generated `Info.plist`**, not `GENERATE_INFOPLIST_FILE`, since those keys aren't `INFOPLIST_KEY_*`-expressible); the entitlements file is unchanged (Core Spotlight + BackgroundTasks need none). **Debug a BGTask leg** from a paused debugger with the LLDB SPI `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"org.wxyc.dj.catalog.refresh"]` (or `_simulateExpirationForTaskWithIdentifier:`); the task must already be submitted, and `_simulateLaunch` bypasses the external-power/network gates. See README for the full recipe.
- **Routable navigation (issue #19 step 6).** `AlbumRoute.swift` is the single value pushed onto every album `NavigationStack` path — `struct AlbumRoute: Hashable, Identifiable { let id: Int; var fallback: AlbumSearchResult? }` with `==`/`hash` over **`id` only**. Both `SearchView` and `BinView` carry **one** `.navigationDestination(for: AlbumRoute.self)` hoisted onto their always-mounted `Group` (was nested inside `SearchView`'s `.results` case / `BinView`'s non-empty `default` case — unregistered in idle/empty states, fatal for a programmatic push and a latent lazy-container warning even for the tap). Search rows route `AlbumRoute(id: row.id, fallback: row)` (the live row renders the detail header instantly); Bin rows route `AlbumRoute(id: entry.albumId, fallback: nil)` (no clone, so the detail view awaits `/library/info`). id-only identity is load-bearing: a clone-hit (`fallback`-bearing) and a clone-miss (`fallback: nil`) for the same album coalesce on the path, and `AlbumSearchResult`'s whole-struct `Hashable` (which diverges across cloned vs. live rows on `addDate`/`artworkURL`/`plays`) never fragments it — the property the step-7 deep link relies on. Value semantics pinned in `WXYCDJTests/AlbumRouteTests.swift`.
- **Spotlight deep link + auth replay (issue #19 step 7).** A home-screen Spotlight tap opens the release detail in **its own `fullScreenCover` + `NavigationStack`** over `RootView` (`Detail/DeepLinkAlbumCover.swift`) — never pushed onto the Search/Bin tab stacks, so it can't pollute their nav/scroll state or fabricate a Back target; the cover's "Close" returns the DJ to the exact tab + scroll position. `Router.swift` is a `@MainActor @Observable` two-slot holder (`deepLink: AlbumRoute?` bound to the cover, `pending: Int?` the cold-launch stash) owned by `AppDependencies` and injected via `.environment`. The resolution logic lives on `AppDependencies` (it owns `catalogStore`): `handleSpotlightTap(albumID:isSignedIn:)` presents immediately when signed in (O(1) `catalogStore.row(id:)` lookup → `CatalogRow.detailFallback` for the instant header; a clone miss routes `fallback: nil` and the detail view awaits `/library/info`) or parks the id in `Router.pending` otherwise; `handleAuthChange(wasSignedIn:isSignedIn:)` reconciles the surface on every auth transition — **flip to signed-in** replays a parked id, **genuine sign-out** (`wasSignedIn && !isSignedIn`) tears down via `invalidateDeepLink()` (dismiss the cover + drop the park) so a detail can't strand over `LoginView` issuing 401s, while a **cold-launch `.unknown` → `.signedOut`** keeps the park for a later manual sign-in (which is why it needs the old *and* new flags, via `AuthService.State.isSignedIn`). Presentation funnels through a private `present(albumID:)`: it early-outs when the same album is already shown (skipping a redundant clone read), clears `pending` synchronously (so a fresh tap supersedes a park), and gates the post-`await` `deepLink` write behind a monotonic `presentationToken` — so when a parked replay, a fresh tap, **or a sign-out** race across the clone-lookup suspension, the **most-recently-requested** outcome wins deterministically rather than whichever store read resumes last (a sign-out bumps the token via `invalidateDeepLink`, so an in-flight `present` resuming post-sign-out bows out). **Activity delivery is via a `UIWindowSceneDelegate`, not the view-level `onContinueUserActivity`** — the latter was silently dropping the `CSSearchableItemActionType` activity in **both** cold- and warm-launch states (the original step-7 bug). `SceneDelegate.swift` is attached to SwiftUI's window scene through `AppDelegate.application(_:configurationForConnecting:)` (only `delegateClass` is set — no `sceneClass`/storyboard — so SwiftUI keeps owning the window and hosting `RootView`; verified no black-screen). It catches the tap in the two states the system actually routes through the scene: cold launch via `scene(_:willConnectTo:)`'s `connectionOptions.userActivities` (the launch activity is **not** delivered to `UIApplication`'s `continue` method in a scene-based app), and warm via `scene(_:continue:)`. Both forward to `AppDependencies.handleSpotlightContinuation(_:)`, which parses the activity via `CatalogSpotlight.albumID(fromActivity:)` (the testable seam wrapping the `userInfo[CSSearchableItemActivityIdentifier]` → `"album.<id>"` extraction, pinned in `CatalogSpotlightTests`) and calls `handleSpotlightTap(albumID:isSignedIn:)` with the live auth state. `RootView` still carries `.onContinueUserActivity(CSSearchableItemActionType)` as a **fallback** routed through the same `handleSpotlightContinuation` (a double-delivery is a harmless no-op — `present()` early-outs on the already-shown album, and the `presentationToken` latch collapses a concurrent double-present), kept until the scene-delegate path is confirmed on device. `RootView` wires its remaining two modifiers onto its always-mounted `Group` (so they're live in **every** auth state, incl. the cold-launch spinner): `.onChange(of: auth.state) { old, new in … }` → `handleAuthChange`, and `.fullScreenCover(item: $router.deepLink)`. Both the scene root and the cover inject the app-wide observable trio (`deps` + its `authService` + its `router`) through one `View.wxycAppEnvironment(_:)` helper (`View+AppEnvironment.swift`) — cover content doesn't inherit the presenter's `.environment(_:)` objects, and the single helper keeps the two injection sites from drifting, so the shared `AlbumDetailView` runs under an identical environment on the deep-link and tab-push paths. The signed-in gate is **passed in** to `handleSpotlightTap` (not read off `authService`) so the replay is unit-testable without a real sign-in — `WXYCDJTests/RouterDeepLinkTests.swift` drives an `AppDependencies` over a temp `SQLiteCatalogStore`. The deep link is an in-app `NSUserActivity` continuation, **not** a Universal Link, so it needs no Associated Domains / AASA entitlement.
- View models are `@MainActor @Observable` classes; each view either constructs its VM via `onAppear` (e.g. `SearchView`) or takes one from a parent.
- Views read `AuthService` directly from `@Environment(AuthService.self)` when they need state, e.g. the toolbar sign-out menu.
- Debounce pattern (in `SearchViewModel`): cancel `searchTask` on every query change, then start a new `Task` that `Task.sleep(for: .milliseconds(300))`s and checks `Task.isCancelled` before issuing the request. Don't reach for Combine.

## Tests

Two bundles, both Swift Testing (not XCTest):

- **`WXYCAPITests`** in `Packages/WXYCAPI/Tests/` — networking, DTOs, auth, JWT decoding. Runs via `swift test --package-path Packages/WXYCAPI` on the host (no simulator needed; the package declares both `.iOS(.v18)` and `.macOS(.v14)`).
- **`WXYCDJTests`** in `WXYCDJTests/` — app-target tests for view models and other code that has to `@testable import WXYCDJ`. Runs via `xcodebuild test` against a booted iOS simulator.

Test fixtures use WXYC-representative artists — Juana Molina / DOGA, Jessica Pratt / On Your Own Love Again, Chuquimamani-Condori / Edits. **Do not** introduce mainstream substitutes (Queen, Radiohead, The Beatles); the canonical pool is `wxyc-shared/src/test-utils/wxyc-example-data.json`.

## CI / pre-push checks

GitHub Actions (`.github/workflows/ci.yml`) runs on every PR and push to `main`. The local pre-flight mirrors it — run both commands before opening a PR so CI minutes aren't wasted on red builds:

```bash
swift test --package-path Packages/WXYCAPI

# Pick any booted iPhone simulator; the workflow pre-boots the first available modern iPhone (preferring iPhone 16 Pro).
SIM_ID=$(xcrun simctl list devices available | grep -m1 'iPhone 1[67].*Booted' | grep -oE '\([A-F0-9-]{36}\)' | tr -d '()')
xcodebuild test \
  -project WXYCDJ.xcodeproj \
  -scheme WXYCDJ \
  -destination "platform=iOS Simulator,id=$SIM_ID" \
  -configuration Debug \
  -skip-testing:WXYCDJTests/SpotlightClientStateToleranceTests \
  CODE_SIGNING_ALLOWED=NO
```

`CODE_SIGNING_ALLOWED=NO` keeps the test step from requiring a provisioning profile. The test step needs a real simulator (not `generic/platform=iOS Simulator`) because `WXYCDJTests` is a host-app unit-test bundle.

`-skip-testing:WXYCDJTests/SpotlightClientStateToleranceTests` is required on the **Simulator** (CI and local): the `WXYCDJ` scheme sets `WXYC_SPOTLIGHT_TOLERANCE=1` (in `project.yml`) so a **physical-device** test run picks up the Core Spotlight client-state tolerance probe automatically — but Core Spotlight rejects client-state commits on the Simulator with `CSIndexError -1002`, so that suite can only pass on device and must be skipped anywhere it runs against a Simulator. Run it by targeting a device destination (drop the `-skip-testing` flag).

## Things explicitly out of scope

Don't add these without asking:

- Rotation editing — requires MD/SM role; separate concept from the personal bin.
- Flowsheet, playback, schedule, request line — different apps own those.
- swift-openapi-generator — currently hand-rolled DTOs; the codegen pipeline is a worthwhile follow-up if scope grows.
- PostHog, Sentry, AppleScript hooks — keep the app minimal.

## LML enrichment

The detail view fan-outs two calls: `GET /library/info` (catalog row, source of truth for shelf data) and `GET /proxy/metadata/album` (LML — release year, label, genres, styles, tracklist, streaming URLs, Discogs URL, Wikipedia URL). The `AlbumMetadata` DTO matches the camelCase response shape `proxy.controller.ts` emits. The metadata call is **best-effort**: a 404, decoding failure, or rate-limit is captured via `os_log` under subsystem `org.wxyc.dj`, category `metadata`, and surfaced inline as a faint footer note instead of a red error banner — the catalog row still renders.
