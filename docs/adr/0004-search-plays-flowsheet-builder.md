# Flowsheet-archive search is a distinct iOS mode with a reusable structured filter builder

The iOS app has shipped catalog search since v1 (`/library/search` over library Album rows; see [`api.yaml`](https://github.com/WXYC/wxyc-shared/blob/main/api.yaml)). It does not have a way to search the *play history* — the flowsheet archive that goes back to Nov 2004 and underlies [wxyc.info/playlists/searchPlaylists](http://www.wxyc.info/playlists/searchPlaylists). v2 adds Search Plays as a second, coequal search mode alongside catalog search: same search-bar mental model, different backend, different result-row shape (a flowsheet entry with date / artist / song / release / label / DJ, not a catalog Album), and a station-wide play-count histogram rendered above the results — matching wxyc.info's surface and adding the Apple Health-style scroll model used by [Album Detail histograms (ADR 0003)](./0003-per-album-play-stats.md). Cross-doc context: this is iOS [pick #16](../sequencing.md#phase-5--flowsheet-archive-search--structured-filter-builder) under [ADR 0009 in the cross-repo doc](../cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder).

The backend exposes a new endpoint `POST /flowsheet/search` taking a structured JSON body (filter rows, sort, pagination). The endpoint is POST-with-structured-body because the iOS surface composes filters via a row-based builder UI rather than a query string — accepting the structure directly removes the round-trip through a wxyc.info-style text-syntax parser that iOS doesn't need and that would have to be maintained on both ends. The response always includes `year_counts` and `month_counts` for the matched set so the histogram renders without a second request — payload overhead is trivial (~280 integers max) and the always-on shape mirrors wxyc.info's `yearCounts` field that ships on every search response. When `totalHits > 10000`, the histogram is computed over the top 10k by relevance with a footer note explaining the cap, matching wxyc.info's existing behavior verbatim. Backend tickets: [BS-32](../bs-work-inventory.md#bs-32-post-flowsheetsearch-endpoint-with-structured-body-and-always-included-histogram) (endpoint) and [BS-33](../bs-work-inventory.md#bs-33-document-post-flowsheetsearch-in-wxyc-sharedapiyaml) (OpenAPI documentation).

The Search Plays UI uses a single primary search bar (for the 80% case of "type a name, browse") plus a [Filters] affordance top-right that opens a builder sheet modeled directly on dj-site's [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx): unlimited rows, per-row field selector (Artist / Song / Album / Label / DJ / Date / Date Range), per-row AND/OR/NOT operator between rows, per-row exact-match checkbox for text fields, date pickers for the date fields. Tapping Apply closes the sheet and renders active-filter badges below the search bar — tapping a badge's × removes that condition. Per-DJ scope ("dj:me") is a filter row using the DJ field, not a separate toggle; the default scope is station-wide. Result row tap navigates to Album Detail (the iOS surface that holds Queue actions, condition reports, review, [histogram](./0003-per-album-play-stats.md), and memos) — wxyc.info navigates to show-context because wxyc.info has nothing better; iOS has Album Detail, and that's the destination DJs need to act on a row. Interactive UX prototype comparing the three options that led here: [`docs/prototypes/search-ux-options.html`](../prototypes/search-ux-options.html).

The builder sheet is implemented as a reusable `FilterBuilder` primitive in `WXYCDJ/Sources/Views/FilterBuilder/`, parameterized over a `FieldConfig` (`{ name, type: .text | .date | .dateRange, supportsExactMatch: Bool }`). dj-site's two near-identical builders (catalog [`QueryBuilder.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/catalog/Search/QueryBuilder.tsx) and playlist [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx)) are the cautionary precedent: the same shape implemented twice, diverging slowly, paying duplicated test and evolution costs. Building iOS's once-only, parameterized over the field-config those two consumers would have shared, prevents that drift before it starts. Search Plays consumes the primitive with its own field-config; future surfaces (an eventual advanced catalog filter, an MD review-queue search) compose the primitive with theirs.

## Consequences

- **Two new endpoints, no new schema.** `POST /flowsheet/search` (structured body, returns paginated results + histogram side-channel) is the only net-new endpoint shape; it consumes the existing [`flowsheet_entries`](https://github.com/WXYC/Backend-Service/blob/main/shared/database/src/schema.ts) substrate with the same query infrastructure that backs [ADR 0006](../cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround)'s per-DJ plays and [ADR 0003](./0003-per-album-play-stats.md)'s per-album plays. Pagination is 100 rows per page with cursor-based infinite-scroll, matching the iOS catalog-search pattern already in place.
- **Histogram always included.** Opt-in via `?include=year_counts` was considered and rejected — a client that forgets the flag silently loses the histogram, which is the headline visual feature of the surface. Always-on side-channel adds at most ~280 integers per response, dwarfed by the 100-row pagination payload.
- **60s TTL cache on the endpoint**, keyed on a hash of the filter payload + sort + page. Matches [ADR 0003](./0003-per-album-play-stats.md) and [ADR 0006](../cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround) caching posture: read-heavy, write-light, slightly stale histograms are imperceptible to DJs.
- **Default scope is station-wide.** Searching with no DJ filter row returns all WXYC plays for the query — mirroring [wxyc.info](http://www.wxyc.info/playlists/searchPlaylists)'s mental model. Per-DJ scope is one DJ filter row away (`DJ contains "biscuit"` or `DJ exact "me"`), no segmented toggle. The Search Plays surface answers "what has the station played" by default; per-DJ scope is a one-tap refinement.
- **Result row tap → Album Detail.** A small "view show" chevron sits at the row's right edge for DJs who *do* want the show-context navigation that wxyc.info defaults to — secondary, not primary. Primary tap routes to the iOS surface with the most actionable consequence (Queue, condition, review, memos, [histogram](./0003-per-album-play-stats.md)).
- **No grouping or parentheses in the filter builder.** Matches [dj-site](https://github.com/WXYC/dj-site) — rows evaluate linearly left-to-right with their AND/OR/NOT operators. The expressive ceiling sits below SQL but above wxyc.info's text syntax (which lacks dates entirely); the simplicity is a feature, not a gap.
- **`FilterBuilder` lives in the app target.** Folder `WXYCDJ/Sources/Views/FilterBuilder/`, tests in `WXYCDJTests`. Not a separate SPM package — the cross-app reuse case (e.g., a macOS DJ tool, an admin tool) is hypothetical, and migrating folder-in-app → SPM-target is a folder-move + Package.swift declaration if a real consumer ever appears. [Project CLAUDE.md](../../CLAUDE.md) guidance: "Don't add features, refactor, or introduce abstractions beyond what the task requires."
- **dj-site convergence is a future ADR, not v1.** [dj-site](https://github.com/WXYC/dj-site) keeps [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx) pointing at its current playlist-search backend in v1; the two surfaces operate in parallel. A future consolidation ADR (in dj-site's repo — see [`dj-site/docs/adr/0006-search-plays-flowsheet-builder.md`](https://github.com/WXYC/dj-site/blob/main/docs/adr/0006-search-plays-flowsheet-builder.md)) would migrate dj-site's playlist search onto `POST /flowsheet/search`, retiring its current backend. Flagged in [`docs/bs-work-inventory.md`](../bs-work-inventory.md) as a future BS opportunity, not committed; also surfaces in [sequencing.md's "What's NOT in v1"](../sequencing.md#whats-not-in-v1).
- **The Search Plays surface is a new top-level Tab** in the iOS app, alongside the existing Search (catalog) and Mail Bin tabs. Naming is unambiguous: Search (catalog) and Search Plays. Icons distinct enough that DJs don't mis-tap (e.g., `magnifyingglass` vs `magnifyingglass.circle` or `clock.arrow.circlepath`) — final selection is an implementation detail.
- **Sort defaults to date desc**, with sortable column headers for date / artist / song / release / label / DJ — matches [wxyc.info](http://www.wxyc.info/playlists/searchPlaylists)'s six sort fields. Mobile-friendly column-tap sort is built into the results table; no separate sort sheet.
- **Mirrors needed.** [Backend-Service](https://github.com/WXYC/Backend-Service) gets a mirror ADR for the new endpoint + caching (see [`Backend-Service/docs/adr/0010-search-plays-flowsheet-builder.md`](https://github.com/WXYC/Backend-Service/blob/main/docs/adr/0010-search-plays-flowsheet-builder.md)). [dj-site](https://github.com/WXYC/dj-site) gets a mirror ADR calling out iOS's adoption of [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx)'s shape and flagging the future convergence opportunity for dj-site (see [`dj-site/docs/adr/0006-search-plays-flowsheet-builder.md`](https://github.com/WXYC/dj-site/blob/main/docs/adr/0006-search-plays-flowsheet-builder.md)). No [semantic-index](https://github.com/WXYC/semantic-index), [LML](https://github.com/WXYC/library-metadata-lookup), or [wxyc-shared](https://github.com/WXYC/wxyc-shared) mirrors required beyond [api.yaml](https://github.com/WXYC/wxyc-shared/blob/main/api.yaml) documentation owned by BS.
- **Reversibility.** Decision is mostly reversible — pull the endpoint, retire the Search Plays Tab, and the app returns to v1 shape. The `FilterBuilder` primitive is retained as dead code or deleted with the Tab; either way, no migration cost. The 22-year flowsheet archive from BS is not generated by us — it's read-only over existing data.
- **Verification needed before shipping.** Builder-sheet UX with multi-condition, AND/OR/NOT, date-range, and exact-match exercised on a staging dataset. Histogram cap (top-10k-by-relevance footer) triggered on at least one broad query (`"rock"`, `"the"`) and one narrow query (a specific obscure artist). Result-row tap landing on the correct Album Detail (`album_id` round-trip through the flowsheet entry).
