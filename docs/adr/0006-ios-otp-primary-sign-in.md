# The iOS app leads sign-in with a mailed one-time code

WXYC DJs already sign in to dj.wxyc.org with a 6-digit code emailed to them, and the site nudges toward it — `UserPasswordForm` calls `savePreferredLoginMethod("otp-email")` on its way to the code form. The iOS app offered only a password, so a DJ whose habit is "ask for a code" had to remember a credential they may use nowhere else. Every WXYC account is provisioned by a Music Director rather than self-registered, so the password is frequently one someone else chose and the DJ has never typed twice.

Decision: the app's login screen **leads with the code** — one identifier field and "Send login code" — and keeps the password form behind "Sign in with password instead". Both credentials remain fully supported; only the default changes.

Mechanism: better-auth's [`emailOTP` plugin](https://www.better-auth.com/docs/plugins/email-otp), already live in Backend-Service (`otpLength: 6`, `expiresIn: 300`, `allowedAttempts: 5`, `disableSignUp: true`). Three calls: `POST /auth/wxyc/lookup-email` resolves a username to its address (skipped when the identifier already contains an `@`, because the resolver echoes such an identifier back unchanged), `POST /auth/email-otp/send-verification-otp` mails the code, and `POST /auth/sign-in/email-otp` redeems it. That last route is a peer of the two password routes — same `setSessionCookie`, and `bearer()` is a global plugin — so it issues the same `set-auth-token` header the app already reads. Tracking: [#100](https://github.com/WXYC/wxyc-dj-ios/issues/100).

## Consequences

- **A code is a third credential onto an unchanged client session lifecycle.** The `set-auth-token` capture, the `/auth/token` JWT exchange, the [#53](https://github.com/WXYC/wxyc-dj-ios/issues/53)/[#66](https://github.com/WXYC/wxyc-dj-ios/issues/66) transient/terminal state machine, Keychain persistence, and [#52](https://github.com/WXYC/wxyc-dj-ios/issues/52)'s leave-no-trace contract are all reused. `AuthService` shares both halves — `completeSignIn(establishing:)` for the orchestration, `establishSession(path:body:rejectionCopy:)` for the wire — so a second credential cannot restate one of those invariants incorrectly.
- **On the server it is *not* merely another credential: OTP sign-in mutates account state.** Backend-Service sets `requireEmailVerification: true`, so an unverified account is refused at password sign-in with `403 EMAIL_NOT_VERIFIED`. `signInEmailOTP` instead calls `revokeUnprovenAccountAccess(…)` and then `updateUser(…, { emailVerified: true })`, permanently flipping the flag. This is accepted rather than worked around: possession of the mailbox is precisely the proof the verification email would have demanded, so treating a redeemed code as verification is sound. It does mean a newly provisioned DJ who never clicked their verification link can bootstrap through the code path — which is a feature for the 50th-anniversary-era roster churn, not a bypass, but it is a real behavioral difference between the two credentials and should not be discovered by accident.
- **A looked-up email address is never displayed.** `POST /auth/wxyc/lookup-email` is what Backend-Service's own source calls "a mild enumeration vector", accepted because it is rate-limited and no worse than `/auth/sign-in/username`'s existing leak. Rendering its answer would promote a vector bounded by request rate into one visible to anyone holding the unlocked phone. The code screen therefore shows the identifier only when the DJ typed an email, and "your registered email" otherwise — the same line dj-site draws in `LoginFormSwitcher.tsx`. `LoginCodeDestination` carries the two strings separately so the view cannot render the wrong one.
- **A mistyped email cannot be reported where the mistake happens.** `disableSignUp: true` makes the send step answer `{success: true}` for an unknown address and the verify step answer `INVALID_OTP` indistinguishably from a wrong code. Only the *username* path can say "no account matches". Mitigated by naming the destination on the code screen and offering "Use a different account"; not solvable client-side, and not worth asking Backend-Service to weaken the anti-enumeration posture for.
- **Rate limits are per-IP and the control room shares one.** `rateLimitKeyFromRequest` keys on `X-Real-IP` at 10 requests per 15 minutes, and a full code sign-in spends three of that bucket (lookup + send + verify) where a password spends one. better-auth adds 3-per-60s on both the send and verify routes. The app gates resend behind a 30-second cooldown and renders a 429 as `AuthError.rateLimited` ("Too many attempts. Wait a few minutes and try again.") rather than "Server error (429)". If shift-change lockouts appear in practice, the follow-up is asking Backend-Service for a per-identifier key on these three paths — not raising the ceiling.
- **This supersedes ADR 0002's bootstrap assumption.** [`0002-qr-device-authorization-shared-computer-signin.md`](./0002-qr-device-authorization-shared-computer-signin.md) states "First-time iOS sign-in remains username/password against `/auth/sign-in/username`". That was already half-false once [#97](https://github.com/WXYC/wxyc-dj-ios/issues/97) added the email route, and is fully false now. QR sign-in's actual dependency is unaffected: it needs the phone to be *already signed in*, and is indifferent to which credential got it there.
- **Preferred-method memory is deferred.** dj-site persists the DJ's last choice (`savePreferredLoginMethod`); the app always opens on the code path. Shipping persistence now would guess at a preference no one has expressed on this surface. Revisit if DJs report repeatedly tapping through to the password form.
- **Reversible at low cost.** Swapping which stage `LoginViewModel` starts in restores the password-first screen; no server change, no schema, no stored state. The cost of reverting grows only with habit.
- **Verification needed before shipping.** End-to-end on a physical device against a real mailbox: a username sign-in, an email sign-in, an expired code (wait past 5 minutes), a wrong code, and a resend. Testing against production trips the per-IP limiter quickly — use `localDevelopment`, where the Express limiters are disabled, for everything except one final production pass.
