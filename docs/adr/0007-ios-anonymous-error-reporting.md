# iOS reports errors with a hard anonymity floor, enforced by construction

The app had no crash or error reporting at all. Every failure was written to `os_log` under subsystem `org.wxyc.dj` and otherwise swallowed at a documented degradation site — a Core Spotlight `-1001` batch rejection, a SQLite store that won't open (catalog and bin features silently go inert), a systematic decode failure against a changed Backend-Service payload. None of those surface anything to the DJ, which is the point of the degradation, and it is also why we only ever learned about one by a DJ mentioning it in passing. Instrumenting for errors is the obvious fix; the complication is who the users are.

`wxyc-ios-64`'s listeners are anonymous — they never sign in, and the app holds nothing about them. **DJ-app users are signed in with real identities**: a username, an email address, a DJ id, a JWT whose payload carries all three, and free text they type into library search. Every one of those is within arm's reach of a crash reporter's default behavior. "Add Sentry" with the listener app's option set would therefore ship materially more about a much smaller, individually-identifiable population, so this app's posture has to be strictly tighter than the reference implementation it otherwise borrows from.

Decision: **instrument with [sentry-cocoa](https://github.com/getsentry/sentry-cocoa) for error reporting only, under a privacy contract enforced by the type system and a scrub pipeline rather than by review convention.** The contract's items are each backed by a mechanism that makes the violating code fail to compile, or that strips the value before it can leave the device — not by a comment asking the next contributor to be careful. Implementation is tracked in [#106](https://github.com/WXYC/wxyc-dj-ios/issues/106); the instrumentation lives in [`WXYCDJ/Telemetry/`](../../WXYCDJ/Telemetry/), and `WXYCAPI`/`WXYCAPIModels` stay SDK-free so they remain host-testable under `swift test`.

## What is never collected, and what makes each hold

- **No identity.** `SentrySDK.setUser(…)` is called nowhere; no username, email, DJ id, or `JWTPayload` field reaches any event, tag, breadcrumb, or context. The mechanism is the shape of the seam: [`ErrorReporter.report(_:context:extra:)`](../../WXYCDJ/Telemetry/ErrorReporting.swift) takes its `context` as a **`StaticString`**, which can only be spelled as a source literal, so `context: "signIn for \(username)"` is a compile error rather than something a reviewer has to notice. `extra` is `[String: TelemetryValue]`, and `TelemetryValue` has **no free-text case** — `.int`, `.bool`, `.string(StaticString)`, `.errorIdentity(domain:code:)` — so `extra: ["query": typedText]` doesn't type-check either. A capture site is simply not able to spell an identity.
- **No search query text.** Whatever a DJ types stays on the device. The channel that made this non-trivial is not the capture sites (none of them touch the query) but the URLs that carry it, covered below.
- **No request URLs with query strings.** `GET /library/search?artist=<typed text>` is the DJ's search box on the wire. [`URLScrubbing`](../../Packages/WXYCAPI/Sources/WXYCAPI/URLScrubbing.swift) strips the query and fragment while keeping scheme, host, and path — knowing that a request to `/library/search` failed is the diagnostic; knowing what was typed into it is not — and [`TelemetryPrivacyScrub`](../../WXYCDJ/Telemetry/TelemetryPrivacyScrub.swift) applies it through `beforeBreadcrumb` (every breadcrumb `message` and `data`) and again through `beforeSend` (the event's `request.url`, its breadcrumbs, every `contexts` value, and every exception's `value` / `mechanism.desc` / `mechanism.data`). The second pass is deliberate defense in depth: `beforeBreadcrumb` is the only *intended* path into the buffer, but re-scrubbing at send time means a breadcrumb added by a future SDK-internal integration still can't ship a query string.
- **No server-sent message text.** `AuthError.rejected(message:)`, `AuthError.serverFailure(status:message:)`, and `APIError.http(status:message:)` all carry copy the server authored. Each enum gained a `caseName` mapping that yields only the case name plus, where it exists, the HTTP status as an `Int` — and, for `APIError` alone, `.decoding(detail:)`'s narrowed detail string (see the deliberate-exception consequence below; every other case's `detail` is `nil`). Both mappings are **exhaustive switches with no `default:`**, so adding a message-bearing case to either enum is a compile-time decision about whether its payload is reportable, not a silent gap. Crucially, the mapping alone would not be enough — see the first leak channel below.
- **No session replay, screenshots, or view hierarchy**, and **no IP retention**: `sendDefaultPii = false`, `attachScreenshot = false`, `attachViewHierarchy = false`, both session-replay sample rates `0`. All six are set explicitly in [`TelemetryBootstrap`](../../WXYCDJ/Telemetry/TelemetryBootstrap.swift) even where they match today's SDK defaults, so a future SDK version flipping a default can't widen collection without this file changing too.
- **No performance tracing** (`tracesSampleRate = 0`, a deliberate departure from the listener app's `0.05`) and **no automatic failed-request capture** (`enableCaptureFailedRequests = false`). Tracing adds a URL-carrying span surface for a benefit nobody asked for, and this app *by design* fails requests and falls back to the on-device clone ([#58](https://github.com/WXYC/wxyc-dj-ios/issues/58)/[#81](https://github.com/WXYC/wxyc-dj-ios/issues/81)), so auto-capture would turn expected offline behavior into event spam.

## The three leak channels this design actually exists to close

None of these is visible from the SDK's documentation, and each one defeats the naive implementation — configure the options, map the enum, ship it.

- **`SentrySDK.capture(error:)` builds the event's headline text from `String(describing: error)`.** For a bridged Swift error, sentry-cocoa renders `exception.value` and `mechanism.desc` from exactly that description — so handing it a raw `AuthError.rejected(message: "<server copy>")` ships the copy verbatim in the field a human reads first, no matter how careful the `caseName` mapping elsewhere is. This is why the mapping alone is insufficient and why `SentryErrorReporter` never captures the original error: [`TelemetryErrorClassification.curated(_:)`](../../WXYCDJ/Telemetry/ErrorReporting.swift) replaces an `AuthError`/`APIError` with a **curated `NSError`** — a controlled domain, a deterministic FNV-1a code derived from the case name (never `String.hashValue`, which Swift salts per process and would re-bucket every Sentry issue on each launch), and a `userInfo` allowlisted to `caseName` plus the status. `URLError` alone passes through raw, because its domain/code bridge is precisely what makes a transport failure readable at a glance.
- **Raw `NSError.userInfo` is copied wholesale into the event.** sentry-cocoa copies it into both `contexts["user info"]` and `exception.mechanism.data`. A `URLError` from `URLSession` carries `NSErrorFailingURLStringErrorKey` and `NSURLErrorKey` — the full request URL, query string included. And the resource-class `URLError`s are exactly the ones this app *does* report, so this is the common case, not the exotic one. The `beforeSend` walk recurses through both payloads and scrubs every URL-bearing value it finds, at whatever nesting depth — including a nested `NSError`, which the walk didn't originally descend into: `NSUnderlyingErrorKey` is a routine `URLError.userInfo` key carrying exactly that shape, and Foundation's default `NSError.description` (the very channel the next bullet closes) would otherwise render that nested error's own `userInfo` inline, unscrubbed, one level down.
- **`NSError.description` renders the entire `userInfo` dictionary inline as free text.** Combine that with the first channel and a query-carrying URL appears inside `exception.value` as a **substring** of a much longer string — `… UserInfo={NSErrorFailingURLStringKey=https://…/library/search?artist=…, …}` — never as the whole field. `URLScrubbing.scrub(_:String)` is deliberately conservative and only touches a value that parses as a URL *in its entirety*, which is right for a structured leaf and useless here. `TelemetryPrivacyScrub.scrubEmbeddedURLs(in:)` therefore scans with `NSDataDetector` — the same detector iOS uses to find tappable links — and rewrites each detected URL in place, leaving every character outside a match alone. It is a strict generalization of the whole-string case, not a competing code path.

## Consequences

- **One deliberate exception is carried, and it was narrowed to make it honest.** `APIError.decoding(detail:)`'s detail *is* reported — carried explicitly through `APIError.CaseName.detail`, `nil` on every other case — because a systematic decode failure in the field is the single most valuable diagnostic for the exact defect class this whole effort exists to surface, and a bare case name would tell us nothing about which field broke. The exception only holds because `APIClient.describe(_:)` was first narrowed to **code-derived facts alone**: the `DecodingError` case kind, the coding-key path, and — on `.typeMismatch`/`.valueNotFound` — the expected `Any.Type` Foundation itself supplies (e.g. `Int.self`), which is derived from the *model's* declared property type, never from the payload bytes, and so restores most of what the next paragraph's drop cost without reopening it. `Context.debugDescription` was dropped entirely, and it was never incidental noise — `JSONCoders`'s custom date strategy builds one as `"Unrecognized date format: \(raw)"`, where `raw` is untouched wire content, and the pre-#106 formatter interpolated it into every `.typeMismatch` and `.dataCorrupted` arm. The `@unknown default:` arm was also made a **constant** rather than `String(describing: error)`, because `String(describing:)` on a `DecodingError` re-embeds that same `debugDescription` — reopening the channel through the one branch no test can construct to catch it. These two facts are load-bearing on each other: `CaseName.detail` is safe to carry only because `describe(_:)`'s own regression tests (`APIClientTests`) prove the formatter can emit nothing but case kind, coding path, and expected type; a future edit that restores `debugDescription` fails that suite, and would silently turn this exception back into a loophole if the suite were ever weakened alongside it.
- **Being offline is not a defect, and both package error enums now say so in the type.** `AuthService` used to flatten every non-`AuthError` throw into `AuthError.network(message:)`, conflating "the DJ is on a train" — a fully supported mode with an on-device catalog clone behind it — with a genuine transport defect worth waking someone for. Both flatten sites now classify through `ConnectivityErrorClassification` (factored out of `ArtworkFailureClassification` so the connectivity-code list has one home, not two copies free to drift) into `.offline(message:)` versus `.network(message:)`. **`APIClient` needed the identical split and didn't have it at review time** (`APIError.offline(message:)`, added in review as `AuthError.offline`'s peer): `fire(_:)`'s catch-all — including its pre-existing cancellation carve-out, which still skips the `ConnectivityMonitor` outcome hook but now throws `.offline` rather than `.network`, since a debounced search or a DJ backing out of a detail screen mid-request is exactly the non-defect this split exists to name — and, one layer below it, `currentJWT()`'s catch-all, because `AuthService.currentJWT()` rethrows a raw, unwrapped transport error (not an `AuthError`) when its own lazy JWT-refresh leg fails offline. Every capture site downstream was taught to skip `.offline` alongside the pre-existing `.notSignedIn` skip: `AppDependencies.refreshCatalog()`/`.handleBackgroundPoll()`, `BinViewModel.refresh()`, and `AlbumDetailView.loadInfo()` (which also — necessarily, since the two legs must not disagree about what "supported mode" means — reconciled with `loadMetadata()`'s existing offline carve-out; see the total-switch consequence below). The two "Non-HTTP response" throws in each package deliberately stay `.network`: a response reaching the HTTP layer without a status code is a bug, not evidence of being offline. `localizedMessage` renders `.offline`/`.network` identically in both enums, so nothing on screen changed — only which case a capture site pattern-matches on.
- **The report-versus-skip decision is a total switch at every capture site.** `LoginViewModel.shouldReport(_:)` and `AlbumDetailView.shouldReportMetadataFailure(_:)` are exhaustive with no `default:`, for the same reason the `caseName` mappings are: a new error case is a decision someone has to make at the keyboard, not a silent inclusion or a silent miss. The rule they encode is consistent — an expected user outcome (wrong password, rate limit, a reason the server named, being offline, an LML 404) stays `os_log`-only; a broken contract or a broken parse gets reported. `loadInfo()`/`loadMetadata()` were reconciled to agree on `.offline` (never reported by either) while still legitimately differing on `.http` (routine LML noise vs. a fatal shelf-data failure), and `loadMetadata()`'s `.network` flipped from skipped to reported now that `.offline` — not `.network` — carries the "probably just a dead connection" meaning. One outcome has no `AuthError`/`APIError` case to switch on at all: a *transient* JWT-exchange failure right after a successful sign-in leg lands `AuthService.state` in the issue-#53 pending window (`.signedIn(payload: nil)`) without ever touching `lastError`, so `LoginViewModel.shouldReport(_:)` has nothing to see. `submit()`/`submitCode()` additionally check `auth.state` after the leg settles and report that window under its own context (`"LoginViewModel.pendingJWT"`) — no package change, since the pending window was already public and already documented.
- **Debug builds report, filed under `environment: development`.** They are not silenced. Simulator and Xcode-run traffic under a default (unset) `environment` would file as `production` and pollute real triage, so `BuildEnvironment` classifies three cases — `development` via `#if DEBUG`, `testflight` via the sandbox receipt file name, `production` otherwise. This is a deliberate accepted cost: developer noise is visible and filterable, whereas a `#if DEBUG`-silenced SDK is one whose scrub pipeline nobody exercises until it matters.
- **Sentry's anonymous installation id feeds release-health session counts, and with a DJ population this small that is pseudonymous, not anonymous.** `enableAutoSessionTracking = true` means the SDK attributes sessions to a per-install identifier it generates itself. It contains nothing we put there and is not linkable to a WXYC account by anything on the wire — but with dozens of active DJs rather than millions of listeners, a per-install identifier plus a timestamp is not a large crowd to hide in. Stated plainly rather than buried: the contract is "we never send who you are," not "correlation is mathematically impossible."
- **The deferred QR-auth structured events must not be built client-side as specified.** [ADR 0002](./0002-qr-device-authorization-shared-computer-signin.md) (cross-repo ADR 0007) defers `auth.qr.approved` / `auth.qr.rejected` events **tagged with phone IP/UA and browser IP/UA**, and that deferral is echoed in [`cross-repo-adrs.md`](../cross-repo-adrs.md) and [`sequencing.md`](../sequencing.md). Emitting those from this app would violate this ADR's no-IP-retention item directly — `sendDefaultPii = false` suppresses the IP Sentry would infer, and hand-attaching one as a tag routes around the entire contract. This is written down because the deferral is live and the next person to pick it up will otherwise read "structured Sentry events" and reach for the SDK that is now conveniently already linked. If richer QR forensics are ever needed, they belong to Backend-Service, which is the party that legitimately observes both IPs; the phone is not.
- **App Privacy: Crash Data, "not linked to identity," no tracking.** That is what the contract above buys and what the App Store label declares. Both SDKs ship `PrivacyInfo.xcprivacy` manifests that Xcode aggregates into the app's privacy report automatically, so the declaration is derived from what is actually linked rather than maintained by hand. Any future change that would make the "not linked" claim false — an identity call, a free-text field, a re-enabled `sendDefaultPii` — is a label change, not just a code change.
- **The package boundary is load-bearing and stays where it is.** `WXYCAPI` and `WXYCAPIModels` are pure Foundation and host-testable via `swift test`; linking an SDK into either would break that and invert the layering. So `URLScrubbing` (the pure judgment) lives in the package while every SDK-touching line lives in the app layer, and only `SentryErrorReporter.swift` imports `Sentry` at all — the rest of `Telemetry/` is Foundation-only, which is what lets `WXYCDJTests` exercise the scrub, the classification, and the build-environment table through `@testable import WXYCDJ` without linking sentry-cocoa into the test bundle (statically linking a largely-ObjC SDK into both a host app and its loaded test bundle invites duplicate class registration and two competing singletons). The one end-to-end assertion that must go through the real started SDK reaches it via a single `#if DEBUG` hook returning a plain `[String: Any]`, and asserts on **every string leaf** in the serialized event rather than a handful of anticipated field paths.
- **Reversibility is high and the cost of getting it wrong is not.** Pulling the SDK removes one package dependency, one directory, and a dozen `report(…)` calls; nothing else depends on it. But the asymmetry matters more than the reversibility: an over-collected event cannot be un-sent, so every judgment here fails closed — an unrecognized error type is curated rather than trusted, an unrecognized `DecodingError` case yields a constant rather than a description, and a value that might be a URL is scrubbed rather than assumed prose.
- **Two follow-ups were chained, and both have now shipped.** [#107](https://github.com/WXYC/wxyc-dj-ios/issues/107) uploads dSYMs so Release events symbolicate — before it landed, Release stack traces arrived as raw addresses, which is also why `beforeSend` does no client-side fingerprinting (the listener app measured client fingerprints degenerating to a single bucket on unsymbolicated frames). [#108](https://github.com/WXYC/wxyc-dj-ios/issues/108) added PostHog product analytics on top of this PR's `Telemetry/` group and injection points; its privacy contract is an **extension** of this one, not a separate negotiation — `personProfiles = .never` (never `.identifiedOnly`, whose anonymity guarantee turned out to rest on a sticky, persisted flag several call paths could flip), no `identify(...)` call anywhere, and a `beforeSend`-wired property allowlist as the runtime backstop behind a typed `AnalyticsEvent` catalog that admits only numbers, booleans, and closed-enum strings. See `WXYCDJ/Telemetry/Analytics.swift`/`AnalyticsEvents.swift` and CLAUDE.md's Telemetry section for the full mechanism. **The PostHog project itself does not exist yet** (the WXYC org's free-tier project limit blocks creating it until a dormant project is deleted, which needs a human in the PostHog web UI), so `TelemetryBootstrap.startAnalytics()` is gated on a real project token replacing a checked-in placeholder — the code is complete and tested, but ships analytics-inert until that token lands.
- **Verification needed before shipping.** The DSN in `TelemetryBootstrap.productionDSN` points at the `wxyc-dj-ios` project in org `wxyc`, so events have a real destination — but a green test suite proves the scrub pipeline is correct in the shapes we anticipated, not that the SDK produces only those shapes. Before this reaches TestFlight, confirm on a physical device that a forced error arrives in the right `environment`, that its `exception.value` carries a case name rather than server copy, and that a deliberately-failed search request leaves no `?` anywhere in the event. The last of those is the one worth doing by hand against a real event in the Sentry UI rather than trusting the suite: the failure mode this ADR exists to prevent is a field we did not think to assert on.
