# Digital-archive playback lives in the app layer, over a PlaybackEngine seam, and reuses only what has no cheaper alternative

The auto DJ's music library — every rotation release plus a ~2,300-album freeform collection, ~23.5k MP3s — sits in a DigitalOcean Space that AzuraCast already streams from for on-air playout. A DJ signed into `wxyc-dj-ios` currently has no way to hear any of it; the plan in `plans/digital-archive/auto-dj-archive-player.md` (§6) makes this app the first consumer of that library, behind a signed, time-limited playback manifest Backend-Service serves and a kill switch. This ADR covers only the `wxyc-dj-ios` side. It was written for the part landing with issue #137's PR — [`AudioSessionCoordinator`](../../WXYCDJ/Playback/AudioSessionCoordinator.swift) — and has since been amended by issue #144, which added the [`PlaybackEngine`](../../WXYCDJ/Playback/PlaybackEngine.swift) seam and [`PlaybackController`](../../WXYCDJ/Playback/PlaybackController.swift). The work was split three ways after #137 shipped: issue #138 carries the two credited system-integration ports plus the background mode, **issue #144** the seam and controller, and **issue #145** the `AVQueuePlayer` adapter and the two UI surfaces. Every "issue #138" this document used to write for the player itself now means #144 or #145; the amendments below say which.

## Decision

**Playback lives in `WXYCDJ/Playback/`, an app-layer module, behind a `PlaybackEngine` seam — not as a dependency on `wxyc-ios-64`'s playback package.** `AVQueuePlayer` (via an `AVQueuePlayerEngine` conformer, issue #145) is the only file importing AVFoundation for actual playback; on the session-management side it is imported by `AudioSessionCoordinator` and by [`AudioSessionProtocol`](../../WXYCDJ/Playback/AudioSessionProtocol.swift), the seam it activates through — the protocol's method signatures are spelled in `AVAudioSession.Category` / `.Mode` / `.RouteSharingPolicy` / `.SetActiveOptions`, so it cannot avoid the import, and `AVAudioSession` conforms to it there. `WXYCAPI` and `WXYCAPIModels` stay untouched by any of this — playback needs one new DTO and one typed `APIClient` method, not a package dependency.

**Why not depend on `wxyc-ios-64`'s `Shared/Playback` package.** Three reasons, all structural rather than incidental:

- It houses **three experimental playback engines** selected by a PostHog flag — `docs/architecture.md` there states plainly that this is temporary ("Houses several playback engines. Eventually this will whittle down to 1 or 2, but is currently in an experimental phase"). Depending on it would import that selection machinery, and its resolution, into an app that needs exactly one engine for one MVP.
- It carries **CPU aggregation and visualizer render taps** for the listener app's now-playing screen. This app has no visualizer and no use for per-engine CPU telemetry.
- The audio-session behaviour this app *does* need is not a separable unit there — it is ~550 lines interleaved inside a 2,693-line `AudioPlayerController` alongside all of the above, plus background-task assertions for a handback path this MVP doesn't need to protect with a `beginBackgroundTask` grant. There is no `AudioSessionCoordinator` file to add as a dependency; extracting the three behaviours into a new, small file was the only option that didn't also import the engine selector, the CPU aggregator, and the render taps.

**What was extracted, not ported, and what was left behind.** `AudioSessionCoordinator` (~475 lines, half of them comments recording why each guard is there) carries exactly three behaviours out of `AudioPlayerController.swift` (`c22a3eb`), each traceable to a specific field failure rather than invented for this app:

1. The category is configured lazily, on the first `activate()`, never in `init` — configuring at init would interrupt whatever else is already playing when the app launches. `.default` route-sharing policy, not the source's `.longFormAudio`: this app plays short-form music, not the long-form content that policy is for.
2. Activation distinguishes a `CannotInterruptOthers` failure (another app holds the session — bounded retry, four attempts over one second) from this coordinator's *own* in-flight deactivation (an event-driven resume instead, because the handback measures ~1s on device and would exhaust the bounded budget before finishing, wxyc-ios-64#514). Both re-drive paths, plus the scheduling of the bounded retry itself, are gated on the caller's standing intent — the source's `playbackIntended` (~1128, ~1149, ~1452), tracked here as an `activationIntended` flag `activate()` sets and `deactivate()` clears, since this coordinator owns no player to read the intent off.
3. Deactivation runs off the main actor under a generation counter, because `setActive(false, …)` is a synchronous ~1s XPC round trip to `mediaserverd` and running it on the caller's turn would freeze whatever UI is waiting on that turn. A second `deactivate()` inside that window is coalesced rather than stacked (source ~1300-1310, drained at ~1505-1510), and the attempt's outcome is carried back out of `sessionLock` before it is logged (~1585), so the logging never happens while the main actor may be waiting on that lock.

Left behind, deliberately: engine selection, CPU/session aggregation, render taps, the watchOS `RadioPlayerController`, and the background-task assertion `AudioPlayerController` takes around its handback (`beginHandbackAssertion`/`endAllHandbackAssertions`) — that assertion exists to protect a pause that arrives right as the app backgrounds, a scenario this MVP's UI doesn't create pressure on yet; it can be added to `AudioSessionCoordinator` later without touching the three behaviours above if a background-pause defect ever surfaces here. Left behind with it, for the same "this coordinator owns no player and no app-lifecycle state" reason: the `isForegrounded` half of the source's re-drive gating, the on-the-caller's-turn handback it performs when the app backgrounds (`deactivateAudioSessionOnCallersTurn`), the silent-startup escalation a post-handback hard failure triggers there, and the `ActivationRetryCause` labelling that distinguishes three diagnoses this coordinator can only reach one of.

**Three guards are *not* left behind, and an earlier revision of this ADR implied they were by describing the three behaviours without them.** Each was restored under review of the PR that introduced this file, because each is load-bearing rather than incidental: the intent gate above (without it, a `deactivate()` issued while an activation is deferred does nothing at all, and the deferral then stands a `.playback` session up moments after the caller asked for release — the `isActivated` guard returns early on exactly the state a deferral leaves behind), the in-flight coalescing (without it, `isActivated` is the only guard, and it is cleared ~1s later in the continuation — so a second `deactivate()` inside that window queues a second detached task that blocks a cooperative-pool thread on `sessionLock` for the rest of the handback, then passes its own generation check, since only an *activation* bumps the generation, and re-fans the resume notification to every other audio app), and the failure logging (a failed handback is a pure silent degrade — nothing on screen marks it, and `isActivated` deliberately stays set so a later call retries, so without a log line even a persistent failure is invisible). The one thing the source had here that this file did not, until issue #144, was an `ErrorReporter.report` beside that log — see **Amendment 2** below for why the injection point turned out to be this file after all. No public resume method, no closure parameter on `activate()`, no `AsyncStream` on the seam: the handback resume is `AudioSessionCoordinator`'s own business, finished inline by `resumeDeferredActivationAfterHandback()` once the deactivation's generation check has run. `PlaybackController` (issue #144) calls `activate()`/`deactivate()` and nothing else — it never orchestrates the handback. **Amendment 1** below adds one read-only observation point to that surface and explains why it is not the same thing.

**Two files are file-level ports, not extractions, and issue #138 carries them (unchanged by the split):** `PlaybackInterruptionRouteHandler.swift` (194 lines) and `NowPlayingInfoCenterManager.swift` (149 lines, deliberately never reading `MPNowPlayingInfoCenter.nowPlayingInfo` back — a synchronous XPC hang the source already discovered and fixed). Both are small, self-contained, and copied with credit in their headers rather than re-derived, because unlike the audio-session behaviour they are not interleaved with anything this app doesn't want.

**The presigned playback URL is a credential, not a resource identifier — extends [ADR 0007](0007-ios-anonymous-error-reporting.md).** ADR 0007's contract is a hard anonymity floor enforced by construction: no identity, no search-query text, no server-message text, no request URLs with query strings reach a Sentry event. A digital-archive manifest URL is a new instance of exactly the value class `URLScrubbing` and `TelemetryPrivacyScrub` already exist to strip — a presigned S3-style GET with the signature living in the query string — so it needs no new mechanism, only the existing one applied to a new call site: never `os_log`ged, and `SentryPrivacyPipelineTests` gets a case (issue #139) asserting a presigned URL's signature never reaches a serialized event. This app still runs `tracesSampleRate = 0`; issue #139's cue→first-frame timing rides an analytics event property instead of a Sentry span, for the same reason ADR 0007 gives for having no tracing at all.

**The digital-audio badge rides the on-device catalog clone — extends [ADR 0005](0005-ios-spotlight-on-device-catalog-clone.md).** ADR 0005 already clones the catalog for Spotlight search and keeps it as the offline-search and deep-link fallback source. `has_digital_audio` (issue #136) is one more optional `CatalogRow` field read off that same clone — offline-capable for free, and excluded from `CatalogSpotlight.fingerprint(for:)` and `searchableItem(for:)` since it is not searchable text and would otherwise force a reindex of every newly-bound album. The manifest fetch itself (`GET /digital-archive/albums/{id}/playback`) is the source of truth for whether audio is actually playable *right now*; the badge is only ever a hint that a manifest fetch is worth trying, exactly as the rest of this app treats the clone as a hint that degrades gracefully against a live 404.

**No downloads in the MVP.** Every track streams from its presigned URL each time; nothing is cached to disk beyond the ordinary `URLCache`/`AVPlayer` buffering that streaming already implies. Offline playback — a client-side cache keyed on `file_id`, validated by `content_hash`, downloaded via `URLSession` into the app container under Data Protection — is designed for in the manifest contract (`file_id`, `content_hash` are present from day one) but explicitly out of scope until the counsel question about on-device copies of these files is resolved. `AVAssetDownloadTask` is HLS-only and unavailable for these MP3 sources regardless.

## Consequences

- **`AudioSessionCoordinator` had no consumer when it landed** (issue #144 gave it one)**.** It is reviewed alone, before `PlaybackEngine`/`PlaybackController` exist, so its size and fidelity to the source behaviours can be judged without also reviewing a queue player and a UI. `FakeAudioSession` (`WXYCDJTests/Support/`) models the self-handback case with genuine lock contention on a real background thread — held and released via a `DispatchSemaphore` — rather than a scripted throw, because the failure it stands in for (`AudioSessionCoordinator`'s own `sessionLock` finding a deactivation already holding it) is not something the underlying session itself ever throws.
- **The two file-level ports and the extraction are two different risk profiles, and reviewers should treat them differently.** A ported file can be diffed against its source line-for-line; an extraction cannot, because there is no source file to diff against — its correctness rests on the extraction's own tests reproducing the source's documented behaviour, which is why issue #137 specifies exactly what `WXYCDJTests` must drive: the retry budget exhausting, the self-handback resuming without spending it, and the generation counter discarding a stale deactivation. Review added four more, one per restored guard plus the uncovered arm that motivated them: a `deactivate()` cancelling a pending bounded retry, a `deactivate()` cancelling an activation deferred behind a handback, a second `deactivate()` inside the handback window producing exactly one `setActive(false, …)`, and a hard non-`'!int'` activation failure scheduling no retry at all. `FakeAudioSession` records the *options* of every `setActive` call, not just the count, so `.notifyOthersOnDeactivation` — the single most user-visible property of the handback path — is pinned rather than assumed.
- **Reversibility is high until a UI ships.** Removing `WXYCDJ/Playback/` costs one directory, this ADR, and — since issue #144 — one property on `AppDependencies` and one line in `View+AppEnvironment`; nothing on screen references any of it. Once issue #145 ships a transport surface, reversibility drops to the ordinary cost of removing any shipped feature.
- **The engine seam is deliberately narrow.** `PlaybackEngine` (issue #144) is `load([PlaybackItem])` / `play()` / `pause()` / `advance()` / `seek(to:)` plus an `AsyncStream<PlaybackEngineEvent>`. An earlier revision of this line justified that narrowness by saying a future FLAC/AAC rendition switch would be "a second conformer, not a redesign" — **that example was already wrong when it was written.** `GET /digital-archive/albums/{id}/playback` serves all five codecs (`mp3, aac, flac, m4a, wav`) through the one endpoint and the one engine; choosing between them is `PlaybackController.codecPreference`, a pure ordered list, not an engine swap. The narrowness is still worth having, for the reason the rest of this ADR gives — it is what keeps every decision the controller makes host-testable against a spy, and what would make a second *engine* (should the "temporary, three engines" problem this ADR avoids depending on ever tempt this app) a conformer rather than a redesign. It is simply not a rendition question.

## Amendments (issue #144)

### Amendment 1 — `AudioSessionCoordinator` is `@Observable`, and `isActivated` is readable

**Decision: make the coordinator `@Observable` and leave `isActivated` `private(set)` but readable; every other stored property is `@ObservationIgnored`.**

The prohibition above is on the *caller orchestrating the handback resume*, and this does not reintroduce that: the resume stays coordinator-internal, inline in the deactivation continuation, and there is still no public resume method, no closure parameter on `activate()`, and no `AsyncStream` on this seam.

Without it there is nothing for a consumer to key on. `activate() -> Bool` returning `false` means **deferred, not failed** — two states produce it (blocked by another app, which retries four times over a second; and blocked by this coordinator's own in-flight handback, resumed inline once it completes) and **both self-resolve**. The coordinator emitted no signal at all, so a `PlaybackController` that wants to know when the session is genuinely up could only poll.

`activate()` stays synchronous and prompt-returning, and that property is load-bearing rather than incidental: a transport tap must render `isPlaybackRequested` immediately rather than block on the ramp, which is the whole reason `PlaybackController` keeps that value separate from `isPlaying`.

Rejected: start optimistically and let AVFoundation report the outcome. It produces a silent failure mode — no audio, no error, nothing to debug — and issue #145 would inherit it.

Mechanically, `@ObservationIgnored` on everything else is not tidiness. `activationGeneration` is read from a `nonisolated` context under `sessionLock`, and the macro's generated accessors are main-actor-isolated, so tracking it would not compile; the rest is private bookkeeping whose observation would be noise.

### Amendment 2 — the `ErrorReporter` injection belongs to the coordinator, not to its consumer

**Decision: `AudioSessionCoordinator.init` takes `reporter: any ErrorReporter = NoOpErrorReporter()` and reports the failed handback itself.**

The earlier text promised that report to "the `PlaybackController` in issue #138, where a reporter is already in scope." **It cannot be kept from outside.** The failure happens inside a detached task in `deactivateLocked(ifGenerationIs:)`, and `deactivate()` returns `Void` — nothing outside this type can observe it, whatever is in scope there.

The same section's "takes no dependency beyond its session seam" line is about not taking a *playback* dependency. `ErrorReporter` is this app's universal diagnostic seam, already injected into `AppDependencies`, `BinViewModel` and `LoginViewModel` on exactly this defaulted-to-no-op pattern, so no existing construction site changes and no unit test fires a real event. It is stored as a `nonisolated let` of a `Sendable` existential so the `nonisolated` deactivation path can call it without hopping back to the main actor mid-handback.

### Amendment 3 — the engine reports failure as a closed enum, never an untyped `Error`

**Decision: `PlaybackEngineEvent.failed` carries `PlaybackEngineFailure` (`.mediaForbidden` / `.mediaFailed` / `.decodeFailed` / `.unknown`), not `any Error`.**

`AVPlayer` never surfaces an HTTP status through `AVPlayerItem.error`: a failed media load arrives as `AVFoundationErrorDomain -11800` wrapping an opaque `NSOSStatusErrorDomain` code, and the status exists only in `AVPlayerItem.errorLog()`'s `AVPlayerItemErrorLogEvent.errorStatusCode`. A controller handed an `any Error` therefore has nothing it can match on to mean "403" — while a spy can be made to emit anything. An untyped seam would have produced a green suite over an app that could not do what the suite claimed, which is precisely the risk an extraction (as opposed to a diffable port) already carries here.

`AVQueuePlayerEngine` (issue #145) owns the `errorStatusCode` → case mapping as its one piece of documented-but-untested wiring — the same carve-out `AlbumDetailView` already lives with. Issue #139's `ArchivePlaybackFailureReason` assumes these cases exist and switches over them with no `default:`.

### Amendment 4 — the manifest is not a complete now-playing record

`DigitalArchivePlaybackManifest` is `{library_id, expires_at, tracks[]}` and carries neither an album title nor an artist name, so `PlaybackItem` takes both from the detail screen's own state (`AlbumInfo`, or the `AlbumSearchResult` fallback behind it) and carries them through the queue. Without that, issue #138's `NowPlayingInfoCenterManager` has nothing to put on the lock screen and issue #145's mini-player has nothing to label.

`PlaybackItem.description` deliberately omits the presigned URL, so the credential rule this ADR states above ("never `os_log`ged") survives an interpolated `"\(item)"` in a log line someone adds later.
