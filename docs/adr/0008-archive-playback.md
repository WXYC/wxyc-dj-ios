# Digital-archive playback lives in the app layer, over a PlaybackEngine seam, and reuses only what has no cheaper alternative

The auto DJ's music library — every rotation release plus a ~2,300-album freeform collection, ~23.5k MP3s — sits in a DigitalOcean Space that AzuraCast already streams from for on-air playout. A DJ signed into `wxyc-dj-ios` currently has no way to hear any of it; the plan in `plans/digital-archive/auto-dj-archive-player.md` (§6) makes this app the first consumer of that library, behind a signed, time-limited playback manifest Backend-Service serves and a kill switch. This ADR covers only the `wxyc-dj-ios` side. It was written for the part landing with issue #137's PR — [`AudioSessionCoordinator`](../../WXYCDJ/Playback/AudioSessionCoordinator.swift) — and has since been amended by issue #144, which added the [`PlaybackEngine`](../../WXYCDJ/Playback/PlaybackEngine.swift) seam and [`PlaybackController`](../../WXYCDJ/Playback/PlaybackController.swift). The work was split three ways after #137 shipped: issue #138 carries the two credited system-integration ports plus the background mode, **issue #144** the seam and controller, and **issue #145** the `AVQueuePlayer` adapter and the two UI surfaces. Every "issue #138" this document used to write for the player itself now means #144 or #145; the amendments below say which.

## Decision

**Playback lives in `WXYCDJ/Playback/`, an app-layer module, behind a `PlaybackEngine` seam — not as a dependency on `wxyc-ios-64`'s playback package.** `AVQueuePlayer` (via an `AVQueuePlayerEngine` conformer, issue #145) is the only file importing AVFoundation for actual playback; on the session-management side it is imported by `AudioSessionCoordinator` and by [`AudioSessionProtocol`](../../WXYCDJ/Playback/AudioSessionProtocol.swift), the seam it activates through — the protocol's method signatures are spelled in `AVAudioSession.Category` / `.Mode` / `.RouteSharingPolicy` / `.SetActiveOptions`, so it cannot avoid the import, and `AVAudioSession` conforms to it there. `WXYCAPI` and `WXYCAPIModels` stay untouched by any of this — playback needs one new DTO and one typed `APIClient` method, not a package dependency.

**Why not depend on `wxyc-ios-64`'s `Shared/Playback` package.** Three reasons, all structural rather than incidental:

- It houses **three experimental playback engines** selected by a PostHog flag — `docs/architecture.md` there states plainly that this is temporary ("Houses several playback engines. Eventually this will whittle down to 1 or 2, but is currently in an experimental phase"). Depending on it would import that selection machinery, and its resolution, into an app that needs exactly one engine for one MVP.
- It carries **CPU aggregation and visualizer render taps** for the listener app's now-playing screen. This app has no visualizer and no use for per-engine CPU telemetry.
- The audio-session behaviour this app *does* need is not a separable unit there — it is ~550 lines interleaved inside a 2,693-line `AudioPlayerController` alongside all of the above, plus background-task assertions for a handback path this MVP doesn't need to protect with a `beginBackgroundTask` grant. There is no `AudioSessionCoordinator` file to add as a dependency; extracting the three behaviours into a new, small file was the only option that didn't also import the engine selector, the CPU aggregator, and the render taps.

**What was extracted, not ported, and what was left behind.** `AudioSessionCoordinator` (~475 lines, half of them comments recording why each guard is there) carries exactly three behaviours out of `AudioPlayerController.swift` (`c22a3eb`), each traceable to a specific field failure rather than invented for this app:

1. The category is configured lazily, on the first `activate()`, never in `init` — configuring at init would interrupt whatever else is already playing when the app launches. `.default` route-sharing policy, not the source's `.longFormAudio`: this app plays short-form music, not the long-form content that policy is for.
2. Activation distinguishes a `CannotInterruptOthers` failure (another app holds the session — bounded retry, four attempts over one second) from this coordinator's *own* in-flight deactivation (an event-driven resume instead, because the handback measures ~1s on device and would exhaust the bounded budget before finishing, wxyc-ios-64#514). Both re-drive paths, plus the scheduling of the bounded retry itself, are gated on the caller's standing intent — the source's `playbackIntended` (~1128, ~1149, ~1452), tracked here as an `activationIntended` flag `activate()` sets and `deactivate()` clears, since this coordinator owns no player to read the intent off.
3. Deactivation runs off the main actor under a generation counter, because `setActive(false, …)` is a synchronous ~1s XPC round trip to `mediaserverd` and running it on the caller's turn would freeze whatever UI is waiting on that turn. A second `deactivate()` inside that window is coalesced rather than stacked (source ~1300-1310, drained at ~1505-1510), and the attempt's outcome is carried back out of `sessionLock` before it is logged (~1585), so the logging never happens while the main actor may be waiting on that lock.

Left behind, deliberately: engine selection, CPU/session aggregation, render taps, the watchOS `RadioPlayerController`, and the background-task assertion `AudioPlayerController` takes around its handback (`beginHandbackAssertion`/`endAllHandbackAssertions`) — that assertion exists to protect a pause that arrives right as the app backgrounds, a scenario this MVP's UI doesn't create pressure on yet; it can be added to `AudioSessionCoordinator` later without touching the three behaviours above if a background-pause defect ever surfaces here. Left behind with it, for the same "this coordinator owns no player and no app-lifecycle state" reason: the `isForegrounded` half of the source's re-drive gating, the on-the-caller's-turn handback it performs when the app backgrounds (`deactivateAudioSessionOnCallersTurn`), the silent-startup escalation a post-handback hard failure triggers there, and the `ActivationRetryCause` labelling that distinguishes three diagnoses this coordinator can only reach one of.

**Three guards are *not* left behind, and an earlier revision of this ADR implied they were by describing the three behaviours without them.** Each was restored under review of the PR that introduced this file, because each is load-bearing rather than incidental: the intent gate above (without it, a `deactivate()` issued while an activation is deferred does nothing at all, and the deferral then stands a `.playback` session up moments after the caller asked for release — the `isActivated` guard returns early on exactly the state a deferral leaves behind), the in-flight coalescing (without it, `isActivated` is the only guard, and it is cleared ~1s later in the continuation — so a second `deactivate()` inside that window queues a second detached task that blocks a cooperative-pool thread on `sessionLock` for the rest of the handback, then passes its own generation check, since only an *activation* bumps the generation, and re-fans the resume notification to every other audio app), and the failure logging (a failed handback is a pure silent degrade — nothing on screen marks it, and `isActivated` deliberately stays set so a later call retries, so without a log line even a persistent failure is invisible). The one thing the source had here that this file did not, until issue #144, was an `ErrorReporter.report` beside that log — see **Amendment 2** below for why the injection point turned out to be this file after all. No public resume method, no closure parameter on `activate()`, no `AsyncStream` on the seam: the handback resume is `AudioSessionCoordinator`'s own business, finished inline by `resumeDeferredActivationAfterHandback()` once the deactivation's generation check has run. `PlaybackController` (issue #144) calls `activate()`/`deactivate()` and nothing else — it never orchestrates the handback. **Amendment 1** below adds one read-only observation point to that surface and explains why it is not the same thing.

**Two files are file-level ports, not extractions, and issue #138 carries them (unchanged by the split):** `PlaybackInterruptionRouteHandler.swift` (194 lines) and `NowPlayingInfoCenterManager.swift` (149 lines, deliberately never reading `MPNowPlayingInfoCenter.nowPlayingInfo` back — a synchronous XPC hang the source already discovered and fixed). Both are small, self-contained, and copied with credit in their headers rather than re-derived, because unlike the audio-session behaviour they are not interleaved with anything this app doesn't want.

**The presigned playback URL is a credential, not a resource identifier — extends [ADR 0007](0007-ios-anonymous-error-reporting.md).** ADR 0007's contract is a hard anonymity floor enforced by construction: no identity, no search-query text, no server-message text, no request URLs with query strings reach a Sentry event. A digital-archive manifest URL is a new instance of exactly the value class `URLScrubbing` and `TelemetryPrivacyScrub` already exist to strip — a presigned S3-style GET with the signature living in the query string — so it needs no new mechanism, only the existing one applied to a new call site: never `os_log`ged, and `SentryPrivacyPipelineTests` gets a case (issue #139) asserting a presigned URL's signature never reaches a serialized event. This app still runs `tracesSampleRate = 0`; issue #139's cue→first-frame timing rides an analytics event property instead of a Sentry span, for the same reason ADR 0007 gives for having no tracing at all.

**The digital-audio badge rides the on-device catalog clone — extends [ADR 0005](0005-ios-spotlight-on-device-catalog-clone.md).** ADR 0005 already clones the catalog for Spotlight search and keeps it as the offline-search and deep-link fallback source. `has_digital_audio` (issue #136) is one more optional `CatalogRow` field read off that same clone — offline-capable for free, and excluded from `CatalogSpotlight.fingerprint(for:)` and `searchableItem(for:)` since it is not searchable text and would otherwise force a reindex of every newly-bound album. The manifest fetch itself (`GET /digital-archive/albums/{id}/playback`) is the source of truth for whether audio is actually playable *right now*; the badge is only ever a hint that a manifest fetch is worth trying, exactly as the rest of this app treats the clone as a hint that degrades gracefully against a live 404.

**No downloads in the MVP.** Every track streams from its presigned URL each time; nothing is cached to disk beyond the ordinary `URLCache`/`AVPlayer` buffering that streaming already implies. Offline playback — a client-side cache keyed on `file_id`, validated by `content_hash`, downloaded via `URLSession` into the app container under Data Protection — is designed for in the manifest contract (`file_id`, `content_hash` are present from day one) but explicitly out of scope until the counsel question about on-device copies of these files is resolved. `AVAssetDownloadTask` is HLS-only and unavailable for these MP3 sources regardless.

## Consequences

- **`AudioSessionCoordinator` had no consumer when it landed** (issue #144 gave it one)**.** It was reviewed alone, ahead of `PlaybackEngine`/`PlaybackController`, so its size and fidelity to the source behaviours could be judged without also reviewing a queue player and a UI. That is history now rather than a standing property, and the review of #144 showed what it cost: with no consumer, nothing exercised the coordinator against a caller, and the first one shipped discarding `activate()`'s return value entirely — see **Amendment 1**, whose rejected alternative it had silently become. `FakeAudioSession` (`WXYCDJTests/Support/`) models the self-handback case with genuine lock contention on a real background thread — held and released via a `DispatchSemaphore` — rather than a scripted throw, because the failure it stands in for (`AudioSessionCoordinator`'s own `sessionLock` finding a deactivation already holding it) is not something the underlying session itself ever throws.
- **The two file-level ports and the extraction are two different risk profiles, and reviewers should treat them differently.** A ported file can be diffed against its source line-for-line; an extraction cannot, because there is no source file to diff against — its correctness rests on the extraction's own tests reproducing the source's documented behaviour, which is why issue #137 specifies exactly what `WXYCDJTests` must drive: the retry budget exhausting, the self-handback resuming without spending it, and the generation counter discarding a stale deactivation. Review added four more, one per restored guard plus the uncovered arm that motivated them: a `deactivate()` cancelling a pending bounded retry, a `deactivate()` cancelling an activation deferred behind a handback, a second `deactivate()` inside the handback window producing exactly one `setActive(false, …)`, and a hard non-`'!int'` activation failure scheduling no retry at all. `FakeAudioSession` records the *options* of every `setActive` call, not just the count, so `.notifyOthersOnDeactivation` — the single most user-visible property of the handback path — is pinned rather than assumed.
- **Reversibility is high until a UI ships.** Removing `WXYCDJ/Playback/` costs one directory, this ADR, and — since issue #144 — one property on `AppDependencies` and one line in `View+AppEnvironment`; nothing on screen references any of it. Once issue #145 ships a transport surface, reversibility drops to the ordinary cost of removing any shipped feature.
- **The engine seam is deliberately narrow.** `PlaybackEngine` (issue #144) is `load([PlaybackItem])` / `play()` / `pause()` / `advance()` / `seek(to:)` plus an `AsyncStream<PlaybackEngineEvent>`. An earlier revision of this line justified that narrowness by saying a future FLAC/AAC rendition switch would be "a second conformer, not a redesign" — **that example was already wrong when it was written.** `GET /digital-archive/albums/{id}/playback` serves all five codecs (`mp3, aac, flac, m4a, wav`) through the one endpoint and the one engine; choosing between them is `PlaybackController.codecPreference`, a pure ordered list, not an engine swap. The narrowness is still worth having, for the reason the rest of this ADR gives — it is what keeps every decision the controller makes host-testable against a spy, and what would make a second *engine* (should the "temporary, three engines" problem this ADR avoids depending on ever tempt this app) a conformer rather than a redesign. It is simply not a rendition question.

## Amendments (issue #144)

### Amendment 1 — `AudioSessionCoordinator` is `@Observable`, and `isActivated` is readable

**Decision: make the coordinator `@Observable` and leave `isActivated` `private(set)` but readable; every other stored property is `@ObservationIgnored`.**

The prohibition above is on the *caller orchestrating the handback resume*, and this does not reintroduce that: the resume stays coordinator-internal, inline in the deactivation continuation, and there is still no public resume method, no closure parameter on `activate()`, and no `AsyncStream` on this seam.

Without it there is nothing for a consumer to key on. `activate() -> Bool` returning `false` means **deferred, not failed** — for two of the three arms that produce it (blocked by another app, which retries four times over a second; and blocked by this coordinator's own in-flight handback, resumed inline once it completes), and **those two self-resolve**. *(Corrected: this amendment as first written said "two states produce it" and that all of them self-resolve. There is a third — `.failed`, a `setActive(true)` that threw anything other than `CannotInterruptOthers` — which schedules no retry, sets no `activationPending`, and can never set `isActivated`. A consumer that waits out every `false` therefore burns its whole wait limit on a ramp that will never complete and reports a timeout for a failure already known synchronously. `activationPending` is the discriminator.)* The coordinator emitted no signal at all, so a `PlaybackController` that wants to know when the session is genuinely up could only poll.

`activate()` stays synchronous and prompt-returning, and that property is load-bearing rather than incidental: a transport tap must render `isPlaybackRequested` immediately rather than block on the ramp, which is the whole reason `PlaybackController` keeps that value separate from `isPlaying`.

Rejected: start optimistically and let AVFoundation report the outcome. It produces a silent failure mode — no audio, no error, nothing to debug — and issue #145 would inherit it.

**What the consumer actually does with it, since the rejected alternative is what #144 first shipped.** The controller's first cut read `activate()`, discarded its `Bool`, and called `engine.play()` on the next line — i.e. it *was* the rejected alternative, with a readable `isActivated` nobody consumed. `PlaybackController.beginPlayback()` now plays immediately on a `true` and, on a `false`, waits for `isActivated` to come up before starting the engine. Three properties of that wait are load-bearing:

- **`isPlaybackRequested` still flips synchronously**, before the wait. A transport tap renders at once; only the engine start is deferred. That is the same property the paragraph above calls load-bearing, and the wait must never be allowed to erode it.
- **The wait is bounded** by `PlaybackController.defaultActivationWaitLimit` (3 s), which covers the coordinator's own bounded retry (4 × 250 ms) and one ~1 s handback XPC round trip with room for them to overlap.
- **Expiry is explicit, not a fallback to playing anyway.** The queue is torn down, the session handed back, `PlaybackFailure.audioSessionUnavailable` recorded, and the give-up reported through `ErrorReporter`. Starting the engine at the bound would reintroduce exactly the silence this amendment rejects, just three seconds later.

The wait is a **read** of `isActivated` plus a timeout, never a callback: no public resume method, no closure on `activate()`, no `AsyncStream`, and the handback resume stays inline in the deactivation continuation. That boundary is unchanged.

Mechanically, `@ObservationIgnored` on everything else is not tidiness. `activationGeneration` is read from a `nonisolated` context under `sessionLock`, and the macro's generated accessors are main-actor-isolated, so tracking it would not compile; the rest is private bookkeeping whose observation would be noise.

### Amendment 2 — the `ErrorReporter` injection belongs to the coordinator, not to its consumer

**Decision: `AudioSessionCoordinator.init` takes `reporter: any ErrorReporter = NoOpErrorReporter()` and reports the failed handback itself.**

The earlier text promised that report to "the `PlaybackController` in issue #138, where a reporter is already in scope." **It cannot be kept from outside.** The failure happens inside a detached task in `deactivateLocked(ifGenerationIs:)`, and `deactivate()` returns `Void` — nothing outside this type can observe it, whatever is in scope there.

The same section's "takes no dependency beyond its session seam" line is about not taking a *playback* dependency. `ErrorReporter` is this app's universal diagnostic seam, already injected into `AppDependencies`, `BinViewModel` and `LoginViewModel` on exactly this defaulted-to-no-op pattern, so no existing construction site changes and no unit test fires a real event. It is stored as a `nonisolated let` of a `Sendable` existential so the `nonisolated` deactivation path can call it without hopping back to the main actor mid-handback.

### Amendment 3 — the engine reports failure as a closed enum, never an untyped `Error`

**Decision: `PlaybackEngineEvent.failed` carries `PlaybackEngineFailure` (`.mediaForbidden` / `.mediaFailed` / `.decodeFailed` / `.unknown`), not `any Error`.**

`AVPlayer` never surfaces an HTTP status through `AVPlayerItem.error`: a failed media load arrives as `AVFoundationErrorDomain -11800` wrapping an opaque `NSOSStatusErrorDomain` code, and the status exists only in `AVPlayerItem.errorLog()`'s `AVPlayerItemErrorLogEvent.errorStatusCode`. A controller handed an `any Error` therefore has nothing it can match on to mean "403" — while a spy can be made to emit anything. An untyped seam would have produced a green suite over an app that could not do what the suite claimed, which is precisely the risk an extraction (as opposed to a diffable port) already carries here.

`AVQueuePlayerEngine` (issue #145) owns the `errorStatusCode` → case mapping as its one piece of documented-but-untested wiring — the same carve-out `AlbumDetailView` already lives with. Issue #139's `ArchivePlaybackFailureReason` assumes these cases exist and switches over them with no `default:`.

### Amendment 4 — the manifest is not a complete now-playing record

`DigitalArchivePlaybackManifest` is `{library_id, expires_at, tracks[]}` and carries neither an album title nor an artist name, so `PlaybackItem` takes both from the detail screen's own state (`AlbumInfo`, or the `AlbumSearchResult` fallback behind it) and carries them through the queue. Without that, issue #138's `NowPlayingInfoCenterManager` has nothing to put on the lock screen and issue #145's mini-player has nothing to label.

`PlaybackItem.description` deliberately omits the presigned URL, so the credential rule this ADR states above ("never `os_log`ged") survives an interpolated `"\(item)"` in a log line someone adds later.

### Amendment 5 — the post-403 refetch recovers the *track*, not the playhead

**The one-shot refetch resumes on the same `file_id` and restarts that track from its beginning. It does not restore the position within the track, and issue #144 could not have made it do so.**

Earlier wording here, in `CLAUDE.md`, and in `PlaybackController`'s own comments described this as resuming "where the DJ was", which reads as a stronger guarantee than the code gives. What it actually guarantees is narrower and still worth having: the *queue cursor* survives the refetch — a refreshed manifest whose track list shifted resumes on the track the DJ was on rather than at whatever now sits at that array index — and the album does not restart from track 1. `cue(from:)` sets `position = 0` and issues no `engine.seek(to:)`, so a 403 twenty minutes into a 24-minute side drops the DJ back at 0:00 of that side. On a long-form freeform release that is a real regression, not a rounding error.

**Fixing it belongs to the engine adapter, and the reason is structural rather than an omission.** Re-seeking needs the playhead at the moment of failure, and this seam deliberately carries no time: `PlaybackEngineEvent` is four cases (Amendment 3's narrow vocabulary) with no periodic time observation, so `PlaybackController.position` is a *commanded* value — what this controller last asked for — never a sampled one. Nothing in issue #144 knows where the DJ actually was. Widening the seam to carry time in order to fix this would trade away the property that makes every controller decision host-testable against a spy, for a recovery case the engine adapter can serve directly once it exists: `AVQueuePlayerEngine` holds `currentTime()` and can re-seek on its own re-cue. Recording the limitation is therefore the whole of #144's obligation here.

**Correction: this amendment originally assigned that fix to issue #145, and #145 closed without doing it.** It shipped `AVQueuePlayerEngine` — so the adapter this paragraph names as the right home now exists — but the adapter samples no time and the post-403 re-cue still starts the recovered track at 0:00. The work is [#149](https://github.com/WXYC/wxyc-dj-ios/issues/149), and the three forward-pointers that named #145 (`PlaybackEngine.swift`'s `PlaybackItem.fileId` doc, `CLAUDE.md`'s `PlaybackController` bullet, and this paragraph) were re-pointed at it during #145's review. Nothing about the reasoning above changes; only the ticket number does.

### Amendment 6 — a terminal failure persists the mini-player in a failed state, and names the album it belongs to

**Decision: `MainView`'s mini-player renders a failed state and stays on screen when `PlaybackController.lastFailure` is set, rather than vanishing with `currentItem`, and it *names the album the failure belongs to*; the detail screen's Play section separately renders the synchronous refusal from a `start()` call that returns `false`, without a name, because it already sits under the album's own header. The two surfaces share one copy mapping (`PlaybackFailureCopy`) and never invent a second vocabulary over `PlaybackFailure`.**

Issue #151 named the defect: `lastFailure` had no production reader, so a refused Play tap did nothing and a mid-playback failure made the mini-player disappear with no explanation. The fix has to answer two separate questions — what does a DJ see when a fresh Play tap is refused, and what does a DJ see when an *already playing* album dies — because the two are backed by different code paths and, it turns out, cannot be answered by the same mechanism.

**Why the Play section's boolean return value cannot carry the second answer.** `start(manifest:albumTitle:artistName:)` returns `false` for exactly three of the six `PlaybackFailure` cases — `.manifestExpiring`, `.emptyManifest`, `.noPlayableRendition` — because those are the only guards that run *before* `queue = items` and `cue(from: 0)`. **That is a fact about `start()`, not a partition of the enum, and reading it as one is the trap this paragraph exists to close.** Those same three cases are set again by `refetchManifest` — `fail(.manifestExpiring)`, `fail(.emptyManifest)`, `fail(.noPlayableRendition)` — which runs mid-playback after a media 403, with no `start()` anywhere in its path. So all three are *both* synchronous-refusal cases and mid-playback cases, depending on how they were reached. The traffic runs the other way too: `.audioSessionUnavailable` is set after `start()` has already assigned the queue and called `cue(from:)`, which calls `beginPlayback()`, which can itself call `fail(.audioSessionUnavailable)` **synchronously, inside the same `start()` call**, if `AudioSessionCoordinator.activate()` returns `.failed` rather than a deferral. `start()` still executes its unconditional `return true` immediately afterward — nothing in its body reads back what `cue(from:)` did. So a caller who only inspects `start()`'s return value can be handed `true` for a call that failed and tore its own queue down before that `true` was returned. This is not a hypothetical: it is the normal shape of a hard audio-session failure that isn't a retryable deferral. Any design that tries to answer "was this failure visible" purely from the boolean return is wrong on this path by construction.

**Why the detail screen is not the general-purpose surface, even though it is a reasonable answer for the boolean case.** Two structural reasons, not merely inconvenience:

1. Two `AlbumDetailView` instances for two *different* albums can be mounted at the same time — Search and Bin each own their own `NavigationStack`, and a detail screen stays on its stack across a tab switch. `fail(_:)` clears the queue whenever it wasn't already empty, so a failure that stops album A because a refused start for album B ran its guard (`start()`'s refusal path deliberately tears down whatever was already playing — see `fail(_:)`'s doc comment) would, if both screens keyed reactively off `playback.lastFailure`, cause *both* mounted screens to render a message about a failure that only one of them caused. There is no field on `PlaybackController` that says which album a failure belongs to (`albumID` is private and is cleared by `clearAlbumIdentity()` as part of the same `fail(_:)` call), so a screen cannot reliably attribute a shared, reactive `lastFailure` to itself.
2. A mid-playback failure can happen while the DJ is nowhere near the detail screen for the album that's playing — browsing Search, or sitting in the Bin tab. The whole point of the mini-player is that it is reachable from every tab; a detail-screen-only surface would silently swallow exactly the failures issue #151 is about whenever the screen isn't presented, which is the common case for something that died three tracks in.

**What the detail screen actually gets instead.** `AlbumDetailView` keeps a local `@State private var playbackStartFailure: PlaybackFailure?`, written only at the moment its own `togglePlayback(manifest:)` calls `start(...)` and reads back `playback.lastFailure` if that call returned `false`. This is scoped to *this screen's own attempt* by construction — it is never read reactively off the controller, so the two-screens-mounted-at-once case above cannot cross-contaminate it. It renders as a faint caption beneath the Play button, in the same register as the existing LML-enrichment footer note, and is reset at the top of every `loadAll()`. In practice it shows **two** cases, not the three `start()` can refuse on: `loadPlaybackManifest()` maps an empty `tracks[]` to `.unavailable` and the section renders only from `.loaded`, so `start()`'s empty-tracks guard cannot fire from this screen and `.emptyManifest` is unreachable here. A mid-`cue` `.audioSessionUnavailable` is not shown here either — `start()` returns `true` on that path — and is covered by the mini-player below. Worth knowing when reading this as a shipped guarantee: both reachable cases are rare in the current production configuration (`.noPlayableRendition` needs a non-mp3 rendition, which the bind job cannot produce until WXYC/Backend-Service#2336; `.manifestExpiring` needs a detail screen left open past 3h50m), so today the mini-player does effectively all of the real work and this caption is close to dead code.

**The mini-player is the comprehensive surface.** `MainView.body`'s `safeAreaInset` gate becomes `playback.currentItem != nil || playback.lastFailure != nil`. This catches every one of the six `PlaybackFailure` cases, regardless of whether the failing call's own return value could have named it, because it reads the one property `PlaybackController` already sets correctly and at the correct time for every exit through `fail(_:)`. Two properties make this safe rather than merely convenient:

- **`currentItem` and `lastFailure` are mutually exclusive in practice.** `start(...)` clears `lastFailure` unconditionally at its top, before any guard, so a successful `start` always leaves it `nil`; and every `fail(_:)` call empties the queue whenever it wasn't already empty, so `currentItem` is `nil` by the time `lastFailure` is set. `MiniPlayerBar` therefore never has to reconcile "playing" and "failed" states at once — exactly one of its two bodies renders.
- **`lastFailure` is cleared at exactly three points, and a natural end-of-queue is not one of them.** A fresh `start()` clears it at the top; `dismissFailure()` clears it for the DJ; and `stop()` clears it — that third one added in review, because `AppDependencies` outlives a sign-out and calls `stop()` from `handleAuthChange`'s sign-out arm, so a failure left standing there renders its bar over the *next* session, plausibly a different DJ on a shared control-room device who has played nothing. A natural end-of-queue and every other transport call leave it alone, so the failed state does not flicker or self-heal behind the DJ's back. Because so little else clears it, the mini-player's failed state carries its own dismiss control (`PlaybackController.dismissFailure()`, a one-line `lastFailure = nil` with no other side effect) — without one, a DJ who reads the message and moves on would have it pinned to the bottom of every tab until they next tried to play something.

**Rejected: filtering the mini-player's gate to only the three "mid-playback" cases** (`.engine(_)`, `.refetchFailed`, `.audioSessionUnavailable`), on the theory that the other three are already covered by the Play section's inline note and repeating them in the mini-player is redundant. It is rejected because **the two sets overlap, so no such filter can be correct.** `refetchManifest` sets `.manifestExpiring`, `.emptyManifest` and `.noPlayableRendition` mid-playback with no `start()` in the path and therefore no inline note anywhere: a DJ three tracks into an album whose refetched manifest comes back with its assets cleared gets `fail(.emptyManifest)`, and under this filter would get exactly the silence issue #151 was filed to remove. It would also reintroduce a second, parallel classification of `PlaybackFailure` that the issue explicitly warns against ("resist the urge to add a new error-state enum in the view; map `PlaybackFailure` directly, or the vocabulary forks"). The redundancy the filter would buy is real but small — a DJ refused inline sees the same sentence twice — and it is not worth a silent-failure path to remove.

> An earlier revision of this amendment argued the filter was "provably wrong on the synchronous-`.audioSessionUnavailable`-during-`start()` case." That argument was self-refuting: `.audioSessionUnavailable` is in the list the filter *retains*, so the filter would not have dropped it. The same revision claimed a DJ "loses nothing" for the other three cases, which the `refetchManifest` paths above make false. The conclusion was right and the reasoning was not — recorded here rather than silently replaced, because the reasoning is what the next contributor will weigh when they consider the same filter again.

**The failure carries its album, and that was a correction rather than a design.** The first version of this amendment stored a bare `PlaybackFailure?` and rendered it unattributed. Review found the defect that creates, and the sharp part is that *this amendment already contains the argument against it*: the case above for why the detail screen cannot key reactively off `lastFailure` is that doing so would "cause **both** mounted screens to render a message about a failure that only one of them caused." The mini-player has the same property in a worse form — it spans every tab, so there is no screen it *isn't* rendering over. Concretely: album A is playing; the DJ opens album B in another tab and taps Play; B is refused, and `fail(_:)` tears down A's queue as it must; the DJ walks back to A's detail screen and reads "**This** album's playback link expired" directly beneath the album whose link is fine. The copy uses a deictic, so an unattributed bar does not merely omit a name — it points at the wrong one, and the DJ's reasonable next move is to reopen the album that was never broken.

`lastFailure` is therefore a `PlaybackFailureRecord` (the case plus the album title), not the bare case. One value rather than two `private(set)` properties, because `fail(_:)` is reached from ten call sites and two fields written separately are two fields a later edit can leave disagreeing — the "one rule over all fields, rather than two rules that drift" argument `retireAutoResumeState(reason:)` already makes in this file.

**`fail(_:albumTitle:)` takes the title with no default, and that is load-bearing rather than fastidious.** `self.albumTitle` is assigned only *after* `start(...)`'s guards pass, and `clearAlbumIdentity()` does not reset it, so at the three refusal arms it still holds the **previous** album's title. A defaulted parameter reading `self.albumTitle` would compile, pass every pre-existing test, and name the wrong album at exactly the sites this record exists to fix — the same defect, inverted. Requiring the argument makes each of the ten sites a decision: the three `start(...)` refusals pass their local parameter, the seven that run once an album is genuinely cued pass `self.albumTitle`. `PlaybackControllerTests.refusedStartNamesTheRefusedAlbum` pins it by starting one album cleanly and having a second refused; against the defaulted form it reports the first album's title.

**Copy is shared, not duplicated.** `PlaybackFailureCopy.message(for:)` (`WXYCDJ/Playback/PlaybackFailureCopy.swift`) is the one total switch (no `default:`) from `PlaybackFailure` to a fixed, static string, plus a nested total switch from `PlaybackEngineFailure` folding all four engine cases into one generic "Couldn't play this album." — matching the issue's "generic couldn't-play-this for the engine and session cases" instruction, with `.audioSessionUnavailable` sharing that same generic string. `.manifestExpiring`, `.emptyManifest`, and `.noPlayableRendition` each get distinct copy, preserving the coverage-gap-vs-codec-gap distinction issue #144 introduced the enum to carry. Both the Play section and the mini-player call this same function; neither view switches over `PlaybackFailure` itself. No case's copy is, or ever should be, derived from the manifest's presigned URL — every string in `PlaybackFailureCopy` is a fixed literal.
