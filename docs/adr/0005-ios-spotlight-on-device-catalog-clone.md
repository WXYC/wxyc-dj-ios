# iOS clones the catalog on-device and indexes it into Core Spotlight for home-screen search

v1 search lives entirely inside the app, behind sign-in and a tab — there is no way for a DJ to type an album into the iOS home screen and jump straight to it. The catalog is small as text (single-digit-to-low-tens of MB, gzipping to a few MB), so cloning the whole thing onto the device and mirroring it into Core Spotlight is feasible. This ADR records the decision to do exactly that: clone the catalog locally, index it into Core Spotlight so it surfaces in home-screen (Spotlight) search, and deep-link a tap straight into the app's [Album Detail](../../WXYCDJ/Detail/AlbumDetailView.swift). It is a **new iOS surface beyond the documented 13 v2 surfaces** in [`README.md`](../README.md) and is not one of the nine cross-repo ADRs in [`cross-repo-adrs.md`](../cross-repo-adrs.md); the [2026-06-10 triage tracker (#18)](https://github.com/WXYC/wxyc-dj-ios/issues/18) flagged that v2 surfaces drift out of the tracker when they live only in prose, so this surface gets a local ADR. Implementation is tracked in [#19](https://github.com/WXYC/wxyc-dj-ios/issues/19) and is **blocked on the only backend work it needs** — a bulk catalog export with a conditional-GET freshness check ([BS#1466 epic](https://github.com/WXYC/Backend-Service/issues/1466) / [BS#1467 watermark + middleware](https://github.com/WXYC/Backend-Service/issues/1467) / [BS#1468 `GET /library/catalog`](https://github.com/WXYC/Backend-Service/issues/1468)).

The data path mirrors Backend-Service's Epic F flowsheet precedent: a `library_watermark` advanced by a DB statement trigger (so the discogs-etl daily sync, which writes straight to Postgres, advances it too) feeds a generalized `conditionalGet` middleware, and the new `GET /library/catalog` returns the whole catalog gzipped with a `Last-Modified` header. iOS sends `If-Modified-Since` from a stored watermark and gets a cheap `304` on the common day (ETL writes ~daily) or a `200` + full body when the catalog moved. The cloned rows reuse the existing [`AlbumSearchResult`](../../Packages/WXYCAPI/Sources/WXYCAPI/DTOs/AlbumSearchResult.swift) DTO — BS#1468's projection follows `AlbumSearchResultRow`, and `[AlbumSearchResult]` already decodes it field-for-field — persisted in an **id-keyed** on-device store, and refreshed both in the foreground and (best-effort) in the background.

A Spotlight tap arrives as an `NSUserActivity` of type `CSSearchableItemActionType` carrying `"album.<id>"`; the deep-link is presented in its **own `NavigationStack` inside a `fullScreenCover` over [`RootView`](../../WXYCDJ/RootView.swift)** rather than pushed onto a tab, and routed through a single `AlbumRoute` value whose identity is the album id. Because a Spotlight tap on a cold launch can land while [`restoreSession()`](../../WXYCDJ/WXYCDJApp.swift) is still resolving (or while signed out), the pending id is stashed and replayed once auth reaches `.signedIn` — without that replay, cold-launch deep links silently drop.

## Consequences

- **Reuse `AlbumSearchResult`; do not add a parallel `CatalogEntry` DTO.** BS#1468's projection follows `AlbumSearchResultRow`, and `[AlbumSearchResult]` decodes it field-for-field — every projected field is required-and-present or `decodeIfPresent`/tolerant, and the columns the projection omits (`add_date`, `label_id`, `rotation_id`, `album_artist`, `matched_via`) all default to `nil`/`[]`. A second hand-rolled `CodingKeys` block tracking the same server contract would just double the drift surface that the repo's "explicit `CodingKeys`, `convertFromSnakeCase` off" rule exists to contain. The only cost is an always-empty `matchedVia: [TrackMatchHint]` on cloned rows — cosmetic. `AlbumSearchResult` (and its nested `TrackMatchHint` / `TrackMatchSource`) flips from `Decodable` to `Codable` so the store can persist it; a decode test pinned to BS#1468's exact 13-field projection guards the shared search/catalog shape against drift.
- **The local store is id-keyed, not a flat array.** The deep-link handler receives `"album.<id>"` and must do an O(1) id→row lookup to build the Album Detail fallback, so the store is keyed by album id (raw SQLite via `import SQLite3`, or an atomically-written `[Int: AlbumSearchResult]` Codable file at this size) with single-transaction atomic replace on a `200`. SwiftData / Core Data are rejected as heavy scaffolding for a read-mostly, wholesale-replaced cache.
- **Spotlight reindex is resumable and gap-free.** A `200` refresh diff-upserts changed rows and deletes only vanished ones inside a `beginBatch()` / `endBatch(withClientState:)` batch carrying the `Last-Modified` watermark as client state — not `deleteSearchableItems(withDomainIdentifiers:)` + re-add, which empties home-screen search for the whole (multi-minute) reindex and, if killed mid-way, wipes the index. The stored poll-watermark advances **only after** the Spotlight commit succeeds; advancing it first would let a crash strand the store ahead of the index, after which the next `304` never re-attempts the reindex.
- **Refresh runs foreground-primary, background-best-effort, via a split task design.** The foreground path (alongside `restoreSession()`) is the budget-unbounded floor; background is opportunistic top-up so a DJ who searches from the home screen without opening the app first still gets a catalog at most a day or two stale. A `BGAppRefreshTask` (`org.wxyc.dj.catalog.refresh`) does only the cheap conditional-GET poll and re-arms; on a `200` it submits a `BGProcessingTask` (`org.wxyc.dj.catalog.reindex`, `requiresExternalPower`) to do the multi-MB download + ~50k-row reindex while charging, keeping the heavy work off the ~30 s app-refresh budget. There is **no guaranteed scheduling** — iOS decides based on usage, battery, and Low Power Mode, and a force-quit suspends background scheduling until the next manual launch; the feature promises eventual convergence, not a freshness bound.
- **The deep link lands in its own cover, not a tab stack.** Pushing onto the Search tab would need both a path binding and a `TabView` selection binding, would orphan a detail view on top of an empty search, and would fabricate a "Back" target into a search the DJ never ran. The `fullScreenCover` returns the user to the exact tab and scroll position they left on dismiss, with a clean "Close". A single `AlbumRoute { id; fallback }` keyed on `id` only (so a clone-hit and a clone-miss for the same album coalesce, and `AlbumSearchResult`'s whole-struct `Hashable` never fragments the path) serves both the deep-link and the in-app tap paths through one hoisted `navigationDestination` — which also fixes a latent bug where the existing destination, nested in a view-state switch, is unregistered when search is idle.
- **Cold-launch deep links are replayed after auth; background auth failures skip silently.** A `@MainActor @Observable` router stashes the pending album id and replays it once `AuthService.state` becomes `.signedIn`. In the background, a missing or expired session (`AuthError.notSignedIn`, or a `401` from `GET /auth/token`) is a silent skip + reschedule — never a sign-in prompt, never a state flip that surfaces `LoginView` out of context. The existing `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` Keychain accessibility is already correct for post-first-unlock background reads and must not be weakened.
- **No Associated Domains, AASA, or Universal Links.** Core Spotlight tap-through is an in-app `NSUserActivity` continuation (`CSSearchableItemActionType`), not a Universal Link — so this surface does **not** reopen the entitlement question that [ADR 0002 (QR device authorization)](./0002-qr-device-authorization-shared-computer-signin.md) deliberately closed when it chose an in-app QR scanner over a Camera-app deep link. The catalog clone is non-sensitive (the shared station library), so its Spotlight domain needs no sign-out cleanup, unlike anything per-DJ would.
- **`Info.plist` moves to an xcodegen `info:` block; no new entitlement.** This repo has no physical `Info.plist` (`GENERATE_INFOPLIST_FILE: YES` + `INFOPLIST_KEY_*` synthesis in [`project.yml`](../../project.yml)), but `UIBackgroundModes` and `BGTaskSchedulerPermittedIdentifiers` are not expressible as `INFOPLIST_KEY_*` (the latter is an array), so the `WXYCDJ` target moves to an xcodegen `info:` block — which turns off `GENERATE_INFOPLIST_FILE` for that target and requires re-declaring the handful of keys currently synthesized (display name, scene-manifest + launch-screen generation, orientations). Core Spotlight and BackgroundTasks are both unentitled, so [`WXYCDJ.entitlements`](../../WXYCDJ/WXYCDJ.entitlements) stays exactly as-is (only `webcredentials:dj.wxyc.org`).
- **The only cross-repo commitment is the bulk-export endpoint, already filed.** Unlike the nine v2 ADRs in [`cross-repo-adrs.md`](../cross-repo-adrs.md), this surface commits no peer repo to new work beyond [BS#1466](https://github.com/WXYC/Backend-Service/issues/1466) / [#1467](https://github.com/WXYC/Backend-Service/issues/1467) / [#1468](https://github.com/WXYC/Backend-Service/issues/1468), which are filed and carry their own design. No semantic-index, LML, dj-site, or wxyc-shared mirror is needed; the endpoint gets documented in `api.yaml` by BS. So there is no mirror-tracking row to add to `cross-repo-adrs.md`.
- **Whole-catalog vs. subset Spotlight index is deferred to live data.** The local store holds everything regardless; only the Spotlight index breadth is open. If the live row count makes a full Core Spotlight index unhealthy (system throttling / eviction), fall back to indexing a subset (rotation + bin + recently-viewed). Decide once the live catalog count is known.
- **Reversibility.** The feature is additive — pulling it removes the store, the Spotlight indexer, and the BGTasks, and the app returns to in-app-only search with no migration cost. The `Codable` flip on `AlbumSearchResult` is a harmless additive conformance retained either way. The BS bulk-export endpoint is independently useful (any client wanting a catalog snapshot can use it).
- **Verification needed before shipping.** Cold-launch from a Spotlight result while signed out lands on the correct Album Detail after sign-in; a `304` poll performs no download and no reindex; a `200` reindex drops removed albums from home-screen search and never empties the index mid-run; a background reindex completes while charging; and the first full index does not block the UI.
