# QR device authorization for shared-computer sign-in to dj.wxyc.org

The control-room computer at WXYC is shared across DJ shows. Password sign-in on a shared keyboard is awkward and exposes credentials to shoulder-surfing and key-logger surfaces we don't fully trust. The iOS app is already an authenticated personal surface for every DJ. QR-based sign-in lets the browser display a QR, the iOS app scan + approve it, and the browser receive a session — without the DJ ever typing a credential on the shared machine.

Mechanism: better-auth's [`device-authorization` plugin](https://www.better-auth.com/docs/plugins/device-authorization) (RFC 8628), already shipped in better-auth ^1.6.11 and present in `apps/auth/node_modules/`. The browser POSTs `/auth/device/code` → renders the returned `verification_uri_complete` as a QR plus the `user_code` in plain text as feedback. Browser polls `/auth/device/token`. iOS opens the in-app QR scanner, parses the code, calls `/auth/device/verify` with the user_code (carrying the DJ's Bearer JWT). Approval is biometric-gated via `LAContext.deviceOwnerAuthentication`. The browser's next poll receives a session valid for 12 hours.

Scope: QR sign-in is restricted to `dj` and above (Music Directors, Station Managers); `member` accounts are rejected with `access_denied` at `/device/verify`. The QR-issued session carries the same role as the approving user — no downgrade. Same role-eligibility rules as password sign-in apply, with a single additional gate.

## Consequences

- **iOS app must already be signed in to scan a QR.** First-time iOS sign-in remains username/password against `/auth/sign-in/username`. QR is a *transfer* of credentials between surfaces, not a bootstrap — the bootstrap path stays intact.
- **The phone is the credential authority** for QR-issued browser sessions. Walked-away-phone is mitigated by `LAContext.evaluatePolicy(.deviceOwnerAuthentication, ...)` (Face ID → Touch ID → passcode cascade) wrapping the Approve action. No biometric, no approval — even with the phone unlocked and the approval card visible.
- **No Universal Links, Associated Domains entitlement, or AASA file.** The in-app scanner means the QR is opaque to iOS Camera — only the WXYC DJ app reads it. Trade-off accepted: the DJ must open the app first before scanning (one extra step in the mental model) in exchange for zero cross-repo deep-link infrastructure.
- **The phone-side approval card omits the `user_code`.** RFC 8628's user_code visual-comparison is a defense against in-flight QR substitution at the display, a threat that doesn't realistically exist for us (HTTPS+HSTS dj.wxyc.org, physically-locked control room). Discord Web and WhatsApp Web both omit the user_code on the phone for the same reason. The card shows site name, signed-in user, and elapsed time; the `user_code` remains visible on the *browser* for debug/feedback. Adding the code back on the phone is a future Tier-2 mitigation if real phishing is observed.
- **12-hour session expiry** on QR-issued sessions (vs better-auth's 7-day default for cookies). Chosen so a forgotten sign-out on the shared computer self-cleans before the next morning's DJ arrives. Implementation is a custom `expiresIn` on the session mint inside the `/device/token` handler — does not affect password-sign-in session lifetime.
- **Phone-coupled session revocation** (auto-kill browser session when the phone signs out) is *not* in v1. Adds surprise — a DJ signing out of the phone for unrelated reasons would unexpectedly lose their booth session. Deferred to v2 if forgotten-sign-out failure modes materialize. An iOS-side "Sign out all browsers" screen is a similarly deferred enhancement.
- **Audit forensics rely on better-auth defaults** for v1. The plugin's `deviceCode` table plus better-auth's existing `session` table answer "show me all sessions for @user this week, indicate which were QR-issued." Structured Sentry events (`auth.qr.approved`, `auth.qr.rejected`) tagged with phone IP/UA and browser IP/UA are a deferred follow-up — cheap to add when an incident demands richer forensics; not worth building speculatively for an internal tool with under 100 users.
- **Rate limiting reuses the existing `authMutationRateLimit`** (10 reqs / 15 min per-IP, keyed via `rateLimitKeyFromRequest`) on `/auth/device/code` and `/auth/device/verify`. `/auth/device/token` is intentionally excluded so RFC 8628's `authorization_pending` / `slow_down` / `expired_token` / `access_denied` JSON responses surface correctly to polling clients; an HTTP 429 layered on top would corrupt the protocol response shape and confuse any current or future polling client.
- **dj-site adds QR as a coequal third Form** alongside the existing `UserPasswordForm` and `EmailOTPForm` in `src/components/experiences/modern/login/Forms/`. The picker UI and `lib/features/application/login-method-storage.ts` already support a third value (`"qr"`); no UX-architecture work — only one new Form component + the polling logic.
- **iOS surfaces the scanner inside the toolbar account menu** (alongside Sign Out), not as a top-level toolbar icon or Home Screen quick action. Discoverable next to Sign Out (DJs find it because they go there to sign out anyway), minimal toolbar pollution, no shortcuts-app integration to maintain.
- **Phone JWT refresh** is handled by the existing `APIClient` 401-retry pattern — if the phone's JWT is stale at scan time, the silent JWT-exchange retry kicks in transparently. If refresh also fails (refresh token expired), the user is prompted to re-sign-in with username/password. No new code path for QR specifically.
- **Reversibility.** Decision is reversible — pulling the `device-authorization` plugin retires the three endpoints and the schema migration is one-table forward. Cost of reverting grows with adoption: DJs trained on QR who lose the path would feel the regression. The 12-hour session expiry, role gate, and biometric gate are all configurable post-ship without protocol changes.
- **Verification needed before shipping.** End-to-end manual test on staging dj.wxyc.org with: one MD account, one DJ account, and one `member` account — confirming the role gate rejects `member` cleanly, the 12-hour expiry triggers as expected, and the biometric prompt fires on every Approve.
