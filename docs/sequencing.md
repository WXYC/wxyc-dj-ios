# iOS v1 sequencing plan

## Phasing principles

Phases are ordered along three rails simultaneously: (1) **backend gating** — the per-DJ plays endpoint (ADR 0006), the semantic-index proxy (ADR 0002), the `AlbumSearchResult.artist_id` extension (C1), and the condition migration (ADR 0004) each gate a cluster of iOS work, so phases follow the readiness curve of those tickets; (2) **iOS substrate** — the unified Catalog explorer and in-show companion mode are platform primitives that several picks reuse, so they ship before features that compose them; (3) **value front-loading** — each phase is meant to deliver a coherent slice of DJ value (foundations → in-show + discovery → personal insight → editorial workflow), not an arbitrary backend-driven cut. Phases are sized so each could be delivered as one PR train of 3–5 PRs by one developer in two-week sprints, with parallel worktree opportunities called out explicitly at the bottom.

Phase 0 (QR sign-in) sits outside the rails above — it neither gates nor is gated by the catalog/in-show track, and can run concurrently with any of the four phases from day one.

## Phase 0 — QR sign-in for the shared-computer scenario (parallel track)

The control-room computer at WXYC is shared across DJ shows; password sign-in on a shared keyboard is awkward and exposes credentials. Per [ADR 0007](./adr/0002-qr-device-authorization-shared-computer-signin.md), iOS becomes a QR scanner that authorizes browser sign-in via better-auth's `device-authorization` plugin (RFC 8628). This phase is self-contained — no dependencies on the catalog/in-show track and no blockers for it — so it can launch in parallel with Phase 1 from day one. Recommended to ship early because (a) DJs are already used to going to the iOS app for one-tap actions, and (b) it lays groundwork for shared-computer security posture before the broader v1 surface rolls out.

- **Backend (BS-26 → BS-29):** register the plugin in `apps/auth/app.ts`, add the custom `/device/verify` hook (role gate + 12h session), extend `rateLimitedPaths`, document the three endpoints in `wxyc-shared/api.yaml`. Four S-sized sub-tickets in one PR. No new application-owned schema — the `deviceCode` table is generated by better-auth.
- **dj-site:** new `QRCodeForm.tsx` in `src/components/experiences/modern/login/Forms/` alongside the existing `UserPasswordForm` and `EmailOTPForm` (the picker UI and `login-method-storage` already accept a third value, `"qr"`). Renders the QR + `user_code`, polls `/auth/device/token` at the interval the server returns. **Size: S.**
- **iOS:** new `QRScannerView` (AVFoundation `AVCaptureSession` + `AVCaptureMetadataOutput` filtering `.qr`), new `QRApprovalView` (site name + signed-in user + elapsed time card), `LAContext.evaluatePolicy(.deviceOwnerAuthentication, ...)` wrapping the Approve action, `APIClient.approveDeviceCode(_:)` method, `Info.plist` additions (`NSCameraUsageDescription`, `NSFaceIDUsageDescription`), new menu item in the existing toolbar account menu alongside Sign Out. **Size: M.**
- **wxyc-shared:** OpenAPI documentation for the three new auth endpoints (covered by BS-29).
- **Total:** ~1 week elapsed if all three repos move in parallel; ~2 weeks if pursued single-threaded.

## Phase 1 — Foundations

Substrate phase. Lands the two reusable iOS primitives plus the smallest backend-cheap picks. Unblocks every later phase.

- **Cross-cutting: Unified Catalog explorer** — lens-based filter/sort over `/library/query` with list/grid toggle, the shared surface that picks #3, #4, #9 plug into. No new BS work. **Size: L.**
- **Cross-cutting: In-show companion mode** — Queue read + send from search/Mail Bin + reorder + remove, polling `/flowsheet/on-air?dj_id=me` for the on-air gate. Per ADR 0003. No new BS work; uses existing endpoints. **Size: L.**
- **Pick #1: Pre-show setlist / crate** — Mail Bin → Queue handoff (matches dj-site's `convertBinToQueue` semantics). Falls straight out of the in-show companion. No new BS work. **Size: S.**
- **Pick #2: Track preview via LML streaming URLs** — deep-link out from album detail to Spotify / Apple Music / Bandcamp URLs already in `AlbumMetadata`. No new BS work; LML already returns these. **Size: S.**
- **Pick #3: New arrivals feed** — lens in the Catalog explorer with a `?sort=add_date_desc&limit=N` query. No new BS work beyond confirming `/library/query` accepts the sort. **Size: S.**
- **Pick #4: Rotation browser** — lens in the Catalog explorer joining `/library/query` with rotation membership; tier facets (H/M/L/S) as filter chips. No new BS work (rotation endpoints exist). **Size: M.**
- **Pick #9: Browse-by surfaces** — lens variants over `/library/query` keyed by label / genre / era. No new BS work. **Size: M.**

## Phase 2 — In-show + discovery

Backend track lights up here: C1 (`AlbumSearchResult.artist_id`) and ADR 0002 (BS proxy with composed `/graph/artists/{id}/deep-dive`) need to land before this phase ships. ADR 0004 (condition migration) also gates pick #5.

- **Pick #8: Artist deep dive** — bio + Discogs photo + catalog + plays + similar artists + reviews, composed via `GET /graph/artists/{id}/deep-dive`. **Depends on:** C1 (`artist_id` on search results so rows are tappable), ADR 0002 (proxy exists), ADR 0001 (BS `artist_id` ≡ semantic-index `id` verified per C5). **Size: L.**
- **Pick #5: Damage / condition reports** — condition picker on album detail, MD-gated UI per JWT `role` claim, audit-log view. **Depends on:** ADR 0004 BS migration shipped (`PATCH /library/{id}/condition`, `condition_transitions` table). **Size: M.**
- **Pick #6: Quick voice memo on a track** — text-primary + ≤15s audio attachment, per-album scope, private. **Depends on:** new BS endpoints for memo CRUD + object storage for the audio clip. **Size: M.**

## Phase 3 — Personal stats + profiles

This is the phase that flips when [ADR 0006 (per-DJ plays)](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround) lands — three picks all consume `GET /djs/{id}/plays`, `/djs/{id}/play-stats`, and `/djs/{id}/has-played`. Pick #15 joins this phase because it consumes the parallel per-album endpoint ([ADR 0008](./cross-repo-adrs.md#adr-0008--per-album-play-history-is-a-first-class-api-surface-parallel-to-per-dj-plays)) and shares the [Swift Charts](https://developer.apple.com/documentation/charts) histogram component that [Phase 5](#phase-5--flowsheet-archive-search--structured-filter-builder)'s pick #16 also uses — shipping the per-album histogram before the archive histogram means the chart primitive is battle-tested by the time the larger surface arrives. Shipping the four play-data picks together amortizes the API integration cost.

- **Pick #7: Underplayed gems** — rate-based B+C+D blend with adaptive weights. Phase B (catalog-relative rarity) + Phase D (rotation-time-decayed) can ship the moment [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround) lands; Phase C (per-DJ relative) requires the `/djs/{id}/plays` endpoint specifically. **Depends on:** [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround) endpoints. **Size: L.**
- **Pick #10: Diversity readout** — 6 axes (artist, album, label, genre, era, new vs catalog), 4 fixed windows (30d / 90d / 1y / all), self-over-time. Each axis card is tappable and drills into a sorted-by-count list (Top Played folded in per [Q15 grilling resolution](../CONTEXT.md)). Interactive prototype: [`docs/prototypes/diversity-readout.html`](./prototypes/diversity-readout.html). **Depends on:** `/djs/{id}/play-stats?window=...` (pre-aggregated per [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround)) plus the `albums` field amendment ([BS-30](./bs-work-inventory.md#bs-30-add-albums-field-to-get-djsidplay-stats-response), ships in the same PR as [BS-20](./bs-work-inventory.md#bs-20-get-djsidplay-stats--pre-aggregated-stats) if not yet merged). Locale is [C2](./cross-repo-adrs.md#c2--lml-locale-enrichment-for-the-diversity-readout); ships in v2 as the 7th axis. **Size: M.**
- **Pick #11: Bin maturity** — per-entry badges (personal + station-wide play counts) and view-level summary. **Depends on:** `/djs/{id}/has-played?album_ids=...` (per [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround)). **Size: M.**
- **Pick #12: DJ profiles** — Tier 1 native edits over reused `auth_user`; Tier 2 fields deep-link to [dj-site](https://github.com/WXYC/dj-site); alumni stay forever. Self-contained on the iOS side. No new BS work for Tier 1 (existing `auth_user` mutations); Tier 2 is just an out-link. **Size: M.**
- **Pick #15: Per-album play histogram on Album Detail** — Apple Health-style horizontally scrollable [Swift Charts](https://developer.apple.com/documentation/charts) surface, Year/Month toggle with span-based default (>5y first-play-to-today → Year, else → Month), dashed `RuleMark` at release year when greater than first-play year, tooltip-only on bar tap (drill-in deferred to v2). Renders below the tracklist and above [LML](https://github.com/WXYC/library-metadata-lookup) extras on the existing Album Detail screen. Canonical iOS ADR: [`docs/adr/0003-per-album-play-stats.md`](./adr/0003-per-album-play-stats.md) (cross-repo: [ADR 0008](./cross-repo-adrs.md#adr-0008--per-album-play-history-is-a-first-class-api-surface-parallel-to-per-dj-plays)). **Depends on:** [ADR 0008](./cross-repo-adrs.md#adr-0008--per-album-play-history-is-a-first-class-api-surface-parallel-to-per-dj-plays) endpoint ([BS-31](./bs-work-inventory.md#bs-31-get-libraryalbum_idplay-stats-endpoint), S-sized). Shares the Swift Charts histogram component with [pick #16](#phase-5--flowsheet-archive-search--structured-filter-builder) (Phase 5). **Size: M.**

## Phase 4 — Review workflow

The largest single feature — full editorial fields, MD-curated queue, author-owned with MD takeover. Pulled into its own phase because it owns the most schema, the most new endpoints, and the most net-new UI surface area in the whole v1.

- **Pick #13: New arrivals review queue** — review detail view, review editor (headline, body Markdown, rotation_hint, FCC explicit, tags from curated vocabulary, per-track callouts with polarity, half-star rating), MD queue dashboard with claim/release, MD authorship-transfer flow, MD-gated tag-vocabulary CRUD. **Depends on:** ADR 0005 schema extensions + 8 new endpoints (`GET/POST/PATCH/DELETE /reviews`, `GET/POST/DELETE /review-queue`, `POST /review-queue/{id}/claim`, `POST /review-queue/{id}/release`, tag-vocabulary CRUD). Visible to signed-in users only — public publication is C4, deferred. **Size: XL.**

## Phase 5 — Flowsheet-archive search + structured filter builder

The largest single net-new iOS surface besides Reviews. Adds a coequal second search mode (alongside the existing catalog search) plus a reusable filter builder primitive that future surfaces can compose. Per [ADR 0009](./cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder), this surface mirrors dj-site's [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx) UX model and consumes a new BS endpoint (`POST /flowsheet/search`) with always-included plays-per-year histogram (matching [wxyc.info](http://www.wxyc.info/playlists/searchPlaylists)). Pulled into its own phase because the combined scope (`FilterBuilder` primitive + Search Plays surface + histogram component + result rows + Album Detail navigation) is roughly equivalent to the entire Review feature in [Phase 4](#phase-4--review-workflow).

- **Pick #16: Search Plays with structured builder + archive histogram** — new top-level Tab (alongside Search and Mail Bin), simple primary search bar plus a [Filters] affordance opening a builder sheet modeled on dj-site's [`PlaylistAdvancedSearch.tsx`](https://github.com/WXYC/dj-site/blob/main/src/components/experiences/modern/playlist-search/PlaylistAdvancedSearch.tsx), active-filter badges below the search bar (× to remove), always-included plays-per-year histogram with Year/Month toggle and Apple Health-style horizontal scroll, paginated results (100 rows infinite-scroll), result row tap → Album Detail (primary action) with a secondary "view show" chevron for the [wxyc.info](http://www.wxyc.info/playlists/searchPlaylists)-style show-context navigation. Canonical iOS ADR: [`docs/adr/0004-search-plays-flowsheet-builder.md`](./adr/0004-search-plays-flowsheet-builder.md) (cross-repo: [ADR 0009](./cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder)). Interactive prototype comparing the three UX options that informed this pick: [`docs/prototypes/search-ux-options.html`](./prototypes/search-ux-options.html). **Depends on:** [ADR 0009](./cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder) BS work ([BS-32](./bs-work-inventory.md#bs-32-post-flowsheetsearch-endpoint-with-structured-body-and-always-included-histogram) endpoint + [BS-33](./bs-work-inventory.md#bs-33-document-post-flowsheetsearch-in-wxyc-sharedapiyaml) OpenAPI). **Size: XL.**

The XL sizing breaks into three parallel sub-tracks: (1) `FilterBuilder<FieldConfig>` reusable primitive in `WXYCDJ/Sources/Views/FilterBuilder/` (parameterized over a field-config so future advanced-catalog-filter or MD review-queue-search surfaces can compose it), (2) Search Plays surface composing the primitive with its specific field set (Artist / Song / Album / Label / DJ / Date / Date Range), (3) histogram component shared with [pick #15](#phase-3--personal-stats--profiles)'s Album Detail surface (already shipped in [Phase 3](#phase-3--personal-stats--profiles), retested against the larger-cap Search Plays dataset). Three worktrees, three developers, converges at the Tab integration.

## What's NOT in v1

- **Pick #14 — Show coverage map.** Deferred from v1.
- **Freeform Map standalone surface.** No standalone discovery surface for the artist graph in v1; the semantic-index data surfaces only inside the Artist Deep Dive's "similar artists" rail (pick #8). A standalone Freeform Map is v2.
- **Tier 2 DJ profile edits in-app.** Tier 1 fields ship natively; Tier 2 fields (long-form bio, links, social, custom avatars) deep-link to dj-site for v1. C4 (public-handle work) is the catalyst for bringing Tier 2 in-app.
- **Public-facing reviews and DJ profiles.** C4 — paired with the `dj-site/694-public-dj-handle` branch landing. Internal-only for v1.
- **Locale axis on Diversity Readout.** C2 — LML doesn't expose country/origin yet. Ships in v2 as the 6th axis once LML extends.
- **Catalog-track-search Track 3** (track-keyed flowsheet picker). C3 — iOS mirrors dj-site once dj-site ships canonical. v1 sends queue entries with empty `track_title` per ADR 0003.
- **Artist endpoint LML enrichment.** Per CLAUDE.md, `/proxy/metadata/artist` bio + Wikipedia is in v1 (folded into pick #8). The second LML artist call with bio tokens was the v2 boundary in earlier notes; that's now corrected in CLAUDE.md.
- **Issue-row layering on album condition.** Per ADR 0004, multiple concurrent observations per album are explicitly out of v1; the v1 model is mutually-exclusive enum + audit log.
- **QR-sign-in enhancements** (per ADR 0007): phone-coupled session revocation (auto-kill browser session when phone signs out), structured Sentry events for QR approvals/rejections, iOS "Sign out all browsers" management screen, and Universal Link / Camera-app deep-linking. All are intentional deferrals — v1 ships the simplest viable flow (in-app scanner, better-auth defaults for audit, 12h expiry as the only cleanup mechanism).
- **Per-album histogram drill-in to raw rows** (per [ADR 0008](./cross-repo-adrs.md#adr-0008--per-album-play-history-is-a-first-class-api-surface-parallel-to-per-dj-plays)): a paginated `GET /library/{album_id}/plays` endpoint and the iOS row-list surface that consumes it. v1 ships tooltip-only on bar tap; the drill-in lands naturally in v2 once Search Plays ([Phase 5](#phase-5--flowsheet-archive-search--structured-filter-builder), [ADR 0009](./cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder)) exists as the row-rendering host.
- **dj-site convergence onto `POST /flowsheet/search`** (per [ADR 0009](./cross-repo-adrs.md#adr-0009--flowsheet-archive-search-is-a-distinct-ios-mode-with-a-reusable-structured-filter-builder)): a future ADR in [dj-site](https://github.com/WXYC/dj-site)'s repo (see [`dj-site/docs/adr/0006-search-plays-flowsheet-builder.md`](https://github.com/WXYC/dj-site/blob/main/docs/adr/0006-search-plays-flowsheet-builder.md)) would migrate dj-site's playlist search onto the new BS endpoint, retiring its current backend. Not committed in v1 — iOS and dj-site operate in parallel with their respective playlist-search backends until a separate consolidation decision is made.

## Parallel work opportunities

Inside a phase, these tracks have no shared files and no shared models — one developer can carry each in their own worktree.

- **Phase 1**: Catalog explorer substrate (one worktree) is the only sequential dependency for picks #3, #4, #9 — but the in-show companion (separate worktree) and pick #1 (third worktree, depends on the companion) can run in parallel with the explorer. Picks #3, #4, #9 then fan out as independent lenses once the explorer lands.
- **Phase 2**: Pick #5 (condition reports) and pick #6 (memos) touch entirely different surfaces (library detail vs. per-album memo storage) and can run in parallel worktrees. Pick #8 (artist deep dive) is the integration test for ADR 0002 + C1 and runs on its own thread.
- **[Phase 3](#phase-3--personal-stats--profiles)**: Picks #7, #10, #11 all consume [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround) endpoints but each owns its own VM, view, and DTOs — three parallel worktrees. Pick #12 (DJ profiles) shares nothing with the plays-endpoint trio and is a clean fourth worktree. Pick #15 (per-album histogram on Album Detail) consumes [ADR 0008](./cross-repo-adrs.md#adr-0008--per-album-play-history-is-a-first-class-api-surface-parallel-to-per-dj-plays)'s endpoint and shares the [Swift Charts](https://developer.apple.com/documentation/charts) histogram component with [Phase 5](#phase-5--flowsheet-archive-search--structured-filter-builder)'s pick #16 — fifth worktree, with the histogram component published to a shared Views module so pick #16 inherits it tested.
- **[Phase 4](#phase-4--review-workflow)**: The review feature is large but internally decomposable — the review editor, the MD queue dashboard, and the tag-vocabulary CRUD are three independent surfaces with shared DTOs. Three parallel worktrees once `ReviewService` lands in `WXYCAPI`.
- **[Phase 5](#phase-5--flowsheet-archive-search--structured-filter-builder)**: Three internal sub-tracks — (1) `FilterBuilder<FieldConfig>` reusable primitive, (2) Search Plays surface composing the primitive with its specific field-config, (3) histogram component shared with [pick #15](#phase-3--personal-stats--profiles) (already shipped in [Phase 3](#phase-3--personal-stats--profiles) — retested against Search Plays' larger-cap data). The primitive must land before the Search Plays surface integrates; the histogram is already shipped. Two-and-a-half parallel worktrees in practice.
- **Cross-phase**: When a phase is gated waiting on BS, the next phase's iOS-only setup work (DTOs in `WXYCAPI`, stub-based view-model tests, view scaffolding) can begin in a separate worktree against `StubRequestSession` fixtures. This is especially valuable before [Phase 3](#phase-3--personal-stats--profiles) — `WXYCAPI` typed methods for the plays endpoints can ship as a PR that's tested entirely against stubs while waiting on [ADR 0006](./cross-repo-adrs.md#adr-0006--per-dj-play-history-is-a-first-class-api-surface-not-a-search-workaround).
- **[Phase 0](#phase-0--qr-sign-in-for-the-shared-computer-scenario-parallel-track) alongside any phase**: QR sign-in ([ADR 0007](./cross-repo-adrs.md#adr-0007--qr-device-authorization-for-shared-computer-sign-in-to-djwxycorg)) shares no files or models with the catalog/in-show track. The three repos involved ([Backend-Service](https://github.com/WXYC/Backend-Service) auth app, [dj-site](https://github.com/WXYC/dj-site) login Forms, iOS [WXYCDJ](https://github.com/WXYC/wxyc-dj-ios) toolbar account menu) are touched in non-overlapping places. Phase 0 can run in a fourth parallel worktree from day one of [Phase 1](#phase-1--foundations) without coordination cost.
- **[Phase 5](#phase-5--flowsheet-archive-search--structured-filter-builder) vs [Phase 4](#phase-4--review-workflow)**: Search Plays (Phase 5) and Reviews (Phase 4) touch entirely different surfaces (search Tab + filter builder + histogram vs review editor + MD queue + tag vocabulary). No shared DTOs, no shared views, no shared BS endpoints. The two phases can run fully in parallel if developer capacity allows; the sequencing places Phase 5 after Phase 4 by default because Reviews is the larger known-priority delivery, not because of any technical ordering.
