Bin Maturity — per-entry badges + view summary

The Mail Bin grows. Without a maturity overlay, a DJ scrolling their bin sees just a list — every entry visually equal — and forgets which they've already aired versus which are still sitting unplayed. This pick layers two play counts and a freshness signal onto every row, plus a summary band that tells the DJ the shape of the whole bin at a glance.

Two counts because they answer different questions. You · N says "am I in a rut on this one, or have I moved on?" Station · N says "is this a station tentpole or a long-tail surprise that hasn't gotten the spins it deserves?" Together they distinguish a 0 / 218 (Yo La Tengo's Painful — heavily aired by everyone but you) from a 0 / 12 (Chuquimamani-Condori's Edits — fresh for the station too).

The orange Stale pill marks the cross-product: added ≥ 8 weeks ago AND you have 0 plays. It's the "you've been sitting on this — either play it or clean it out" prompt. 8 weeks is two months — long enough to forgive any reasonable backlog, short enough that the pill actually surfaces things.

Why the summary band? The per-row badges are useful while scanning, but the three tiles at the top answer the meta-question — "what's the shape of my bin right now?" — without scrolling. The stacked mix bar makes the ratio legible at a glance.

Try it

  • Tap a filter chip (Untouched, Aired by you, Stale) — list narrows, summary tiles dim contextually
  • Tap the sort icon (top-right) — sheet with 5 options slides up
  • Pick a sort — list reorders, sheet dismisses
  • Notice the orange Stale pill on entries sitting ≥ 8 weeks with zero plays from you
  • Compare entry #11 (Icky Mettle — 0/74, stale) vs #10 (Today's Active Lifestyles — 5/148, your most-played) — both are tentpoles for the station, only one is dormant for you

BS contract

Bin contents come from the existing GET /djs/bin endpoint — the per-album play counts join in as a separate batched lookup so this can ship as a pure additive layer.

GET /djs/{id}/has-played?album_ids=1,2,3,...
  -> { "1": 0, "2": 1, "3": 2, ... }

GET /library/play-counts?album_ids=1,2,3,...
  -> { "1": 12, "2": 8, "3": 21, ... }

# both fan out from a single Bin fetch:
GET /djs/bin
  -> [ { album_id, album_title, artist_name, alphabetical_name, label,
         code_letters, code_artist_number, code_number, format_name,
         genre_name, legacy_release_id }, ... ]

Correction (issue #77): the route is GET /djs/bin — no DJ id in the path; the bin is scoped to the bearer token. More importantly, there is no added_at: the bins table has exactly four columns (id, dj_id, album_id, track_title) and no timestamp, and the projection above is everything the endpoint returns. The staleness feature below therefore has no "when did I bin this" signal to work from as designed. The only insertion-order proxy that exists today is the bins.id serial, which the endpoint does not project. Adding a real timestamp means a migration on bins plus a backfill decision for existing rows — there is no historical value to recover. Verify against Backend-Service/apps/backend/services/djs.service.ts before designing further; api.yaml still documents a BinEntry shape (with an added_at) that nothing has ever emitted.

Performance notes

  • Badge latency is the binding constraint. DJ opens Bin → expects badges immediately. One batched has-played call (not N round-trips) is intentional.
  • Stale-ness is computed client-side from added_at + the personal count — no extra endpoint. (Blocked — see the correction above: added_at does not exist on bins or on the wire.)
  • The summary tiles and mix bar are also client-side aggregates over the in-memory bin. No /bin/summary endpoint needed.
  • If /library/play-counts proves too costly as a wholesale lookup, fall back to piggy-backing on the existing /library/info response shape (which already exposes a station play count per album).

Out of scope (later picks)

  • Tapping a badge → drill into the per-album play history
  • "Bulk clean up stale" action
  • Time-window selector on the station count (this prototype shows all-time)
