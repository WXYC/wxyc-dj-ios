Memos — private scratch notes with voice

Memos are private per-DJ notes attached to an album. Text is the spine; an optional voice clip (≤ 15s) rides along when speech is easier than typing — a mix instinct, a vocal hook to remember, a quick gut reaction recorded mid-show.

Why private only. DJs need to be candid about programming reactions — "first track is fine, the rest is dead air" — without performing for peers. Cross-DJ visibility turns honest notes into curated public takes, and we lose the candor that makes the feature useful. Memos stay scoped to dj_id server-side; the API has no surface for reading another DJ's memos.

Why per-album, not per-track. Track-keyed memo selection waits on Catalog-Track-Search (Track 3) and coordination item C3 — until the iOS app has a reliable way to identify "the second track on this CD," typing or paging through a track picker on a phone feels worse than just saying "watch the gap between 'Eras' and 'Cosoco'" in the album-level note.

Why 15s cap on voice. Object storage cost stays bounded (15s @ 64kbps AAC ≈ 120 KB per clip), the upload is fast enough to feel synchronous on station Wi-Fi, and short clips remain tractable for future server-side transcription (v2 idea: transcribe into body so memos become searchable).

Try it

  • Tap + New memo to open the composer sheet
  • In the composer, type to enable Save
  • Tap Record voice clip — preview the recording UI in mode Composer (recording)
  • Tap a memo's play button to flash through a faked waveform progression
  • Switch modes with the tabs at the top of the page

BS contract

GET /memos?album_id={id} POST /memos { album_id, body, clip_url? } POST /memos/upload-url → { put_url, clip_url, expires_at } PUT {put_url} (client uploads m4a/aac, ≤ 15s) DELETE /memos/{id}

Notes

15s hard cap enforced both client (record button auto-stops at 15.0s) and server (rejects clips with longer duration on the upload-url issuance and on POST /memos validation).

Object storage TBD: S3-compatible, signed PUT URL valid for 5 min, server stores only clip_url on the memo row — no bytes in Postgres.

Private — the GET /memos handler scopes by JWT's dj_id. No flag, no parameter — there's no way to request another DJ's memos.

Future v2: server-side transcription of the clip, stored alongside body, so memos become first-class search-targets in the flowsheet-archive search.
